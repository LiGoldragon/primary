# Nomos Language Train — Codex Dispatch

Dispatch prompt for a Codex worker joining the protos-engine family to implement
the authored-Nomos train. This document is the briefing; the bead train in
protos-engine's Dolt tracker (`bd`) is the work order. Read this whole document
before touching code.

## 1. Who you are, and why this train exists

You are a worker on the protos-engine family of repositories: `protos-engine`,
`core-nomos`, `core-ethos`, `core-logos`, `nomos-engine`, `raw-discovery`,
`structural-codec`, `name-table`, `sema-translator`, `signal-sema-translator`,
and neighboring micro-repos. Each repository is small and owns one thing;
cross-repository composition happens through published revisions, never
shared mutable checkouts. You will work across several of these repositories
in sequence as the bead train requires it.

The reason this train exists, in the psyche's own words
(`PsycheVisionReacquisition-2026-07-29.md` entry 4, dictated 2026-07-29):

> the entire reason why we have nomos is so that we can modify the
> transformation using the nomos language. So if the nomos language was never
> implemented, then the entire engine is currently a failure because the
> whole point of creating nomos was to be able to modify.

The authored path is currently missing entirely. `core-nomos` already runs
transformers as data — `MacroDefinition`/`MacroIdentity`/`ResultTemplate` with
a closed `Realize`/`Invoke`/`Splice` escape algebra, `MacroPackage`
content-hashed and executed by `nomos-engine` through `apply_enriched` — but
every transformer in production is built by hand in Rust
(`core-nomos/src/fixtures.rs`). There is no file format, no text syntax, no
loading from authored artifacts. Closing that gap is this train.

## 3. Vocabulary correction (entry 5) — read this before writing anything

The psyche ruled, dictating in full (entry 5, quoted here because it is easy
to under-weight in summary):

> I'm going to use the word transformer instead of macro because I think
> macro is overloaded ... this is really a type transformation.

And:

> if we talk about template, I think you mean string templates, in which
> case that's not at all what I'm looking for.

Concretely, in everything you write — code comments, commit messages, bead
notes, your own prose:

- Say **transformer**, not macro, for the concept. The existing Rust type
  names (`MacroDefinition`, `MacroPackage`, `MacroIdentity`, `MacroKind`,
  `ResultTemplate`, `GenerationClass`) predate this ruling and stay literal —
  you are not renaming types as part of this train unless a bead says so.
  If you introduce a rename bead, it is its own bead, not folded into
  functional work.
- Say **encoded form**, or **the true form** (the psyche's own alternate
  name for it today, consistent with the founding "used to be called
  true/core" language) for the data the transformation actually operates
  over. Transformation is strictly encoded-form to encoded-form. There is no
  string manipulation, introduction, or reading of any kind anywhere in the
  Nomos transformation path.
- Wherever `ResultTemplate` or "template" appears in your own writing,
  state plainly that it means a **typed Logos skeleton** — typed encoded
  data with typed placeholder (escape) positions — never a text or string
  template. This is not a stylistic preference; the psyche explicitly warned
  that "template" reads as string-templating to him and that is not what
  this is.
- The Nomos engine's runtime scope is the complete Ethos and Logos type
  universes, not one declaration's worth of types. Per entry 5: "Nomos is
  going to have to load all of the Logos types into its runtime because it
  has to convert into them, and it's going to have to load all of the Ethos
  types, obviously, too." Placeholders key the movement of typed values from
  Ethos input into generated Logos output — plural output types, including
  positional insertion into specific vector slots. Keep this in mind when you
  implement bead `protos-engine-po2.2` (EncodedForm/NameTable) and
  `protos-engine-po2.6` (engine loading): do not build a narrower,
  per-declaration-only model where the wider one is what is actually ruled.
- Entry 5 also names a forward direction, explicitly beyond this train's v1
  scope: transformation may eventually need to operate over the entire Ethos
  payload, cross-declaration, compiler-grade analysis (the psyche's own
  rustc analogy — lifetimes, ownership, types all analyzed together before
  code generation starts). Bead `protos-engine-po2.10` exists to hold this
  consideration so it is not lost. Do not build toward it speculatively; do
  not foreclose it either. `GenerationClass` (already a whole-ethos reader)
  and ScopeOf (already a whole-Domain-tree reader) are existing precedents,
  not exceptions to design around.
- Long-term framing, the psyche's own words, not this train's scope but
  worth carrying: "we might make Nomos ... the most load-bearing part that
  could do all of the correctness verification or more than what the Rust
  compiler actually does today ... Logos actually compile into assembly
  language through LLVM." This train is the first vertical slice of that
  trajectory. Build it capable and extendable; do not build a throwaway.

## 4. Standing laws — these bind every bead, unconditionally

- **No strings in the Nomos transformation, of any kind.** Not manipulation,
  not introduction, not reading. `ProtosEngineDesign` section 10: "in the
  nomos transformation (ethos to logos), there shall be *no string
  manipulation/introduction/reading of any kind*." Every identifier is
  resolved through the nametree; nothing is ever matched, built, or compared
  as text inside the transformation path.
- **Fields are positional. Field names are illegal everywhere in the
  encoded/authored data model.** Rust identifiers for positional fields are
  produced only at emission time through the ruled projection mechanism, not
  authored as named fields.
- **No aliases.** Do not introduce a second name, a compatibility shim, or a
  parallel path for something that already has a name or a path. If a rename
  or a new mechanism is needed, it replaces the old one; it does not sit
  beside it "for compatibility."
- **Translator-only allocation.** Nothing declares a coreID/encodedID except
  the sema-translator, and only when it receives a word it has not seen
  before (DesignReviewRulings entry 3). Do not invent a second allocation
  authority for Nomos transformer names or binding names, no matter how
  convenient it looks mid-implementation.
- **Micro-repo topology.** Each repository owns one thing. Do not collapse
  `core-nomos`, `nomos-engine`, `core-ethos`, or `core-logos` into each
  other, and do not add a dependency edge that does not already exist without
  checking whether it belongs in a different repository instead.
- **Published-revision pins.** Cross-repository composition happens through
  exact published revisions (git/jj commit hashes), pinned explicitly in the
  consuming repository — never a mutable branch reference, never a local
  path dependency in a committed state. When you close out a bead's work,
  record the exact revisions you published in the bead's notes (see section
  6).
- **Never edit psyche logs.** `RecoveredNomosVision-2026-07-29.md`,
  `PsycheVisionReacquisition-2026-07-29.md`, and any other design-log file
  recording a firsthand psyche ruling or dictation are append-only from the
  psyche's side and read-only from yours. If you believe one needs
  correcting, that is an open question for the psyche (section 5), not a
  file you edit.
- **Never claim a ruling is satisfied.** If a bead's acceptance criteria are
  not fully met, say so plainly in the bead notes and leave the bead open (or
  move it to blocked). Do not close a bead on partial, approximate, or
  "close enough" grounds. Equivalence claims in particular must be proven,
  not asserted (section 7).
- **Open questions go to the psyche, not to inference.** Two beads in this
  train are explicitly blocked pending psyche rulings
  (`protos-engine-po2.7` — ScopeOf helper identity and the recursion/Fold
  mechanism). Do not implement past an open ruling by guessing the answer,
  by picking "the more conservative option," or by treating a design
  document's proposal as if it were already approved. A proposal marked
  `[proposal]` or discussed as a "candidate" in
  `NomosAuthoredRulesDesign-2026-07-29.md` is not a ruling. When you reach a
  genuinely open question that blocks progress, stop, record it precisely in
  the bead's notes, and surface it — do not resolve it yourself.
- **Use beads to line up work and record progress in bead notes.** The bead
  train (`protos-engine-po2` and its children) is the work order. Claim a
  bead (`bd update <id> --claim`) before starting it. As you make progress —
  what you tried, what you published, what you found — append it to that
  bead's notes (`bd note <id> '<text>'` or `bd update <id>
  --append-notes '<text>'`), not only to your own working memory or a
  separate report. The next worker (human or agent) who picks this train up
  reads the bead notes first.

## 5. Equivalence-witness-first discipline

Every structural bead in this train that touches the production path
(`protos-engine-po2.4` through `.6`, and each generation-class migration
inside `protos-engine-po2.8`) follows the same discipline, named explicitly
in `protos-engine-po2.5`'s design: **do not claim equivalence from
inspection; prove it by running both paths over the same witness corpus and
comparing output.**

Concretely:

- The authored path and the existing Rust-built path (`fixtures.rs`,
  `generation.rs`) must produce the same `Lowering` (the same `EncodedItem`
  sequence and the same resolved names) over the same Ethos input, or an
  explicitly justified behavioral equivalence if content identity legitimately
  differs.
- This comparison is a gate in protos-engine's Nix check graph
  (`nix run .#check-all` and whatever specific check target the equivalence
  proof lives under), not a one-time manual proof you write up and move on
  from. If a later change to either path breaks equivalence, the build must
  fail, not a human review.
- Do not cut the production path over (`protos-engine-po2.6`) before the
  equivalence gate for the corresponding transformer package
  (`protos-engine-po2.5`) is green. Do not retire a hardcoded generation
  class (inside `protos-engine-po2.8`) before its individual equivalence
  proof is green. "It looks right" is not the bar; the gate passing is the
  bar.
- `SliceOneTransformation` (`core-nomos/src/slice_one.rs`) and the
  `fixtures.rs` constructors remain the reference/bootstrap implementations
  until their corresponding authored surface proves equivalence. They become
  test-only equivalence oracles after that, never deleted outright by this
  train unless a bead explicitly says so.
