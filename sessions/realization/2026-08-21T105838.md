Objective: continue realization flow `01a020ff` and sketch the implementation of the proposed Emacs extension.

Governing direction: the Emacs plugin is a standalone repository and an input to `criomos-home`. The prior flow, written psyche, and concrete repository integration surfaces are being reacquired before the implementation sketch is formed.

Recovered ground:

- Flow `01a020ff` established that the shared Dark transition succeeded and the independent one-shot `emacsclient --eval` projection failed without retained evidence. Chroma discarded output, ignored nonzero exit status, and had no retry or postcondition check. The exact transient Lisp error is unknowable.
- The prior agent proposal was an Emacs-resident `chroma-theme-mode` that queries and subscribes to semantic `(theme, revision)` state, applies and verifies the mapped theme, acknowledges success or bounded failure, and reconciles at startup and reconnect. It was a proposal, not a psyche ruling.
- The existing `CriomOS-emacs` repository is a scaffold for the whole Emacs distribution, already planned as a `criomos-home` input; it is not yet evaluable because the Blueprint package call lacks the required legacy `hob` argument. Whether the new plugin belongs there or in a distinct repository remains open.
- Chroma currently exposes a one-shot rkyv-over-Unix-socket command protocol and no public D-Bus service or theme revision/status model. The Home Emacs 30.2 build has working D-Bus support.
- `criomos-home` currently owns generated Ignis theme files, the Emacs service/distribution configuration, and the obsolete Darkman startup selection. Chroma owns semantic light/dark authority and directly runs the fragile Emacs process concern.

Proposed implementation anatomy for psyche review:

- Chroma remains desired-theme authority and gains a narrow session-bus theme protocol with current snapshot, monotonic persisted revision, change signal, consumer registration, and per-revision acknowledgement/status.
- A standalone Emacs package owns only the Emacs projection: subscribe/query/reconnect, map Light and Dark to declaratively supplied theme symbols, preserve unrelated overlay themes, reconcile idempotently, verify the postcondition, and report typed bounded failure while retaining full Lisp diagnostics locally.
- `criomos-home` pins the plugin input, builds/native-compiles it, supplies the Ignis theme mapping/load path, enables the resident mode, and removes Darkman plus the one-shot adapter. Theme generation remains in Home.
- The plugin repository proves Lisp state transitions and lifecycle against a fake protocol service; Chroma proves protocol/revision/status behavior; `criomos-home` provides the end-to-end Nix check with real Chroma and an isolated Emacs daemon.

Open psyche rulings: whether this is a distinct repository or the existing whole-distribution `CriomOS-emacs`; whether the narrow D-Bus protocol is the selected transport rather than a dedicated bidirectional Unix stream; and whether theme generation remains in Home while the plugin owns projection only.
