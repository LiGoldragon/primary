The psyche reports that the default browser is wrong and asks for a review of the current opening logic, recalling an earlier discussion about using something more capable than `xdg-open`.

Current objective: recover the relevant written psyche and implementation, then explain the present setup visually. No implementation change has been requested in this round.

## Findings

- Authored Home Manager logic creates an `xdg-open` wrapper backed by `handlr`, but the live shell selects the system xdg-utils `xdg-open`; the user-local wrapper is shadowed by `PATH`.
- `NIXOS_XDG_OPEN_USE_PORTAL=1` makes that system `xdg-open` send URLs and local files to the desktop portal. If the `handlr` wrapper won `PATH`, it would instead resolve MIME/scheme handlers and execute their desktop entries directly.
- Authored browser MIME associations name `chromium.desktop`, while the installed configured browser supplies `google-chrome.desktop`. Live handler queries therefore resolve HTTP, HTTPS, and HTML to GNOME Epiphany.
- The file side of the dispatcher is working independently: text/source types resolve to Emacs, PDFs to Zathura, and directories to Nautilus.
- Historical reports describe the intended generic shape as `xdg-open` command compatibility backed by `handlr`, including editor-specific routing. No surviving written psyche or report settles a replacement opener or intended default browser.
- Browser-automation history favors supervised use of the visible main Chrome session, but that is a distinct concern from desktop URL association.

## Handoff

Review is complete. No opening configuration or executable behavior was changed.
