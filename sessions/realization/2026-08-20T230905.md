Objective: determine from witnesses why Emacs did not follow the Chroma-owned theme switch reported in session `01a01b52`, identify any other affected consumers, and locate the fragile boundary that allowed a simple appearance projection to fail. This round authorizes investigation, not implementation or live mutation.

Governing psyche: `psyche/Vision/noctalia.md` rules that Noctalia must yield light/theme authority to Chroma. No new psyche ruling has landed in this flow.

Current state: the prior realization record says Chroma, the Settings portal, dconf, GTK, and Noctalia were live Dark after deployment, while Chrome and Emacs were not witnessed. The current failure report supersedes any implication that the whole desktop theme projection was proved end-to-end.

Chronology finding: Emacs was absent from the implementation diff and verification matrix. The deployment changed Chroma, Noctalia, their Home integration and pins, then replaced the stale Noctalia process, restarted Chroma through its supported reapply path, reconciled Noctalia's mutable mode, and reloaded Noctalia. It neither changed nor restarted Emacs. The final “theme fix is deployed and live” statement was witnessed for Noctalia, dconf, the Settings portal, and GTK request state only; it was not an end-to-end application rendering claim.

Emacs-path findings: the active Emacs init reads the obsolete Darkman state file only at startup and installs no live theme subscription. Current Chroma instead projects theme changes by spawning `emacsclient` with an eval form. That adapter discards client output, ignores a nonzero exit status, has no retry or later reconciliation, and reports only spawn/wait/timeout failures. At the original session startup, Emacs and Chroma began in the same second while the Emacs server socket appeared about four seconds later, creating a witnessed race window whose exact client result is unavailable. Later Chroma restarts occurred after Emacs was ready; current Emacs and Chroma are both Dark.

The current automatic-transition failure is broader than Emacs: Chroma rejects GeoClue's repeated 26 km fixes under its 1 km accuracy limit, reports `SolarClockUnavailable`, and consequently cannot resolve the configured sunrise/sunset waypoints. It remains at its Dark default, so no current Light transition exists to project to any consumer. Whether the reported symptom was the historical one-shot startup miss or the later absent scheduled transition is unknown because the observation time was not recorded.

Shared-surface audit: current live values converge on Dark in Chroma, Emacs, Noctalia, dconf, the Settings portal, and both GTK/GNOME portal backends. No current visual divergence was proved. Noctalia nevertheless repeatedly logged `portal color-scheme unavailable: System.Error.ENXIO` after the portal services were already active; its retained external fallback masks that confirmed projection-read failure. The portal has split generic and Niri-specific backend selection, though the active backends currently agree, so backend ambiguity is exposure rather than a proved cause. A Chrome process separately dumped core with SIGTRAP during the earlier process-replacement window, but no evidence connects the crash to appearance.

Diagnosis: if the reported miss was an expected automatic Light transition, the witnessed cause is upstream: Chroma had no valid location and generated no transition. If it was the original startup/application event, the exact historical client result is unknowable because it was discarded; the concrete Chroma-before-Emacs-server race plus ignored nonzero exit status is the strongest bounded explanation. The fragility is systemic: Chroma writes settings or launches application-specific commands and declares success without acknowledgement from consumers; consumers have independent startup, portal, fallback, and legacy-state paths; there is no end-to-end desired-state reconciliation or durable live-transition witness.

No source, generated configuration, live setting, service, process, or deployment was changed during this investigation. The work is tracked by `primary-v6j`.

This disconfirms the preceding use of `SolarClockUnavailable` as the incident cause.
