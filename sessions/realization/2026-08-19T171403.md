## Lojix ledger and root-deployment skill proposal

The living psyche asked what Lojix's ledger is and requested a proposal, with explicit approval required after the proposal before any skill edit. The exact approval boundary was logged in `psyche/Vision/skillDesigning.md`. No Curriculum source, manifest, generated skill, or deployment file was changed.

Source audit established that “ledger” in the conversation means Lojix's durable sema state plane rather than one formal table: deployment records and in-flight jobs, live-generation projections, GC roots, events, outbox delivery records, and pending transition intents. Lojix queries read these committed records; they do not probe `/nix/var/nix/profiles/system` or `/run/current-system`. A host activation sets the Nix profile before `switch-to-configuration`; if the latter returns nonzero after changing the host, Lojix terminalizes the deployment without recording `GenerationActivated`. That is how deployment 16 produced live system generation 163 while ledger `Current` remained generation 7.

The approval-pending proposal replaces the currently inactive mixed Lojix note with an activated deployment-focused runtime skill. It uses current `Deploy.Host` with `CompleteHost` composition and `Deploy.UserEnvironment` vocabulary; configured root versus target-user transport fields; direct deploy authority without transport reconfirmation; pushed immutable consumer source; terminal watch/query; and target-link inspection when a failed terminal may follow a partial activation. Supporting proposal scope includes root deployment variables plus module/output manifest activation. Exact wording is presented to the psyche in the response; no edit occurs without explicit approval.
