# Driving his own Chrome: four routes

Source-only comparison, 2026-11-15. No browser, extension UI, account, profile storage or credential was opened; nothing was attached, installed, moved or restarted. Installed Playwright source was read; other implementations were read upstream. Build sizes below are judgments, not measured estimates.

## Short answer

**Chrome DevTools MCP is the nearest existing alternative, but its ordinary auto-connect route still has a Chrome permission dialog.** A launch-owned debugging pipe removes extension-token handling and a listening TCP port, but needs a persistent owner: it is not an endpoint an arbitrary later process can simply attach to. A custom native-messaging extension can retain the current everyday profile and put access behind local IPC permissions; it is the most new software. The working Playwright bridge remains the least-change option, with its known token-in-argv defect.

These are principally different transports and permission boundaries. Playwright can itself drive a CDP-accessible Chrome; changing the transport need not mean replacing its page automation library.

## (a) Chrome DevTools MCP, Chrome's remote-debugging setting

- **Secret / exposure:** Chrome 144+ offers `--autoConnect` after remote debugging is enabled at `chrome://inspect/#remote-debugging`. No extension pairing token is required. Endpoint discovery uses Chrome's data-directory information; upstream source explicitly reads `DevToolsActivePort` for a supplied directory. The local WebSocket address is connection metadata, not a substitute for the browser's approval. Avoid adding header credentials through command-line `--wsHeaders`.
- **Interaction:** enable the setting once; Chrome shows an Allow dialog for a connection attempt. The documentation does not promise permanent approval, so this is not a demonstrated unattended reconnect route. The machine could handle an authorized dialog through the desktop; nothing need be asked of him. Existing Chrome need not move its profile for this setting-based route; this differs from the startup switches in (b).
- **Capability / work:** existing navigation, input, JavaScript, network/debugging, screenshots and performance tools; the documented connection reaches all windows of the selected profile. Small packaging/client-configuration work, plus an approval-handling boundary. It is not a narrow read-only grant. Disable the package's separate usage statistics and CrUX requests if those external emissions are unwanted. [Connection guide](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md), [connection source](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/8ba2ac945ebaf1adb92208c29f3a30e73a920956/src/BrowserManager.ts), [options](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/8ba2ac945ebaf1adb92208c29f3a30e73a920956/src/config/browser-options.ts), [capabilities and emissions](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/README.md).

## (b) His everyday Chrome, a named data directory, startup debugging

- **Chrome 136 rule:** branded Google Chrome on Linux, macOS and Windows ignores both `--remote-debugging-port` and `--remote-debugging-pipe` for its default data directory. A genuinely non-default `--user-data-dir` is required; choosing `Profile 1` inside the default root does not change that root. This restriction on switches does not disprove the newer UI-enabled route in (a). [Chrome announcement](https://developer.chrome.com/blog/remote-debugging-port), [enforcement source](https://github.com/chromium/chromium/blob/main/chrome/browser/devtools/remote_debugging_server.cc).
- **Migration / interaction:** one coordinated Chrome shutdown, move of the whole user-data root, and restart through the configured wrapper—not a second profile copy. Preserve `Local State` and all profile directories, rather than moving only a profile subdirectory. Session continuity after relocation is **unverified**: Chrome documents different encryption keys for non-standard directories; a move is not a source-backed guarantee that every login survives. Every launcher must select the same new root. Once running with startup debugging, there is no extension token or Playwright Allow dialog per attach.
- **Port security:** no built-in pairing secret is needed. Chrome binds its startup TCP server to loopback, but loopback is not a Unix-user permission boundary: other local users/processes in that network namespace can reach it unless separately restricted. Protecting `DevToolsActivePort` does not protect an unauthenticated discoverable port. A random port is not authentication. Ordinary remote hosts cannot directly reach a loopback-only listener, but forwarding or an exposed proxy changes that. Profile path and port can appear in argv. [Listener source](https://github.com/chromium/chromium/blob/main/chrome/browser/devtools/remote_debugging_server.cc).
- **Pipe security / ownership:** the authority is possession of inherited pipe descriptors, not a token or publicly listening socket. Other local users have no normal endpoint to connect to; same-user descriptor/process access depends on Linux process protections, and root remains privileged. A supervisor must create and retain the pipe from launch, then expose any later-client IPC with explicit permissions. Current DevTools MCP launches through Puppeteer with `pipe: true`; its existing-connect branches use WebSocket discovery/URLs, not an arbitrary pre-existing pipe. Chrome's pipe-disconnect callback closes the browser, so supervisor lifetime is also everyday-Chrome lifetime. [MCP launch/connect source](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/8ba2ac945ebaf1adb92208c29f3a30e73a920956/src/BrowserManager.ts), [pipe implementation](https://github.com/chromium/chromium/blob/main/content/browser/devtools/devtools_pipe_handler.cc), [disconnect callback](https://github.com/chromium/chromium/blob/main/chrome/browser/devtools/remote_debugging_server.cc).
- **Capability / work:** browser-wide CDP automation and inspection. Port variant: modest wrapper and migration work, substantial access-policy consequence. Persistent pipe variant: more lifecycle/IPC work, or accept MCP as Chrome's long-lived launcher; a Nix flag alone is insufficient. No migration is authorized by this comparison.

## (c) Our own extension with native messaging

- **Secret / exposure:** Chrome starts a registered native host and exchanges framed messages through stdin/stdout. Its manifest permits specific extension origins; no browser token needs to enter argv. The origin argument and host manifest are identifiers, not secrets. A machine-facing Unix socket could use an owner-only parent directory, restrictive socket permissions and peer credentials; those protections would be ours to implement. `allowed_origins` alone is not local-program authentication: another program can launch the host itself. Same-user programs and root remain inside the relevant OS trust boundary. [Native messaging contract](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Chromium security FAQ](https://github.com/chromium/chromium/blob/main/extensions/docs/security_faq.md).
- **Interaction / capability:** install and grant the extension's declared permissions once, register its native host; no recurring pairing dialog is inherent to native messaging. `activeTab`-only access would still require a user gesture; persistent declared host permissions or `debugger` change that tradeoff. A debugger-based extension can read/drive selected tabs through CDP, but only Chrome's exposed domains and permitted pages; native messaging by itself grants no page access. Chrome can still display debugger/extension indicators. [Debugger API and limits](https://developer.chrome.com/docs/extensions/reference/api/debugger).
- **Work:** largest new implementation: extension, host, deployment, request/response protocol, tab/frame routing, permission enforcement, reconnection and cleanup. A named-field reader could be much smaller than a general browser driver. The Claude/Codex analogy does not establish their actual security architecture; neither extension was audited here.

## (d) Current working Playwright extension bridge

- **Secret / exposure:** saved extension token enters the wrapper through the environment or gopass. Installed relay code puts it into `connect.html?token=…` and Chrome's spawned argv. The extension removes it from the visible URL after loading; that does not undo process-argument exposure. Same-user environment/process access and privileged readers remain relevant. Extension authentication data is stored in its profile localStorage. An input configuration file alone cannot remove the URL/argv hop.
- **Interaction / capability:** the confirmed matching-token route reconnects without an Allow click; token-free use requires Allow & select on the connect page. It drives the real logged-in browser through `chrome.debugger`; current Default extension groups controlled tabs. This is powerful browser access, not a read-only account-data API. Keep page selection and read boundaries explicit.
- **Work:** existing operational route, least new software. Moving automatic authentication off argv requires a changed relay/extension exchange or a different transport. Installed CLI `--raw` is not a snapshot-free guarantee; a narrow reader still needs a supported containment contract. Prior runtime success and cleanup are reported evidence, not rerun here.
