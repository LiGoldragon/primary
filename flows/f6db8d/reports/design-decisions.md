## 1. `Datomizable`: one conversion or two? (open-items A1)

### What is actually there — three different answers in circulation

**Witnessed**, `Vision/protos.md:70-85`. The table gives `Datomizable` to two
different bearers:

| type | kind | becomes |
|---|---|---|
| `Protos` | `Datomizable`, or `Ethosizable` further on | its concept |
| composition | `Datomizable` | datom |

and the snippet under it gives them two different signatures:

```rust
impl Datomizable   for Protos { fn datomize(&self) -> Result<Datom, Error>; }
impl Datomizable   for Person { fn datomize(&self, at: Path) -> Datom; }
```

Those differ in arity (`at: Path` present or absent) and in fallibility. They
are not two impls of one trait; as written they cannot both compile. The same
doubling holds for `Protosizable`, borne by `String` (descent, fallible) and by
`Datom` (ascent, infallible) in the same snippet.

**Witnessed**, datom-codec 0.26.3 (`627db67`, clean tree),
`/git/github.com/LiGoldragon/datom-codec/src/core.rs:126-135`:

```rust
pub trait Compositional: Sized {
    fn compose(datom: &Datom, budget: &mut Budget) -> Result<Self, Error>;
}
pub trait Datomizable {
    type Output;
    fn datomize(&self, at: Path) -> Self::Output;
}
```

The code resolved the contradiction by adding an associated `Output` and giving
both directions the `Path` argument. `Output = Result<Datom, Error>` for
`protos::Protos` (`src/composition.rs:165-170`); `Output = Datom` for every
value type (`src/composition.rs:172-175`). So today **one kind names both
conversions**, discriminated only by an associated type.

**Witnessed**, a third answer, in the `datom` skill's authored source
`/git/github.com/LiGoldragon/Curriculum/skills/datom.md:75-95` (last touched
`67459de`, 2026-09-04):

```rust
pub trait Corporal<C: Protosizable>: Embodied {
    type Fault;
    fn incorporate(concept: C) -> Result<Self, Self::Fault>;
}
pub trait Datomic: Corporal<Datom, Fault = Fault> {
    fn datomize(&self) -> Datom;
}
```

**`Corporal`, `Embodied`, `incorporate` and `Fault` exist in no repository.**
A grep across datom-codec, protos and ethos-zero returns zero hits for each
(witnessed by the read-only subflow that read all three). The skill that every
flow loads before touching datom describes a vocabulary that was never built.
That is a tenth false statement in the skill corpus, of the same class as the
nine already filed against the `lojix` skill, and it is the first thing to fix
regardless of which way item 1 is decided.

### What the governing Intent says

**Witnessed**, `Intent/conversion.md` in full:

> A kind names one conversion and is borne by the type that undergoes it,
> named for the layer it becomes. Each step yields a wholly new type. A chain
> is composed in the open, never folded into a kind on its first type.

Intent outranks Vision. By the letter of it, `Datomizable` with two `Output`
shapes is already wrong: it names two conversions.

But the naming rule itself is the deeper problem, and this is the finding worth
the living's attention. "Named for the layer it becomes" is **direction-blind**.
Descent `Protos → Datom` and ascent `composition → Datom` both "become datom",
so the rule mints the same name for both. The same collision hits `Protosizable`
(`String → Protos` and `Datom → Protos`). The collision is not an oversight in
one line of Vision; it is generated by the rule, and it will recur at every
layer boundary the protos family adds.

### Researched

The weight of practice is decisively two traits, and the reasons are mechanical
rather than stylistic.

- **Every mainstream Rust codec splits.** serde `Serialize`/`Deserialize<'de>`;
  `From`/`TryFrom`; `FromStr`/`Display`; rkyv `Archive`/`Serialize<S>`/
  `Deserialize<T,D>`; bincode 2 `Encode`/`Decode<Ctx>`; borsh. In each case a
  parameter belongs to one side only — a lifetime, a context, an error type —
  and a merged trait would inflict it on the other side's use sites.
  (https://doc.rust-lang.org/std/convert/trait.TryFrom.html)
- **The one mainstream unifier pays a visible bill.** `prost::Message`
  (https://docs.rs/prost/latest/prost/trait.Message.html) carries both
  directions, and to do so it exiles `encode` behind `where Self: Sized` and
  `decode` behind `where Self: Default`. The result: `dyn Message` exists and
  can do nothing, and **every** implementor is forced to be `Default` — a
  constraint imported purely by the decode half onto types that are only ever
  written. That is exactly the trade our `Datomizable<Output = …>` makes in
  miniature: a kind whose bound constrains nothing useful at a generic call
  site.
- **The shape difference is not cosmetic.** Decode is an *associated function
  returning `Self`*; encode is a *method on `&self`*. `Compositional::compose`
  is already written `compose:` in the ethos (the no-self sigil,
  `datom-codec-kinds.ethos:9`) while `datomize` is written `datomize.`
  (shared-reference sigil). The two sigils in one file are the ethos itself
  saying these are different kinds of capability.
- **The pair has a proper name, and it is not "one conversion".** An infallible
  build plus a fallible match is exactly a **Prism** in optics
  (https://oleg.fi/gists/posts/2017-04-18-glassery.html; codec-as-prism written
  up at https://yairchu.github.io/posts/codecs-as-prisms-asts). The Prism laws
  are asymmetric: `match (build a) = Right a` always; `build <$> match s = Right s`
  only where the match succeeded. A single trait asserting "these are one
  conversion" would be **claiming an isomorphism we do not have** — datom text
  has non-canonical spellings (bare vs guillemeted strings), so `datomize ∘
  incorporate` is not the identity on text. Two kinds plus a round-trip
  property test states the truth; one kind states a falsehood.
- **Systems that genuinely unify pay in expressiveness.** Rendel & Ostermann,
  *Invertible Syntax Descriptions* (Haskell Symposium 2010,
  https://www.informatik.uni-marburg.de/~rendel/unparse/) get one description
  yielding parser and printer, at the cost of losing `Functor`/`Applicative`/
  `Monad` entirely and writing everything point-free through partial
  isomorphisms. Boomerang (POPL 2008, https://dl.acm.org/doi/10.1145/1328438.1328487)
  gets it at the cost of being a separate language. The arrangement that won
  everywhere else is: **unify at the schema/derive level, split at the trait
  level** — which is precisely what Ethos already does with
  `#[derive(Datomizable, Compositional)]`.

### The decision

**Two kinds, and `Datomizable` keeps only the ascent.** Specifically:

- `Datomizable` is borne by a composition and by `Datom`'s own children; it is
  `fn datomize(&self, at: Path) -> Datom`, infallible, with **no associated
  `Output`**. The associated type goes away, which is the whole point: a bound
  `T: Datomizable` then means something.
- The descent `Protos → Datom` is a different kind with a different name. It
  already exists in the code under the right name and is merely shadowed:
  `DatomForming` (`src/composition.rs:5-7`,
  `fn datom_form(&self, path: Path) -> Result<Datom, Error>`). Keep it; delete
  `impl Datomizable for protos::Protos` (`src/composition.rs:165-170`), which
  is a one-line forwarder to `datom_form` and exists only to satisfy the Vision
  table.
- `Compositional` keeps the descent `Datom → composition` as an associated
  function, which is what it already is, and takes back `ARITY` per the living's
  ruling of this morning (`flows/f6db8d/vision/arity.md`) — a sibling flow owns
  that change; nothing here conflicts with it.
- The bundling super-kind that the `datom` skill calls `Datomic` may stay as a
  *name for the pair*, declared as `Datomic.{ [ Datomizable Compositional ] [] [] [] }`
  with a blanket association and **no capability of its own**. That is circe's
  `Codec[A] extends Decoder with Encoder` and play-json's `Format extends Reads with Writes`
  — the unified name is always derived from the two primitives, never a primitive
  itself. If the living does not want the extra name, drop it; nothing depends on it.

### Alternatives rejected

- **Keep one `Datomizable` with `type Output`** (today's code). Rejected: the
  bound constrains nothing, `prost` is the cautionary precedent, and it
  contradicts `Intent/conversion.md` by the letter.
- **Ship the skill's `Corporal`/`Datomic`/`incorporate`/`Fault` vocabulary.**
  Rejected on two grounds. `Corporal` is not qualifier-named, against
  `Vision/ethos.md:54` ("Kinds are qualifier-named: Runnable, Textualizable,
  Structural, Embodied"); and `Fault` was already renamed to `Error` in
  ethos-zero (`recent-vision.md` item 9). The skill is a stale design sketch,
  not a specification.
- **Name the pair an isomorphism / `Iso`.** Rejected: datom text is not
  canonical, so the second Prism law does not hold. Naming it `Iso` would be a
  false claim in the type system.
- **Rename the descent to `Datomizing`/`Datomization`.** Rejected:
  `Vision/ethos.md:54` wants qualifier names, and a noun-form name for a kind is
  the thing that rule exists to prevent.

### Vision lines affected

- `Vision/protos.md:72` — the table row `| \`Protos\` | \`Datomizable\`, or \`Ethosizable\` further on | its concept |`.
  **Superseded.** Replace with a row naming the descent kind separately, e.g.
  `| \`Protos\` | \`DatomForming\`, or \`EthosForming\` further on | its concept |`.
- `Vision/protos.md:79-81` — the three-line snippet. `impl Datomizable for Protos`
  becomes `impl DatomForming for Protos`; `impl Protosizable for String` and
  `impl Protosizable for Datom` need the same treatment (the descent one becomes
  `BoundedProtosizable`, which already exists in protos-kinds.ethos and already
  carries the budget the descent needs).
- `Vision/protos.md:65-66` — the naming rule, *"Kinds are borne by the type
  converted and named for the layer it becomes."* **Amend, do not delete.** The
  rule is right for the ascent and generates collisions on the descent. Proposed
  amendment: *"Kinds are borne by the type converted. An ascending kind is named
  for the layer it becomes; a descending kind is named for the act of forming
  that layer, because descent may fail and ascent may not."* That one sentence
  removes the whole class of collision, including the `Protosizable` one.
- `Intent/conversion.md` — **unaffected and vindicated.** This decision is what
  that Intent already says.

### Implementation plan

Repository `datom-codec`, one breaking release.

1. `datom-codec-kinds.ethos:8` — `Datomizable.{ [] [ Output ] [] [ datomize.{ [ Path ] [ Output ] } ] }`
   becomes `Datomizable.[ datomize.{ [ Path ] [ Datom ] } ]`. Regenerate
   `generated-contract/datom-codec-kinds.rs`; the committed-output freshness test
   is the gate.
2. `src/core.rs:132-135` — drop `type Output`, return `Datom`.
3. `src/composition.rs:165-170` — delete `impl Datomizable for protos::Protos`.
   Its four call sites are `Potential::actualize` (`src/core.rs:422`) and three
   tests; each becomes `.datom_form(Path::new())`, which is what the forwarder
   called anyway.
4. `crates/datom-codec-derive/src/lib.rs:189-199` — the struct arm's bound list
   currently spells `Datomizable<Output = ::datom_codec::Datom>`; the bound
   collapses to `Datomizable`. Same in the enum arm.
5. `datom-codec.ethos:22` — same declaration change in the data file.
6. If the living wants the bundling name: add `Datomic` to
   `datom-codec-kinds.ethos` as a superkind of `[ Datomizable Compositional ]`
   with no capabilities.

Wire impact: **none.** No text form changes, no rkyv archive changes. This is a
Rust API break only. Consumers affected: every crate that writes
`T: Datomizable<Output = Datom>` in a bound — a grep of the estate found the
spelling only inside datom-codec's own derive macro, so the blast radius is one
repository plus a version bump that dependents pick up on their next repin.

Tests: the existing round-trip suite is the gate. Add one property test
asserting the Prism law that actually holds — `compose(datomize(x)) == Ok(x)`
for every fixture type — which is the thing a merged trait was pretending to
assert.

Also owed, independent of the decision: correct
`/git/github.com/LiGoldragon/Curriculum/skills/datom.md:75-95` to the shipped
vocabulary, and regenerate the skill trees. Right now every flow that loads the
`datom` skill is told to implement four types that do not exist.

## 2. Single-field structs: refused, or `X.T` newtypes? (open-items A9; `recent-vision.md` item 12)

### What the psyche said, and the trap in it

**Witnessed**, `flows/8e9e77/vision/single-field-structs.md`, 2026-09-08, typed:

> I think we should possibly even refuse single-field struct types and ethos,
> and instruct against them even in Rust, because those should be new types.

> This should be a new type and not a struct with just a single element in it.
> ... a new type should be just the name of the type and then the separator,
> which is a period, and then the name of the contained type. ... A new type
> generally is like `name.string`, `age.integer`.

The trap: the form the psyche named for a new type, `X.T`, is the form
ethos-zero lowers to a Rust **alias**, and `Vision/ethos.md:255-256` says in so
many words that an alias *"is not a new type and cannot carry a derive."* So the
psyche asked for a new type and pointed at the one construct Vision defines as
not being one. That is the whole of item 2, and it has a clean resolution.

### What the code does

**Witnessed**, ethos-zero 8.0.1 (`de3d992`),
`/git/github.com/LiGoldragon/ethos-zero/src/conception.rs:390-398`. The
alias-vs-struct decision is made **purely on the body's enclosure and never on
arity**:

```rust
        if let Some(p) = body.children(Enclosure::Braced) {
            Ok(TypeDeclaration::Struct(identity, p.references()?))
        } else if let Some(v) = body.children(Enclosure::Bracketed) {
            Ok(TypeDeclaration::Enum(identity, v.variants()?))
        } else {
            Ok(TypeDeclaration::Alias(identity, body.conceive()?))
        }
```

Braced → struct, bracketed → enum, bare → alias. `X.T` is the third arm and
emits `pub type X = T;` (`src/generation.rs:670-679`). There is no arity-1
refusal anywhere.

**Witnessed**, the seam. `protos.ethos:17` is the only arity-1 product
declaration in production code across protos, datom-codec and ethos-zero (the
other nine hits are ethos-zero test fixtures). It declares
`ReaderBudget.{ Integer }` and generates
`pub struct ReaderBudget { pub integer: i64 }`
(`protos/generated-contract/protos.rs:83-85`) — a field named after the
intrinsic, because a one-position brace gives the generator nothing else to name
it with. The hand-written type it is supposed to mirror is
`pub struct ReaderBudget { pub remaining: usize }` (`protos/src/core.rs:67-70`).
And datom-codec then hand-patches the codec for it
(`datom-codec/src/composition.rs:595-600`):

```rust
impl Datomizable for protos::ReaderBudget {
    type Output = Datom;
    fn datomize(&self, at: Path) -> Datom {
        (self.remaining as Integer).datomize(at)
    }
}
```

That hand-written impl datomizes to the **bare integer**, unwrapping the single
position — the opposite of what the derive would emit for the same declaration
(`crates/datom-codec-derive/src/lib.rs:189-199` wraps every struct arity in
`Form::Struct`). So the estate's one arity-1 production declaration has already
been hand-corrected to behave the way a collapse rule would make it behave
automatically. The derive itself already has the collapse — for enums:
`lib.rs:140-143` unwraps a one-field variant to its body, `lib.rs:189-199`
does not do the same for a one-field struct. The asymmetry is the defect.

### Researched

- **The two constructs are genuinely different tools and both are needed.** A
  type alias is *transparent* (no identity, no instances, no distinct checking);
  a newtype is *generative* (new identity, own trait impls, prevents mixing two
  Integers that mean different things). Haskell `type` vs `newtype`; Go
  `type A = B` vs `type A B`, where the spec is explicit that "a defined type is
  different from any other type, including the type it is based on" and only a
  defined type can carry methods (https://go.dev/ref/spec,
  https://go.dev/blog/alias-names); Ada `subtype` vs `type … is new …`; Scala 3
  `opaque type` (https://docs.scala-lang.org/scala3/book/types-opaque-types.html),
  which demonstrates that the runtime cost of the generative form is an
  implementation artifact, not inherent.
- **The pattern literature is unanimous that the generative form is what domain
  code wants**: Primitive Obsession (Fowler, *Refactoring*), Whole Value (Ward
  Cunningham, https://c2.com/ppr/checks.html), Tiny Types, Domain Primitives
  (*Secure by Design*), and "parse, don't validate" for the single construction
  point.
- **ASN.1 corrects a premise worth correcting.** A type *assignment*
  `X ::= INTEGER` does **not** create a distinguishable type: the named type
  keeps the base's tag, ASN.1 equivalence is tag-based, and `A ::= INTEGER` and
  `B ::= INTEGER` cannot coexist in a `CHOICE`
  (https://www.oss.com/asn1/resources/asn1-made-simple/asn1-quick-reference/asn1-tags.html).
  The generative mechanism in ASN.1 is *tagging*, `X ::= [0] INTEGER`. The
  lesson for us is sharp: **naming alone reads as transparent to everybody**, so
  if `X.T` is to be generative it needs a marker, or it will be misread forever.
- **No IDL refuses the one-field product.** Smithy generates an alias for a
  named simple shape and explicitly warns against inventing wrapper types where
  a built-in exists
  (https://smithy.io/2.0/guides/building-codegen/mapping-shapes-to-languages.html),
  but does not refuse single-member structures. Thrift's `typedef` is
  transparent and single-field structs are unremarkable. Cap'n Proto's `using`
  aliases with no nominal effect. FlatBuffers has no alias at all, so a wrapper
  is the only way to name anything. **Protobuf is the most telling**: it
  retired `google/protobuf/wrappers.proto` and the current header recommends
  "embed your value in your own wrapper message which can be specifically
  documented" — protobuf explicitly endorsing the hand-written single-field
  message over a generic one.
- **The decisive Rust-specific argument, which no schema-language survey
  supplies: orphan rules.** `datom-codec` cannot implement `Datomizable` or
  `Compositional` for `String` or `i64` from a downstream crate. Today it
  can only because it owns those impls itself. The moment a generated contract
  wants dialect behaviour attached to *its own* named scalar — a
  `LockName` that datomizes differently from a bare `String`, a `Meters` that
  refuses a negative — an alias makes it impossible and a newtype makes it
  trivial. An alias-only schema language is structurally unable to attach
  behaviour to a name.

### The decision

**Do not refuse the one-field product until `X.T` is generative; then refuse it
as a redundant spelling.** Two changes, in this order, and the order matters
because doing the second first breaks protos's own gate:

**(a) Make `X.T` emit a newtype, not an alias.** `X.T` becomes
`pub struct X(pub T);` with the full derive stack. This is what the psyche
asked for in plain words — *"a new type should be just the name of the type and
then the separator, which is a period, and then the name of the contained
type"* — and it is what Vision currently forbids. This is the Vision line that
must be superseded, not the psyche's.

Consequence to be paid honestly: `Vector<T>` aliases and the like. Today
`SyntaxError.Vector<FilePath>` emits `pub type SyntaxError = Vec<FilePath>;`. If
every `X.T` becomes generative, that becomes `pub struct SyntaxError(pub Vec<FilePath>);`.
That is *correct* by the same argument (a `SyntaxError` is not a `Vec<FilePath>`;
it is a thing that contains one) but it is a large mechanical change across every
generated contract in the estate. Two ways to take it:

- *All at once*, which is the honest reading of "everything moves". Every
  generated contract regenerates; every consumer adds `.0` or a `From`. Large,
  mechanical, and gated by each repository's own freshness test.
- *With a marker*, which is ASN.1's answer: keep `X.T` transparent and add one
  generative spelling. But the psyche named `X.T` specifically, so a marker
  would be inventing syntax against a stated preference. **Recommend all at
  once**, and say plainly that it is the larger change.

**(b) Then refuse `X.{ T }`.** Once `X.T` is generative it is the better
spelling of the same thing in every case, so the one-position brace becomes a
redundant second way to say it — and `Vision/ethos.md`'s closing law is *"Any
repetition in ethos syntax is an implementation failure."* A new `Problem`
variant in `Checkable` refuses it, naming the `X.T` replacement in the refusal
text. `protos.ethos:17` becomes `ReaderBudget.Integer`, which then generates
`pub struct ReaderBudget(pub i64)` — a real newtype whose hand-written
counterpart at `protos/src/core.rs:67` can finally be deleted rather than
shadowed, and whose datom form is the bare integer the hand-patched impl in
datom-codec already produces. **The hand patch at
`datom-codec/src/composition.rs:595-600` disappears.** That is the test that
this decision is the right one: it deletes code rather than adding it.

Note the interaction with the ARITY ruling, which a sibling flow is
implementing. With (b) in place, `Compositional::ARITY` is never 1 for a
struct, because arity-1 structs cannot be declared. The arity-1 arm the
enum derive has (`datom-codec-derive/src/lib.rs:140-143`) then stays where it
belongs — on variants, where a one-field variant carrying its type's own form is
already ruled (`Vision/datom.md:132`) — and the struct derive needs no arity-1
arm at all. `recent-vision.md` item 12 step (d) proposed adding one; with this
decision it is unnecessary, which is one fewer branch.

### Alternatives rejected

- **Refuse `X.{ T }` now, leaving `X.T` an alias.** Rejected, and it is the
  option the open-items entry leans toward. It leaves the estate with *no* way
  to express a new type at all, which is the opposite of what the psyche asked
  for, and it breaks protos's `dependency-ethos` flake check the day it lands
  (witnessed: `protos.ethos:17` is inside that check's input).
- **Add an arity-1 collapse to the struct derive and leave the declaration
  legal.** Rejected: it fixes the wire form and leaves the modelling problem.
  `Meters.{ Integer }` would still generate a struct with a field named
  `integer`, which is the shape the psyche called absurd.
- **A marker syntax for the generative form** (ASN.1's tag, a sigil on the
  separator). Rejected as inventing syntax the psyche did not ask for — but it
  is the honest fallback if the all-at-once change proves too large, and it is
  the only option the literature actively recommends, so it should be put to the
  living alongside the recommendation.
- **`Deref` on the generated newtype** to soften the ergonomic cost. Rejected:
  `Deref` for inheritance re-leaks the abstraction the newtype just bought, and
  it is the standard warning against the pattern. Generate `From`/`Into` if
  ergonomics bite; never `Deref`.

### Vision lines affected

- `Vision/ethos.md:255-256` — *"An alias bears them through the type it names:
  an alias is not a new type and cannot carry a derive."* **Superseded** by
  (a). Replacement: *"`X.T` declares a new type wrapping T. It is generative:
  it has its own identity, bears the kinds through its own derive, and cannot
  be substituted for T."*
- `Vision/ethos.md:260-261` — the two `pub type` examples in the snippet, which
  become `pub struct`.
- `Vision/ethos.md:211` — the comment *"types: FilePath is an alias of String"*.
- `Vision/ethos.md:289` — *"Head then symbol is … an alias in the types
  section"* — reword to "a new type in the types section".
- A new line is owed under `Vision/ethos.md`'s non-repetition law recording the
  refusal of `X.{ T }` and pointing at `X.T`.
- `Vision/datom.md:132` — *"a single-field variant carries its type's own form"*
  — **unaffected and now consistent**: with `X.T` generative, a single-field
  *variant* still collapses and a single-position *struct* no longer exists.

### Implementation plan

Ordered; each step is a release.

1. **ethos-zero (major).** `src/conception.rs:390-398` keeps its three arms.
   `src/generation.rs:670-679` (`TypeDeclaration::Alias`) changes from
   `quote! { pub type #name #parameters = #aliased; }` to a tuple-struct emit
   carrying the same derive stack `src/generation.rs:572-589` gives structs.
   Add the arity-1 refusal to `src/checking.rs` with a new `Problem` variant.
   Update the nine arity-1 fixtures under `fixtures/`; the checked-in
   `tests/generated/*.rs` files are the gate and every one of them changes.
2. **protos (major).** `protos.ethos:17` → `ReaderBudget.Integer`;
   `Symbol.String` already becomes a newtype and matches the hand-written
   `pub struct Symbol(pub String);` at `src/core.rs:27`, which can then be
   deleted in favour of the generated one. Regenerate `generated-contract/`.
3. **datom-codec (major).** Delete the hand-written

## 3. Socket binding: built-in default, or the persisted store? (open-items A17)

### What is actually implemented

**Witnessed**, orchestrate 0.33.1 (`7b965a0`, clean main). The whole startup is
`crates/orchestrate-nexus/src/main.rs:8-27`:

```rust
    match DefaultConfiguration::from_process()
        .and_then(|defaults| {
            let (store, configuration) =
                OrchestrateStore::open(defaults.store_path(), defaults.configuration())?;
            …
            let transport = TransportRuntime::bind(configuration, store)?;
```

The built-in default goes **in**; what the store hands **back** is what binds.
The choice is `crates/orchestrate-nexus/src/store/mod.rs:71-89`:

```rust
        let state = match engine.match_records(QueryPlan::all(metadata))?.records() {
            [] => engine.seed_metadata(metadata, &defaults)?,
            [stored] => stored.state.clone(),
            rows => return Err(StoreError::MetadataInvariant { count: rows.len() }),
        };
        …
        let configuration = state.desired_configuration().clone().into_public();
```

The built-in default is consulted **only** for a fresh metadata tree. The
defaults themselves are XDG-derived (`src/defaults.rs:73-105`): `XDG_STATE_HOME`
falling back to `$HOME/.local/state`, and `XDG_RUNTIME_DIR` **mandatory with no
fallback**. No XDG crate; hand-read env vars.

The hazard is `crates/orchestrate-nexus/src/transport/socket.rs:67-81`:

```rust
        match StandardUnixStream::connect(self) {
            Ok(_) => Err(TransportError::SocketAlreadyActive(self.to_path_buf())),
            Err(error) if error.kind() == ErrorKind::NotFound => Ok(()),
            Err(error) if error.kind() == ErrorKind::ConnectionRefused => {
                fs::remove_file(self)?;
                Ok(())
            }
```

A **live** socket refuses; a **stale** one is deleted and taken. So a copy of a
production store, opened while the real Nexus is down, takes the production
socket paths. That is the witnessed hazard in `orchestrate-followup.md` §6.1.

### What Vision actually says, read in its own section

**Witnessed**, `Vision/nexus.md:83-92`, the section headed **First
configuration** — the last sentence of which is the line the open-items entry
quotes:

> A Nexus keeps a standard metadata tree. In it a type records whether the meta
> Configure was ever done … The tree holds everything standard about the Nexus:
> its socket paths — its own and those of every edge-socket it connects to — and
> whatever else comes up as standard nexus configuration data. The built-in
> default configuration is independent of this and is what gives the socket path
> on which the Configure signal arrives.

And the raw record it distils, **witnessed**,
`flows/acbb6006/vision/archive-nexus.md:61`, the psyche typed:

> this is independant of the builtin default configuration, which are needed
> since otherwise we wouldnt have a socket path to even fall back on to even
> allow the configure signal to come in.

**The open-items entry reads this line out of its section.** The psyche's
sentence is a *justification for having built-in defaults at all* — without them
there is no socket on which the very first Configure could arrive — not a
precedence rule saying the default beats the store forever. And the same record
puts socket paths **in** the metadata tree and makes meta-Configure the way they
change. If the built-in default won for binding, Configure of a socket path
would be a write that never takes effect, and the metadata tree's socket-path
field would be decoration.

So: **Vision does not say what A17 says it says, and the implementation is
faithful to the psyche's record.** That finding alone closes half the item.

Independent corroboration, **witnessed**: the `nexus` crate's own
`ARCHITECTURE.md:13-18` already states the rule the implementation follows —
*"`desired_configuration` is the persisted configuration. The active process
uses the snapshot loaded at startup; settings that determine bound resources
take effect on restart. The stable Sema discovery path is an executable-owned
default and is never part of mutable configuration."*

### Researched — and this is where the literature pushes back hard

The external evidence is nearly unanimous the other way, and it must be reported
honestly rather than smoothed over.

- **No mainstream daemon takes its listen address from its own data store on the
  next start.** sshd: `ListenAddress`/`Port` in `sshd_config(5)`, nothing in
  `/etc/ssh`'s key material. etcd: `--listen-client-urls`/`--listen-peer-urls`
  as flags or `/etc/default/etcd`, never `--data-dir` content
  (https://etcd.io/docs/v3.4/op-guide/configuration/). Docker: `-H` in
  `/etc/docker/daemon.json` or the unit; `/var/lib/docker` never decides.
  systemd: `ListenStream=` in the `.socket` unit, and PID 1's
  `/run/systemd/private` is a compile-time constant.
- **PostgreSQL is the sharpest case, and it cuts both ways.**
  `postgresql.conf` lives *inside* PGDATA by default and *does* supply
  `listen_addresses` and `unix_socket_directories` — so "the listen address
  lives in the data directory" has real precedent. But Postgres also writes
  `postmaster.pid` into PGDATA carrying the port (line 4), socket directory
  (line 5) and first listen address (line 6)
  (https://www.crunchydata.com/blog/postgres-postmaster-file-explained) — and
  treats that file as **state, deleted on clean shutdown, never read as
  configuration on the next start**. It is read only to detect an already-running
  server and to let clients *find* one. The docs explicitly contemplate it being
  stale and wrong.
- **The general name for our hazard.** It is environment capture in a portable
  artifact — Kubernetes' `spec` vs `status` (observed values never feed back as
  inputs), Terraform's "state file is per-deployment, not configuration", XDG's
  own three-way split where a socket path is `$XDG_RUNTIME_DIR` material and
  therefore by definition neither portable nor durable
  (https://specifications.freedesktop.org/basedir-spec/latest/).
- **The vocabulary that resolves it is etcd's**: `listen-*` is local and
  ambient; `advertise-*` is published into shared state for others. The folk
  statement of the constraint is "the address of the thing cannot be stored
  inside the thing" — you must already be able to reach it to read it.

### The decision

**The store wins for binding, and Vision is right — but the design is missing
two things the literature says are not optional, and their absence is the real
defect A17 found.**

Why the store wins, despite the survey: every daemon in that survey has ambient
configuration — a unit file, a flag, an env var. **A Nexus deliberately has
none**: `Vision/nexus.md:78` — *"A Nexus starts with no arguments and there is
no bootstrap binary."* Given that premise, the store *is* the Nexus's
configuration file, and it is the `postgresql.conf`-in-PGDATA case, not the
`postmaster.pid` case. Taking the listen address out of the store would leave
`Configure`'s socket-path field unimplementable and would require re-introducing
the arguments Vision forbids. The right answer is not to move the address out;
it is to add what Postgres has and we lack.

**Owed change 1 — the listen/advertise split, or rather its absence.** Today
the store holds one socket-path field doing two jobs: *where I intend to listen*
(spec, meta-configurable) and, implicitly, *where I am listening* (status). Add
the status half. At bind time the Nexus writes into the metadata tree an
observed record: the **absolute path of the store file it actually opened**, the
socket paths it actually bound, its PID and the boot id. This record is
system-authored, never an input to binding, and is what a client or a human
reads to find the running Nexus.

**Owed change 2 — the copy guard, which is what actually kills the hazard.** On
start, compare the observed record's store path against the path this process
just opened. If they differ, the store is a copy that has been moved, and the
Nexus **refuses to bind the persisted socket paths**. Two reasonable responses,
and the living should pick: refuse to start with a typed error naming both
paths; or bind the built-in defaults instead and record that it did. Refusing to
start is the safer default and is what Postgres does with a conflicting lock
file. Either way the witnessed failure mode in `orchestrate-followup.md` §6.1
— *"a copy of a real store opened by 0.32.0 tried to bind the live socket
path"* — becomes impossible rather than being caught by luck.

**Owed change 3 — stop stealing a stale socket.** `prepare_socket`'s
`ConnectionRefused → remove_file` branch is the other half of the hazard: a
stray instance started while the service is down takes the production paths and
nothing notices. The Unix answer is an advisory `flock` on a lock file beside
the socket, acquired before the socket is touched and held for the process's
life. A second instance then fails to acquire and exits with a typed refusal,
regardless of whether the socket inode is stale. This is strictly more correct
than the connect-probe, which has an unclosable race between the probe and the
`bind`.

### Alternatives rejected

- **Built-in default always wins; the store never supplies a socket path.**
  Rejected: it makes `Configure`'s socket-path field dead, contradicts the
  psyche's own record putting socket paths in the metadata tree, and would
  require ambient configuration the Nexus is forbidden to have.
- **Built-in default wins unless the store was meta-configured.** Rejected as a
  third rule nobody can hold in mind, and it still does not stop a copy of a
  *meta-configured* store — which is the one in the witnessed incident.
- **Environment variable override** (`ORCHESTRATE_SOCKET=…`). Rejected: it is
  the argument Vision forbids, wearing a different hat.
- **Detect the copy by file inode or a store UUID rather than by path.**
  Considered and *preferred where available*: a UUID minted at store creation
  and compared against a UUID in the observed record detects a copy even when
  the copy sits at the same path on a different machine, which the path
  comparison misses. Recommend the UUID; the path comparison is the cheap
  version if sema-engine makes a creation-time UUID awkward.

### Vision lines affected

- `Vision/nexus.md:91-92` — *"The built-in default configuration is independent
  of this and is what gives the socket path on which the Configure signal
  arrives."* **Not superseded — clarified.** Proposed rewording that keeps the
  psyche's meaning and removes the misreading: *"The built-in default
  configuration is independent of the tree. It is what a fresh store is seeded
  from, and so what gives the socket path on which the first Configure signal
  arrives. Once the tree holds socket paths, those are what the Nexus binds."*
- A new statement is owed under `Vision/nexus.md`'s **Configuration** section
  for the observed record and the copy guard. Proposed: *"A Nexus records where
  it is actually bound and which store file it actually opened. That record is
  written, never read as configuration. A store opened somewhere other than
  where its record says it lives is a copy, and a Nexus refuses to bind a
  copy's sockets."* This is a genuinely new rule; it is not in any psyche record
  this thread read, and it is this flow's proposal.

### Implementation plan

Repository `orchestrate` first, then `nexus`, then every other Nexus.

1. **`nexus` crate**, minor then major. Add an `ObservedBinding` type beside
   `ConfigurationState` and a kind — say `Situated` — with the capabilities to
   write it at bind and to compare it at open. This is universal Nexus
   behaviour and belongs there, not in orchestrate; see item 8.
2. **`orchestrate`**, major.
   - `crates/orchestrate-nexus/src/store/mod.rs` — a second metadata row (or a
     second field on `StoredMetadata`) carrying the observed record; a store
     UUID asserted at seed time.
   - `crates/orchestrate-nexus/src/main.rs` — after `open`, compare; on
     mismatch return a new `StoreError::CarriedStore { recorded, opened }`.
   - `crates/orchestrate-nexus/src/transport/socket.rs:67-81` — replace the
     connect-probe with `flock` on `<socket>.lock`; keep the probe only as the
     error message's evidence.
   - `crates/orchestrate-nexus/src/transport/mod.rs:42-59` — write the observed
     record after both binds succeed.
3. **Tests**, each seen failing first: a store copied to a second path refuses
   to start and names both paths; a stale socket file with a live lock holder is
   refused; a stale socket with no lock holder is taken; the existing
   `configuration_authority.rs:109-140` assertion that *"a store resumes its own
   configuration, not the executable's defaults"* must keep passing unchanged —
   it is the assertion this decision preserves.
4. **Wire impact**: none on the ordinary contract. The meta contract gains a
   query for the observed record (`ObserveBinding` → `BindingObserved`) so the

   `meta-signal-orchestrate`. The `StoredMetadata` sema record changes shape,
   which every existing store must cross — and the cutover path for that already
   exists (`store/mod.rs:118-157`).

## 4. `WatchDeployments`: build the subscription, or delete the contract? (open-items A43)

### What is there

**Witnessed** by the read-only subflow, lojix 4.0.1 (`0bb3d66`) and
signal-lojix 4.1.1. The contract declares five subscription-shaped things
(`signal-lojix/ethos/signal.ethos`):

```
  DeploymentWatch.{ Option<DeploymentIdentifier> Option<ClusterName> Option<NodeName> }
  CacheRetentionWatch.{ Option<ClusterName> Option<NodeName> }
  SubscriptionToken.Integer
  SubscriptionOpened.{ SubscriptionToken CommitSequence }
  SubscriptionClose.{ SubscriptionToken }
  SubscriptionClosed.{ SubscriptionToken }
  RejectedWatch.{ WatchRejectionReason }
  WatchRejectionReason.[ MalformedWatch SubscriptionLimitReached StreamUnavailable ]
  RejectedUnwatch.{ UnwatchRejectionReason SubscriptionToken }
  UnwatchRejectionReason.[ SubscriptionTokenUnknown SubscriptionAlreadyClosed ]
```

**There is no event or observation reply variant at all.** The reply block has
`Watching`, `Unwatched`, `WatchRejected`, `UnwatchRejected` — the handshake —
and nothing that could ever carry a change. The vocabulary was never finished,
let alone implemented.

The implementation, in full, `lojix/src/schema_runtime.rs:2591-2608`:

```rust
    fn open_subscription(&mut self) -> nexus::NexusAction {
        let subscription_token = self.store.next_subscription_token();
        let reply = match self.store.commit_sequence() {
            Ok(commit_sequence) => ordinary::Output::Watching(ordinary::SubscriptionOpened { … }),
            Err(_) => ordinary::Output::WatchRejected(…StreamUnavailable),
        };
        nexus::NexusAction::ReplyToSignal(…)
    }

    fn close_subscription(&mut self, close: ordinary::SubscriptionClose) -> nexus::NexusAction {
        let reply = ordinary::Output::Unwatched(ordinary::SubscriptionClosed::new(close.into_payload()));
        nexus::NexusAction::ReplyToSignal(…)
    }
```

The filter payload is bound to `_` and discarded. Nothing is registered. Five of
the six declared refusal reasons are never constructed. `close_subscription`
echoes back any token, including one never issued.

**Witnessed**: `broadcast`, `mpsc`, `watch::`, `Sender`, `subscriber` return
**zero hits** in lojix's source. Six type names that `ARCHITECTURE.md` promises
— `DeploymentObservation`, `CacheRetentionObservation`, `SubscriptionSink`,
`StreamingFrameBody`, `SubscriptionEvent`, `StreamEventIdentifier` — exist in no
Rust file in the workspace. `ARCHITECTURE.md:291-293` states as an invariant:
*"Push, never poll. Subscribers register; the daemon pushes DeploymentObservation
and CacheRetentionObservation events as they occur."* That is false.

The CLI, `lojix/src/client.rs`, writes one frame and reads exactly one:

```rust
    pub fn exchange(&self, request: Vec<u8>) -> Result<Vec<u8>> {
        let mut stream = UnixStream::connect(&self.socket_path)?;
        stream.write_frame(&FrameBody::from(request), self.capacity)?;
        Ok(stream.read_frame(self.capacity)?.bytes().to_vec())
    }
```

No loop. A `WatchDeployments` invocation prints the token handshake and exits,
dropping the stream.

**A correction to the open-items entry, witnessed.** A43 calls
`deployment-outbox` and `pending-transition-intent` *"two orphaned tables"* that
*"exist to serve this and have no consumer either way."* They are **not
orphaned.** Intents are asserted from four real deploy-transition entry points
(`lojix/src/lib.rs:1968, 2096, 2191, 2437`), all reached from production
(`daemon.rs:706,728,867,1058,1070`), and drained by a four-step ladder
(`lib.rs:1674-1681`: bind → dispatch → journal → acknowledge). What they do is
**local**: `append_transition_intent_journal` appends to the `event-log` table,
and `reconcile_pending_transition_intents` runs at store open to recover
interrupted transitions. They are a durable write-ahead log for deploy
transitions, which is real and load-bearing. They are *also* the natural source
for a real subscription — but they are not dead code, and deleting them along
with the watch vocabulary would delete crash recovery. **That part of A43 is
wrong and should not be acted on.**

### Researched

- **What a real watch requires.** etcd's Watch (https://etcd.io/docs/v3.5/learning/api/)
  is revision-based: `start_revision`, `progress_notify`, and — the important
  part — an explicit `compact_revision` cancellation when the client asks for
  history that no longer exists. Kubernetes is list-then-watch with
  `resourceVersion`, `BOOKMARK` events to advance a cursor without data, and
  `410 Gone` meaning "clear your cache, re-list, restart"
  (https://kubernetes.io/docs/reference/using-api/api-concepts/).
- **The invariant that decides this item.** *A design that forbids polling needs
  a monotonic cursor to be correct.* Without one, a reconnecting subscriber
  cannot distinguish "nothing changed" from "I missed everything", and its only
  recovery is to poll. Postgres LISTEN/NOTIFY is the counterexample that proves
  it: no history, no acknowledgement, and every production user works around it
  by re-reading state after subscribing. D-Bus signals are the same shape and
  every correct D-Bus client does a separate `Get` and treats the signal as an
  invalidation hint.
- **Slow consumers need a declared policy** — backpressure (one slow subscriber
  stalls all writes), collapse-to-"something changed" (safe only for
  level-triggered clients), or disconnect with a typed reason. etcd and
  Kubernetes both chose disconnect.
- **The cost of an unimplemented verb.** Fowler's *speculative generality*
  (https://refactoring.guru/smells/speculative-generality) — diagnosed when the
  only users are test cases, remedy is removal. The wire-specific aggravation:
  a stub that **returns success and does nothing** is strictly worse than an
  absent verb, because a client cannot tell "subscribed, nothing has changed
  yet" from "silently dropped" and will wait forever. gRPC's established answer
  for a verb that exists but is not built is `UNIMPLEMENTED`, never a success
  reply.

### The decision

**Delete the whole subscription vocabulary from `signal-lojix`, and keep the two
tables.** Three reasons, in descending force:

1. **The living never asked for it** (`lojix-history.md` §2.3, relayed). A
   feature nobody requested, whose only exercise is a unit test round-tripping
   `Query::Unwatch`, is the textbook case Fowler's smell names.
2. **The declared vocabulary cannot express a correct subscription anyway.**
   There is no event reply variant and no revision in the *watch* path. A
   correct design needs the cursor plumbed through the watch request and reply;
   what is declared is a token handshake and nothing else. Implementing against
   this vocabulary would mean redesigning it, so "implement it" and "delete it"
   both start by deleting it.
3. **The spirit skill settles the compatibility question**: *"Backward
   compatibility is never a design variable."* And the living this week:
   *"Less code is usually a good way to do it"*
   (`flows/f6db8d/vision/workPractice.md`). Deleting ten types, two verbs, four
   replies and thirty lines of stub is less code; implementing is several
   hundred more.

**But** `Vision/nexus.md:117-125` is distilled Vision and says *"State is
observed by subscription … Polling is forbidden."* Deleting lojix's watch
vocabulary does not violate it — lojix has no subscriber today and gains none by
keeping a stub — but it does leave lojix unable to satisfy it later without
building the thing properly. So the decision has a second half:

**When a real subscription is built — in lojix or anywhere — build it from the
commit sequence, not from a token.** The pieces already exist and orchestrate has
already proved the shape. `lojix/src/lib.rs:2282` issues a token from an
in-memory `AtomicU64`, which carries no ordering relative to the store. The
store's `commit_sequence()` is the monotonic cursor the design needs, and
`SubscriptionOpened` already carries it — the one part of this vocabulary that
was designed right. The minimum correct contract is:

```
  WatchDeployments.{ Option<CommitSequence> DeploymentWatch }   ; resume point, then filter
  DeploymentObserved.{ CommitSequence DeploymentObservation }   ; the event, carrying its cursor
  WatchLagged.{ CommitSequence }                                 ; earliest still available
```

and a bounded per-subscriber queue that, on overflow, sends `WatchLagged` and
makes the subscriber re-read — etcd's `compact_revision` and Kubernetes' `410
Gone`, shrunk to one process.

Orchestrate already implements exactly this shape without the cursor, and it is
worth naming as the reference: `orchestrate-nexus/src/core.rs:32-139` uses a
`tokio::sync::broadcast` with `ANNOUNCEMENT_BACKLOG = 64` and, on
`RecvError::Lagged`, **re-sends the whole observation** instead of a delta —
witnessed, and a defensible simplification for a small state. Its own comment
says why: *"a subscriber that joins mid-stream and one that has followed from
the start then hold the same value."* For lojix, whose state is an event log
rather than a lock table, whole-state resend is not available and the cursor is
mandatory.

### Alternatives rejected

- **Implement against the vocabulary as declared.** Rejected: there is no event
  reply to implement, so this is not an option that exists.
- **Keep the verbs and return a typed `Unimplemented`.** This is gRPC's
  recommended middle path and it was the closest call here. Rejected because the
  Nexus contracts are closed enums with no catch-all (`nexus` skill: *"No
  catch-all variants — the vocabulary is closed"*), so an `Unimplemented` reply
  would itself be a new permanent variant in the vocabulary — carrying the exact
  liability we are trying to shed.
- **Delete the tables as well.** Rejected on witnessed evidence: they are
  written from four production paths and drained at store open for crash
  recovery. A43's claim that they have no consumer is incorrect.

### Vision lines affected

None superseded. `Vision/nexus.md:117-125` stands; this decision is about where
it is not yet realized, not about whether it is right. What is affected is a
**document**: `lojix/ARCHITECTURE.md:68-70, 112-115, 121-123, 259-260, 279-285,
291-293` makes six false claims about streaming and names six types that do not
exist. Those paragraphs go with the vocabulary.

### Implementation plan

1. **`signal-lojix`**, major (5.0.0 → 6.0.0 from its current 4.1.1 line; a
   sibling flow released 5.0.0 tonight, so confirm the head first).
   `ethos/signal.ethos` — delete `WatchDeployments` and `WatchCacheRetention`
   from the request block; delete `Watching`, `Unwatched`, `WatchRejected`,
   `UnwatchRejected` from the reply block; delete `Unwatch`; delete the ten
   types listed above. Regenerate; the checked-in projection is the gate.
2. **`lojix`**, major. Delete `open_subscription`/`close_subscription`
   (`src/schema_runtime.rs:2583-2608`), the `subscription_sequence` field and
   `next_subscription_token` (`src/lib.rs:582-585, 2282-2286`), and the
   lowering arms (`src/adapters.rs:764-778`). **Keep** `DEPLOYMENT_OUTBOX_TABLE`,
   `PENDING_TRANSITION_INTENT_TABLE`, their row types and the four-step ladder.
3. **`lojix/ARCHITECTURE.md`** — delete the six streaming paragraphs. Add one
   sentence saying observation is not yet built and naming the cursor design
   above as the shape it will take, so the next flow does not re-invent a token.
4. **Curriculum** — the `lojix` skill documents no watch verb, so nothing is
   owed there; confirm with a grep before the release.
5. **Tests**: the round-trip test at `clients/ordinary/src/lib.rs:76-77` goes
   with the verb. Nothing else references it. The gate is that every existing
   check stays green with the vocabulary gone — which is the witness A43 itself
   asked for.

Wire impact: **breaking**, on a verb no deployed client has ever successfully
used. Every `signal-lojix` consumer repins.

### Researched

The governing principle here is not from an external survey but from our own
`Intent/context.md`, which is the higher authority and which settles it:

> A value at any layer carries the context it makes sense in, and no layer
> carries a fact that belongs to another.

`horizon-rs`'s commit message — *"enum-shadow structs"* — is that Intent applied.
A boolean named `modelIsThinkpad` in a node projection is not a fact about the
node; it is a CriomOS policy question ("does this machine get ThinkPad battery
thresholds?") that has been pushed up into the node's own description. The
projection's job is to say what the machine *is* (`model: "ThinkPadT14Gen5Intel"`);
deciding what that *means for systemd* is the consumer's job. The deletion was
right.

The supporting external argument is the one from item 2's research, applied at
the Nix layer: an open string that a consumer matches with no closed set behind
it is primitive obsession, and its failure mode is exactly what A31 warns about
— a typo or a new model yields `false` for every branch, silently. The remedy is
not to move the classification back upstream; it is to **close the set where the
policy lives**.

### The decision

**Split the eleven fields three ways. None of A31's three options is right taken
whole; each is right for one third.**

**(a) Lid switch — relocate to CriomOS, no Horizon change.**
`handleLidSwitch{,ExternalPower,Docked}` are a systemd policy derived from
`behavesAs.center`, `behavesAs.lowPower` and `behavesAs.edge`, all live today.
Compute them in `modules/nixos/metal/default.nix` from the current contract, in
one `let` binding reproducing the deleted derivation verbatim. This is A31's
third option ("relocate the behaviours elsewhere") and it is unambiguously
correct: the values are systemd `logind.conf` strings, they were never hardware
facts, and CriomOS is where systemd lives.

**(b) Species flags — already relocated; finish the job.** `typeIs.*` is
`behavesAs.*` under an older name for most uses. CriomOS's one live use is
`typeIs.center` at line 608, already commented out. CriomOS-home's two uses of
`typeIs.largeAiRouter` (`min/pi-models.nix:37`, `max/browser-use.nix:56`) need
a real answer: today's `BehavesAs` has `router` and `large_ai` but not the
conjunction. Either read `node.behavesAs.router && node.behavesAs.largeAi`, or —
better — read `NodeSpecies` directly, since `LargeAiRouter` is a species and the
conjunction is an inference about it. **Delete the `or false`** in both files:
that default is the silent-degradation hazard A31 names, and it is live today.

**(c) Model classification — match the raw string in CriomOS, against a closed
table, with an assertion.** This is A31's second option, chosen deliberately over
its first. Reasons: `horizon-rs` made a design judgement against per-model
booleans and it is the right judgement by `Intent/context.md`; CriomOS already
matches the raw string in a dozen places, so this direction reduces the number of
mechanisms rather than adding one; and the classification is policy, which
belongs to the consumer.

The correctness that the closed enum used to provide is not lost — it moves. In
`modules/nixos/metal/default.nix`, one `modelFacts` attrset keyed by model name,
holding `isThinkpad`, `chipIsIntel`, `isRpi3b` and whatever else the twelve
broken lines need, plus an explicit `generic` entry for `"all-x86-64"`. Then
**an assertion that `model` is a key of that attrset.** An unknown model becomes
a build-time error naming the model and the file to add it to — which is
strictly better than `KnownModel` gave us, because `KnownModel::known()` returned
`Option` and the projection silently emitted all-false for an unrecognised
string. The thing A31 fears — *"inventing a default here would silently disable
every real ThinkPad's battery/thermal/lid handling"* — is prevented by the
assertion, not by the enum.

**(d) The fixtures.** All five check fixtures are rewritten to the *real*
projected shape, and the mutual inconsistency found above is the reason this
cannot wait. The better structural answer — CriomOS taking horizon-rs as a flake
input and projecting at check time rather than checking in a fixture — is A33,
a separate item; it would make this class of drift impossible and it is the right
end shape. Until it lands, at minimum the five fixtures must agree with each
other and with `HardwareView`.

### Alternatives rejected

- **Reintroduce typed hardware classification in Horizon** (A31 option 1).
  Rejected: it reverses a considered design judgement, it puts consumer policy
  in the producer's contract against `Intent/context.md`, and it means every new
  ThinkPad model needs a horizon-rs release and an estate-wide repin before
  CriomOS can branch on it. The per-model boolean struct is also a wire-surface
  smell the `nexus` skill names independently: *"Storage classification
  vocabulary never appears on the public wire."*
- **A `hardwareClass` enum in Horizon** — a middle path where Horizon emits
  `Laptop | Desktop | SingleBoard` rather than per-model booleans. Genuinely
  attractive, and worth putting to the living as a fourth option. Rejected as
  the recommendation only because nothing in the twelve broken lines needs it:
  every one of them is either model-specific (thermal, microcode, battery) or
  species-derived (lid switch). A class enum would serve neither.
- **`modelIsThinkpad = model != null && lib.hasPrefix "ThinkPad" model`.**
  Rejected: prefix-matching an operator-supplied string is the silent-failure
  mode with extra steps, and it gets `"ThinkPadX250"` (present in
  `modelKernelModulesIndex`) right by luck and `"GMKtec EVO-X2"` wrong by
  design.
- **Leave the fixtures alone and fix only the module.** Rejected: the fixtures
  are already false-green on live fields, witnessed. They would hide the next
  divergence as they hid this one.

### Vision lines affected

None. Neither `Vision/` nor `Intent/` names hardware classification, and this
thread's search of `flows/*/vision/` and `vision-raw/` found no psyche record on

## 6. The Kameo actor boundary for a Nexus core (open-items A18; `orchestrate-work.md` §6.3)

### What is there

**Witnessed**, orchestrate 0.33.1. There is no `kameo` dependency; the marker
comment at `crates/orchestrate-nexus/src/core.rs:12-15` says why:

```rust
//! Serialization is `Arc<Mutex<_>>`, which Vision permits while the Kameo
//! standards are undesigned. The boundary is drawn so that becoming an actor
//! is a change of this file only: nothing outside it touches the store.
```

The shape today: one `tokio::select!` accept loop over two `UnixListener`s
spawning per-connection tasks into a `JoinSet`
(`transport/mod.rs:84-128`); one `Session` type per connection doing framing
through `signal`'s codec only (`transport/session.rs:57-79`); `NexusCore` holding
`Mutex<OrchestrateStore>` and a `broadcast::Sender<Observation>`
(`core.rs:34-38`); dispatch by two trait impls, `Applies<OrdinaryQuery>` and
`Applies<MetaQuery>`, on the same `NexusCore` — no dispatch enum.

**Witnessed**, the Kameo fork. `/git/github.com/LiGoldragon/kameo` is at
**0.20.0**, detached at `3486e4f`, with a merge-base against `upstream/main` at
`4d2e2d0` and **exactly five authored commits** by `li` (2026-05-16 / 06-19),
all on one theme: actor lifecycle terminal outcomes and a split lifecycle-control
mailbox (`src/mailbox.rs` near-rewritten, `tests/lifecycle_phases.rs` +997).
A19 records that *"what the fork changes relative to upstream was never
established"* — it is established now, and it is small and coherent.
Crates.io is at **0.22.2**. `lojix/Cargo.toml:63-70` already patches the fork
out to crates.io with the note that `triad-runtime` *"uses only upstream 0.20
API"*.

**Witnessed**, `#[messages]` is used **nowhere in the estate** — zero
occurrences of `#[message` in any repository. Every consumer hand-writes
`impl Message<T> for A`. So the fork's macro crate is essentially unexercised.

**Witnessed**, the existing ontology attempt. `triad-runtime/src/role.rs` is a
file of seven **empty marker traits** (`pub trait NexusWork {}`,
`pub trait SemaWriteInput {}`, …) — precisely what the psyche complained of
(`flows/fd301d9a/vision/archive-nexusTraits.md`, 2026-08-19, dictated):

> the first implementation just simply created placeholder traits for every
> function, and just sort of mindlessly created traits that don't create a
> sensible ontology.

Beside it, `triad-runtime/src/reaction.rs` holds something much better and
largely unnoticed:

```rust
pub enum Work<Event, Write, Read, Effect> {
    SignalArrived(Event), SemaWriteCompleted(Write), SemaReadCompleted(Read), EffectCompleted(Effect),
}
pub enum Action<Reply, Write, Read, Effect, Continuation> {
    ReplyToSignal(Reply), CommandSemaWrite(Write), CommandSemaRead(Read),
    CommandEffect(Effect), Continue(Continuation),
}
```

That **is** a dataflow ontology — a typed continuation machine where a request
becomes a sequence of commanded reads, writes and effects. It predates the Nexus
vision, is written against NOTA, and sits under a pile of empty marker traits.
It is the single best piece of prior art in the estate for item 8, and it
belongs in the conversation here because what an actor *owns* is decided by what
the actor's step function is.

### Researched

- **Kameo 0.22.2** (https://docs.rs/kameo). `Actor` has `type Args`, `type
  Error`, and a **required `on_start(args, actor_ref) -> Result<Self, Error>`
  that constructs the actor** — so fallible startup (opening the store, binding
  the socket) has a natural home and a failure there is a startup error rather
  than a half-built actor. Provided hooks: `on_stop(reason)`, `on_panic ->
  ControlFlow<ActorStopReason>`, `on_link_died`, `on_undelivered`, and `next()`
  for selecting over the mailbox plus another stream. `ActorRef` gives `ask`,
  `tell`, `stop_gracefully()` (drains the mailbox) vs `kill()` (drops it),
  `link`/`unlink`, and `attach_stream`. Supervision is explicitly Erlang-shaped:
  `OneForOne` (default) / `OneForAll` / `RestForOne`, restart policies
  `Permanent`/`Transient`/`Never`, with restart limits per window. **Mailboxes
  default to bounded, capacity 64, explicitly for backpressure** — the single
  most consequential knob in front of a durable store. `pool` and `pubsub` moved
  out to the `kameo_actors` crate, so older references are stale. Remote actors
  ride libp2p and are dead weight for a Unix-socket daemon — keep the feature
  off.
- **What an actor owns, from OTP and Akka.** An actor owns exclusive mutable
  state and serializes access to it — that is the only thing it is for. One
  actor per **unit of consistency**; Akka's cluster-sharding docs name this the
  DDD Aggregate and call the entity a *consistency boundary*
  (https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html).
  The **error kernel** pattern (https://www.reactivedesignpatterns.com/patterns/error-kernel.html):
  an actor holding important state *"should source out any possibly dangerous
  sub-tasks to children it supervises"* — the state holder sits at the top and
  does nothing risky. And actors must not block: a synchronous fsync inside a
  handler blocks the whole mailbox, converting the state actor into a
  head-of-line-blocked queue.
- **Where real systems draw the line.** Erlang's ranch
  (https://ninenines.eu/docs/en/ranch/2.0/manual/ranch/) has a *pool* of
  acceptor processes that do nothing but accept and hand off, and a **separate**
  supervisor for connection processes, one per connection — so a crashing
  session cannot take down the listener. Alice Ryhl's *Actors with Tokio*
  (https://ryhl.io/blog/actors-with-tokio/) is the canonical Rust statement of
  the same split: a task owning the state and the `Receiver`, plus a cloneable
  handle owning only the `Sender`; spawn inside the handle's constructor;
  **always bounded**; RAII shutdown when the last handle drops; and *"beware of
  cycles"* — a cycle of bounded channels deadlocks.
- **Privileged vs ordinary.** systemd's `/run/systemd/private` is a second
  root-only socket speaking the same protocol to **the same PID 1 and the same
  state** — a transport-and-credential separation, not a state separation, and
  systemd explicitly declares that socket's protocol internal and unstable
  (https://systemd.io/PORTABILITY_AND_STABILITY/). etcd separates client (2379)
  and peer (2380) ports with separate TLS, both mutating one Raft state.
  PostgreSQL has one listener and carries authority in the session. Docker has
  one socket and no granularity, and is the cautionary example. **The weight of
  practice: the privileged socket reaches the same state actor, carrying an
  authority token minted at accept from the peer credentials.**
- **Is an actor warranted at all?** The honest literature answer is: not by
  having state. The Tokio tutorial is explicit that a `std::sync::Mutex` is
  right for simple data and a dedicated task for things needing async I/O
  (https://tokio.rs/tokio/tutorial/shared-state). A single actor with ask-only
  traffic is semantically a `Mutex` with a queue in front — a serialization
  bottleneck with worse ergonomics and an extra hop.

### The decision

**Adopt Kameo for the Nexus, and draw the boundary at the store, not at the
connection.** Four rules, which together are the "standards of their use" Vision
says are undesigned.

**Rule 1 — one state actor per Nexus, and it owns the store.** `NexusCore`
becomes the actor. It owns `OrchestrateStore` by value (no `Mutex`), and it is
the only thing in the process that touches it. This is the consistency boundary:
a lock table has one unit of consistency, so it gets one actor. Splitting the
domain across several actors is forbidden until there are genuinely independent
consistency units, because every split is a potential bounded-channel cycle.

**Rule 2 — sockets are not actors. Sessions are tasks.** The accept loop stays a
plain task per listener; each accepted connection stays a spawned task holding a
cloned `ActorRef<NexusCore>`. This is ranch's shape and Ryhl's, and it keeps the
listener alive when a session panics. A session holds no domain state, so making
it an actor would buy only supervision it does not need. The one thing that
changes is that the `JoinSet` of detached tasks becomes a supervised child set,
so a session that panics is recorded rather than printed to stderr
(`transport/mod.rs:105, 115` currently `eprintln!`).

**Rule 3 — authority is a token minted at accept, carried in the message, and
checked by types.** Both sockets reach the same actor; what differs is what each
session is allowed to construct. Today `Applies<OrdinaryQuery>` and
`Applies<MetaQuery>` already do this structurally — the meta contract's types
are unconstructable from an ordinary session because the session only ever
receives `OrdinaryQuery`. Keep exactly that and make it explicit: the message
type *is* the authority token. This is the systemd model with Rust's types doing
what `SO_PEERCRED` checks do in C, and it needs no new mechanism.

There is one live defect this rule exposes, **witnessed**:
`transport/session.rs:94-106` writes the peer refusal as a
`MetaResponse::PeerRefused` from a socket-agnostic trait. It is correct today
only because `SocketAuthority::Ordinary::admits` is unconditionally `true`, so
the ordinary path never reaches that line. A third socket would silently write a
meta-contract frame onto an ordinary socket. The refusal must be per-contract.

**Rule 4 — the mailbox is bounded and the store does not block it.** Keep
Kameo's bounded default. If sema-engine's commit path blocks, it goes behind
`spawn_blocking` or the actor becomes the throughput of the disk. And the
subscription fan-out must be non-blocking from the actor's perspective —
`try_send` and mark-lagged, never await a slow subscriber — or one slow watcher
stalls every write. That is the same bounded-cycle deadlock Ryhl warns about,
and item 4's cursor design is what makes mark-lagged recoverable.

**On the fork (A19), which this decision forces a view on.** Take crates.io
0.22.2 and drop the fork, unless the five lifecycle commits are needed. The
evidence says they are not needed *yet*: `#[messages]` is unused estate-wide,
lojix already patches the fork out with a note that `triad-runtime` uses only
upstream 0.20 API, and upstream 0.22 gained supervision strategies and restart
limits that the fork does not have. The fork's contribution — terminal lifecycle
outcomes, a split lifecycle-control mailbox — is exactly the kind of thing to
offer upstream rather than carry. This is a recommendation, not a ruling; A19 is
the living's call and it is marked never-unattended.

**On whether the actor is warranted at all.** Stated honestly: for
`orchestrate` *as it stands today* — one store, one lock table,
`Arc<Mutex<_>>` that Vision explicitly permits — Kameo buys little. What it buys
is `on_stop(reason)` (a guaranteed flush hook that runs on graceful stop *and*
on panic-induced stop), fallible construction in `on_start`, `stop_gracefully`
vs `kill` as the SIGTERM/SIGKILL distinction a daemon needs, restart limits, and
the `kameo console` TUI showing mailbox backpressure and restarts. Those are
daemon-lifecycle goods, not state-management goods. **So: the actor is warranted
for the daemon, not for the store.** Which is also why Vision's *"Arc-Mutex is
permitted"* is not a concession to be embarrassed about — it is correct for the
inside of one actor.

### Alternatives rejected

- **One actor per connection, domain state behind an `RwLock`.** Rejected: it
  loses the single-writer property that makes announcements coherent, and it
  puts the consistency boundary nowhere.
- **A separate actor for the meta path.** Rejected: two owners of one store is
  impossible, and a proxying meta actor is a message with extra steps plus a
  bounded-channel cycle. OTP keeps supervision (about failure) and authority
  (about permission) on different axes; so should we.
- **The privileged socket reaches a supervising actor.** Rejected for the same
  reason — a supervisor that also serves requests stops being an error kernel.
- **Hand-rolled `mpsc` + owned loop (Ryhl's pattern, no library).** Rejected,
  but it is the closest call and deserves to be named: it is ~30 lines, it is
  what orchestrate effectively has, and it gives RAII shutdown for free. It
  loses supervision, restart limits, `on_panic`, and the operational console.
  The psyche has already ruled that Kameo is the actor layer
  (`flows/fd301d9a/vision/actorLibrary.md`, 2026-08-22: *"we are definitely
  using kameo actors in nexus"*), so this alternative is closed by Vision, not
  by argument.
- **Separate mailboxes for the two sockets.** Considered and **recommended as a
  follow-on, not now**: one pathological ordinary client filling a 64-slot
  mailbox can lock out the admin path, which is the real argument behind etcd's
  separate ports. The fix is either a second higher-priority channel selected in
  `Actor::next`, or admission control in the session tasks. Not urgent while the
  ordinary socket is `0o660` on a single-user machine.

### Vision lines affected

- `Vision/nexus.md:110-112` — *"The engine inside a Nexus is driven by Kameo
  actors. The standards of their use are still to be designed. Arc-Mutex is
  permitted."* **Not superseded; completed.** The second sentence is what this
  item exists to discharge. Proposed replacement for it, four lines to sit
  under the same heading:

  > One actor owns the durable store and is the only thing that touches it.
  > Sockets are not actors: a listener is a task and a connection is a task
  > holding a reference to the one actor. Authority is the message type a
  > session can construct, minted from the peer at accept. The mailbox is
  > bounded and nothing that blocks runs inside it.

- `Vision/nexus.md` **Actors** section, the Arc-Mutex sentence — keep it,
  scoped: *"Arc-Mutex is permitted inside one actor."*

### Implementation plan

Repository `orchestrate` is the pilot, because it is the smallest Nexus and its
`core.rs` was already written to be the only file that changes.

1. `crates/orchestrate-nexus/Cargo.toml` — add `kameo = "0.22"` from crates.io.
2. `core.rs` — `NexusCore` becomes `impl Actor` with `Args = OrchestrateStore`,
   `on_start` taking the opened store, `on_stop` flushing. `Mutex` goes; the
   store is owned. `Applies<OrdinaryQuery>` / `Applies<MetaQuery>` become
   `Message<OrdinaryQuery>` / `Message<MetaQuery>`. The `broadcast::Sender`
   stays — it is the right primitive for fan-out and Kameo's pubsub is not
   needed for one topic.
3. `transport/mod.rs` — `TransportRuntime::bind` spawns the actor and holds an
   `ActorRef`; the `JoinSet` becomes a supervised child set; the two `eprintln!`
   become `on_link_died` records.
4. `transport/session.rs:94-106` — make the peer refusal per-contract, closing
   the D-9 defect above. This is a real bug fix and should be its own commit
   with its own failing-first test.
5. **Tests, each seen failing first**: a session that panics does not stop the
   listener; `stop_gracefully` drains a queued request before exiting; a
   refusal on the ordinary socket carries an *ordinary* contract frame.
6. **Then, and only then**, lift the pattern into `nexus` — see item 8. Do not
   generalise from one Nexus before it runs.

Wire impact: none.

## 7. Ethos-generated derives, and recursion under rkyv (`aggregator-migration.md`)

### What is there

**Witnessed**, ethos-zero 8.0.1, `src/generation.rs:572-589` — the complete
derive policy, and both arms are unconditional:

```rust
impl DatomDeriving for bool {
    fn datom_derives(&self) -> TokenStream {
        if *self {
            quote! {
                #[derive(rkyv::Archive, rkyv::Serialize, rkyv::Deserialize, Clone, Debug, PartialEq)]
                #[cfg_attr(feature = "datom", derive(datom_codec::Datomizable, datom_codec::Compositional))]
            }
        } else {
            quote! {
                #[derive(datom_codec::Datomizable, datom_codec::Compositional, Clone, Debug, PartialEq)]
            }
        }
    }
}
```

The `bool` is `matches!(scope.file, File::Signal(_))` — Signal files get rkyv,
Library files do not. `Clone, Debug, PartialEq` unconditional in both;
`Eq`, `Hash`, `Default`, `Copy` in neither. Aliases get nothing, because a
`pub type` cannot carry a derive. **Nothing is emitted for the *archived*
type at all** — no `#[rkyv(derive(...))]`, no `#[rkyv(compare(PartialEq))]` —
which is a gap neither the aggregator report nor open-items A10 notices.

**Relayed**, `aggregator-migration.md`: *"129 aggregator types lost `Copy` and
`Eq` as a consequence … no contract type derives `Eq`, `Hash` or `Default`, so
no contract value can be a map key."* And the meta contract's lost `Default`
impls were deliberately rebuilt as a `DefaultingPolicy` kind in the consumer:
*"the generated projection derives no `Default`, and a runtime ceiling is a
policy a runtime asks for, not a zero value."*

**Relayed and witnessed**, the recursion finding. A `Signal` root cannot express
a recursive type: the flow generated a minimal recursive Signal and got
`error[E0275]: overflow evaluating the requirement Vec<TextQuery>: Archive`, and
the same for `Box<TextQuery>` alone. A `Library` root's `fixtures/tree-types.ethos`
recurses fine because it derives only datom-codec. The consequence shipped:
`TranscriptBlockTextQuery` and `TranscriptBlockSearchEvidence` became **flat node
arenas** — a vector of nodes plus a root index — *"a real wire redesign, made
because the tree cannot cross this wire at all, not as a preference."*

**Witnessed by this thread**, the working recipe already exists in the estate.
`/git/github.com/LiGoldragon/dotos-text-query/src/query.rs:8-24`:

```rust
#[derive(rkyv::Archive, rkyv::Serialize, rkyv::Deserialize, Clone, Debug, PartialEq, Eq)]

    bytecheck(bounds(__C: rkyv::validation::ArchiveContext)),
    serialize_bounds(
        __S: rkyv::ser::Writer + rkyv::ser::Allocator,
        __S::Error: rkyv::rancor::Source,

    AllOf(#[rkyv(omit_bounds)] Vec<Query>),
    AnyOf(#[rkyv(omit_bounds)] Vec<Query>),
    Not(#[rkyv(omit_bounds)] Box<Query>),
    Near(NearQuery),
```

Hand-written, compiling, in production. Ethos Zero emits none of it.

### Researched

**On recursion.** The finding that matters most is not that recursion is hard —
it is that the *safe* way to read a recursive archive is not the default.

- **rkyv's derive uses "perfect derive"**: for every field of type `F` it emits
  `where F: Archive`. On a self-reaching type that bound is self-referential and
  the solver never terminates — the exact `E0275` the aggregator flow hit.
  `#[rkyv(omit_bounds)]` suppresses it, and because that also removes the
  legitimate bounds, three explicit bound attributes must be added back. rkyv
  ships the canonical worked example, and it is **exactly our Signal problem**:
  `rkyv/examples/json_like_schema.rs`, a recursive `JsonValue` enum with
  `serialize_bounds`, `deserialize_bounds`, `bytecheck(bounds(__C: ArchiveContext))`
  and `#[rkyv(omit_bounds)]` on each recursive field. `dotos-text-query`'s
  hand-written stack is that example, character for character. (rkyv 0.8.18
  docs and rkyv.org; the derive once produced a compiler ICE on a cyclic enum,
  rust-lang/rust#123238.)
- **The archived form of a recursive type is itself recursive**, via relative
  pointers. `ArchivedBox<T>` is a `#[repr(transparent)]` wrapper around a
  `RelPtr` — four bytes at the default 32-bit pointer width; `ArchivedVec<T>` is
  a `RelPtr` plus a length, with `T` being the *archived* element type. So
  `ArchivedSignal::Vector(ArchivedVec<ArchivedSignal>)` works and costs one
  offset dereference per level, with no allocation and no deserialize pass.
  (https://rkyv.org/format.html)
- **Cycles are structurally impossible**, which is better than expected. rkyv's
  validator uses a **subtree range** model: each child must lie in a range
  strictly smaller than its parent's, so a back-edge cannot validate. No cycle
  detection is needed. (https://rkyv.org/validation.html)
- **Depth is not guarded by default, and this is a real hazard.**
  `ArchiveValidator::with_max_depth(bytes, Option<NonZeroUsize>)` exists and
  `ExceededMaximumSubtreeDepth` is its error — but
  `ArchiveValidator::new(bytes)` passes `None`, and the high-level
  `rkyv::access::<T, E>(bytes)` builds its validator through that constructor.
  So **validating an untrusted archive of a recursive root runs with unlimited
  depth**, and a small buffer encoding a few thousand nested levels overflows
  the native stack — which in Rust is an abort, not a catchable error.
  (`rkyv/src/validation/archive/validator.rs`, `rkyv/src/api/high/checked.rs`.)
  Compare **Cap'n Proto, which ships the limit on by default**: nesting depth
  64 and a 64 MiB traversal limit, explicitly *"designed to prevent stack
  overflow when handling a deeply-nested recursive type"*
  (https://capnproto.org/encoding.html). CBOR and MessagePack implementations
  have shipped CVEs for exactly this omission.
- **Two cheap shape wins.** Recurse through `Vec<Self>` rather than
  `N × Box<Self>` — one offset and a contiguous slice instead of N offsets. And
  an enum's variant payloads are **inline**, so every element of every array is
  as large as the largest variant: keep payloads pointer-sized. FlexBuffers
  (https://flatbuffers.dev/flexbuffers/) is the closest existing analogue to a
  Signal root and encodes a map as **two parallel sorted vectors** (keys,
  values) rather than a vector of pairs, which gives binary search and keeps the
  key run contiguous — worth knowing, though `Vision/datom.md`'s Map section
  already rules that datom has no map.
- **Arrow is the negative data point worth recording**: its schema is a finite
  tree, so it **cannot express an unbounded recursive type at all**, and a
  recursive value in Arrow is encoded as a flat arena. Columnar zero-copy
  formats resolve recursion by flattening, not by self-reference — which is
  where the aggregator's forced redesign landed.

**On derives.**

- **`Eq` is not "unsound" for a float-bearing type; it is un-compilable.**
  `#[derive(Eq)]` on a struct containing an `f64` is a hard error, because
  `f64: PartialEq` but `f64: !Eq` (NaN breaks reflexivity). So an unconditional
  `Eq` derive fails the moment a schema author adds a `Decimal` — and
  `Vision/ethos.md:133` makes Decimal an intrinsic that
  `ethos-zero/src/generation.rs:58` lowers to `f64`.
- **Deriving `Hash` and `PartialEq` together is safe; splitting them is where
  bugs live.** The `a == b ⟹ hash(a) == hash(b)` contract holds for derived
  impls because both are structural. The cost worth naming for a recursive root:
  a derived `Hash` walks the whole tree on every hash, so a Signal used as a map
  key wants a cached or content-addressed hash, not a derived one.
- **`Default` on a generated wire type is the zero-value problem.** It
  manufactures a value satisfying the type but not the schema's invariants; it
  is the exact inverse of "parse, don't validate"
  (https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/); and
  every downstream `unwrap_or_default()` becomes a silent invariant violation.
  On an enum, `#[derive(Default)]` has required an explicit `#[default]` on a
  **unit** variant since Rust 1.62 (RFC 3107) — a constraint that is a feature
  here, because it forces the *author* to answer a question the generator
  cannot.
- **prost's `Default` is not a counterexample.** `prost-derive` generates
  `impl Default` because `Message::decode` requires `Self: Default` — protobuf's
  wire model is "start from defaults, merge fields". It is a protocol
  requirement, not a convenience. And prost derives **no** `Eq`, `Hash` or
  `Ord`; those are opt-in per type via `Config::type_attribute`
  (https://docs.rs/prost-build/latest/prost_build/struct.Config.html), which
  itself has a known blast-radius wart (tokio-rs/prost#586, paths match
  submessages).
- **The pattern across every generator surveyed** — prost, tonic, serde,
  capnpc, schemars, typeshare — is: *emit the minimum that is always correct,
  plus whatever the serialization model structurally requires, and expose an
  opt-in for the rest.* Nobody derives the maximum. `bindgen`, which tries to,
  has a long bug tail from it (rust-bindgen#1093).
- **The semver asymmetry decides the default.** Adding a std derive is
  non-breaking; removing one is a major break. Rust API Guidelines C-COMMON-TRAITS
  argues for eager implementation on the orphan-rule ground that downstream
  crates cannot add these themselves — a real argument — but it is cheap to add
  later and expensive to remove, which argues for the minimum now.

### The decision

**(a) `Eq` and `Hash`: the terminal answer is to fix `Decimal`, not to make the
derive conditional.** A7 already stands open: `Vision/ethos.md:133` makes
Decimal an intrinsic, `generation.rs:58` lowers it to `f64`, and the witnessed
symptom is that `{ NaN }` writes text no reader accepts. A **finite decimal**
type — no NaN, no infinities, no `-0.0` distinct from `0.0` — is `Eq`, `Hash`
**and** `Ord`, and it is the same fix A7 needs for a different reason. With it,
`Eq` and `Hash` become **unconditional**, alongside `Clone`, `Debug` and
`PartialEq`, and no conditional machinery is needed at all. That is the
design than which none better is possible here: one type change removes a wire
defect, a derive limitation and a canonicalization hazard together.

Until A7 lands, the interim, stated with its cost: derive `Eq`/`Hash`
**conditionally**, gated on a memoised, cycle-safe reachability fold answering
*"does this type reach a Decimal?"*. The cost is real and must not be glossed —
**adding one float field to one leaf type silently removes `Eq` from every type
that transitively contains it, which is a major semver break emitted by an
innocuous schema edit.** Mitigate it by having the generator *report* the derive
set it chose for each type, so the removal is visible in the diff of the
committed projection rather than only at a consumer's build. If the living finds
even that unacceptable, the alternative is an opt-in ethos annotation that the
generator *verifies* and **errors** on rather than silently downgrading — which
is prost's shape and is the literature's own preference. Recommend the interim
conditional, and recommend prioritising A7 so the interim is short.

`PartialEq`, `Clone` and `Debug` stay unconditional. `Copy` stays **unrestored**:
a `Copy` wire type is a size claim as well as a semantic one, and a contract
growing a `String` position would silently break every consumer relying on it.
The 129 aggregator types that lost `Copy` should stay lost.

**(b) `Default`: never derive it, and the aggregator already wrote the rule.**
*"A runtime ceiling is a policy a runtime asks for, not a zero value."* A wire
type's `Default` is a lie about what a peer sent. Where a default is wanted it
is a **kind** declared in ethos and implemented by the consumer — the
`DefaultingPolicy` shape the aggregator built — which puts the default where the
policy is and names the policy. This is a place where the code got ahead of the
generator and the generator should follow it.

**(c) Recursion: emit the bound attributes; do not forbid recursion.** Ethos
Zero already detects self-reaching types for `Library` roots
(`fixtures/tree-types.ethos` boxes them, witnessed). Extend the detection to
`Signal` roots and emit exactly the `json_like_schema.rs` / `dotos-text-query`
stack: `#[rkyv(omit_bounds)]` on each self-reaching position plus the three
type-level bound attributes. **Emit it only where a self-reach is detected** —
`omit_bounds` silently weakens bounds on non-recursive types, so an
unconditional emission would be worse than the current gap. This removes the
sentence *"any recursive contract type is presently unexpressible in an Ethos
Signal"*, which is the kind of sentence that quietly redesigns wire formats, as
it already did once.

**(d) Guard the depth, and this is the finding that outranks the rest.** Every
Nexus reading a recursive Signal from a peer through bare `rkyv::access` is one
adversarial kilobyte away from a stack-overflow abort, because rkyv's default
subtree depth is unlimited. Three things follow:

- `signal`'s frame-reading path must build its validator explicitly —
  `ArchiveValidator::with_max_depth(bytes, NonZeroUsize::new(64))`, Cap'n
  Proto's number — and go through the explicit-context API rather than
  `access`. This is worth doing **whether or not** any recursive type is ever
  declared, because it costs one constructor and closes the class.
- The aggregator's hand-built bounds (depth 32, 256 nodes, cycle detection)
  were the right instinct and should not have had to be hand-built. The node
  and depth ceilings belong in `signal` beside the frame capacity, not in each
  consumer.
- The cycle detection the aggregator wrote is, for an rkyv archive,
  **unnecessary** — the subtree-range model makes a back-edge unvalidatable.
  It is still necessary for the *datom text* path and for a peer-supplied
  arena's indices, which is what the aggregator actually guards. Worth recording
  so the next flow does not delete the wrong one.

**(e) Two gaps neither report names, fixed in the same pass.** Nothing is
emitted for the *archived* type: `#[rkyv(compare(PartialEq))]` would let a
Nexus compare `Signal == ArchivedSignal` without materialising, which for a
zero-copy wire is more valuable to consumers than `Eq` on either; and
`#[rkyv(derive(Debug))]` on the archived type makes a refused frame printable.
Both are additive and cheap.

**(f) Recommend the arena for peer-facing recursion, without enforcing it.**
Making recursion expressible is not making it wise. Arrow cannot express a
recursive type at all and flattens; Cap'n Proto and FlatBuffers express it and
then bolt on the limits that flattening makes unnecessary. A flat arena's
validation is a linear pass — no stack depth, no traversal budget — and it
yields stable four-byte node handles that a relative pointer cannot give
(a `RelPtr` is only meaningful at its own address and cannot be copied). So the
aggregator's forced redesign landed on the better shape, and the report should
not read as a defeat. Put the guidance in the `ethos` skill; do not enforce it
in the generator, which cannot see whether a type is peer-facing.

### Alternatives rejected

- **Derive `Eq`/`Hash` unconditionally without fixing `Decimal`.** Rejected: it
  does not compile for any type reaching a Decimal.
- **Conditional derive as the permanent answer.** Rejected as permanent,
  accepted as interim, for the silent-semver-break reason above.
- **Opt-in ethos annotation for derives.** The literature's own preference, and
  a closer call than it first appeared: it is *not* the syntactic repetition
  `Vision/ethos.md`'s closing law forbids, because it states an intent the
  structure does not determine — "this type is meant to be a key" — and the
  generator verifies rather than restates it. Rejected as the recommendation
  only because fixing `Decimal` removes the need for any annotation, and adding
  syntax that a pending fix would make vestigial is the wrong order.
- **Forbid recursive types in a Signal root and mandate arenas.** Rejected:
  a Library root already recurses fine, so the rule would be arbitrary at the
  boundary, and the generator cannot see which types face peers.
- **Emit `omit_bounds` unconditionally** to avoid the detection work. Rejected:
  it silently weakens bounds on every non-recursive type, trading a compile
  error for a latent one.

### Vision lines affected

- `Vision/ethos.md` has **no statement on derives at all** — this is open-items
  A10. So no line is superseded; lines are **owed**. Proposed, near
  `Vision/ethos.md:253`:

  > A declared type derives what its structure justifies. Clone, Debug,
  > PartialEq, Eq and Hash always, once Decimal is a finite type; never Copy,
  > because a wire type's size is not part of its contract; never Default,
  > because a default is a policy the consumer holds, not a value the wire
  > carries.

  *"A type that reaches itself is generated with the bounds rkyv's derive
  cannot infer."*
- `Vision/ethos.md:133` — Decimal as an intrinsic. **Not superseded; narrowed.**
  Proposed: *"Decimal is finite: it has no NaN and no infinity, so a Decimal is
  ordered and equal to itself."* This is the A7 fix and this decision leans on
  it.
- `Vision/signal.md`, **Protocol** — *"Signal is portable rkyv plus whatever
  protocol is standardized on top of it. The protocol is to be decided."* A
  line is owed here for the reading bounds: *"A Nexus reads a peer's archive
  under a declared depth and size ceiling; an archive that exceeds either is
  refused, not read."* This is genuinely new and is this flow's proposal.
- Note the interaction with item 2: if `X.T` becomes generative, aliases stop
  existing, *"An alias bears them through the type it names"* goes with them,
  and every named type carries its own derives — which makes this decision
  simpler, not harder.

### Implementation plan

Three repositories, in this order.

1. **`signal`**, minor — and do this first, because it is the security half and
   it does not wait on anything. Replace the bare `access` in the frame-reading
   path with an explicitly constructed
   `ArchiveValidator::with_max_depth(bytes, NonZeroUsize::new(64))` plus the
   existing `FrameCapacity` byte ceiling, and give the refusal a typed name.
   Test, seen failing first: a hand-built archive nesting past the ceiling is
   refused rather than aborting the process.
2. **`ethos-zero`**, major.
   - `src/generation.rs:572-589` — `DatomDeriving for bool` becomes a method on
     the declaration, not on a `bool`, so it can see the type. (A trait
     implemented on `bool` is also the *"traits live on data-bearing types"*
     rule from the `nexus` skill broken in miniature; fix it in the same pass.)
   - New: a memoised, cycle-safe reachability fold — *"does this type reach a
     Decimal?"* — gating `Eq`/`Hash`. Must be cycle-safe, because recursive
     types are precisely what step (c) admits.
   - New: a self-reach predicate per position; where true, emit
     `#[rkyv(omit_bounds)]` on the position and the three `#[rkyv(…)]` bound
     attributes on the type, copied from
     `dotos-text-query/src/query.rs:10-17`.
   - Add `#[rkyv(compare(PartialEq))]` and `#[rkyv(derive(Debug))]` to the
     Signal arm.
   - Fixtures, which are the whole gate: a recursive Signal (the exact case that
     produced `E0275`) with its checked-in expected output; a pair of types, one
     reaching `Decimal` and one not, pinning the conditional; and a fixture
     whose recursion goes through both `Vec<Self>` and `Box<Self>`.
3. **A7, then a follow-up ethos-zero release** turning the conditional
   unconditional once `Decimal` is finite. Worth scheduling together so the
   interim is short and the semver break happens once.
4. **The estate** regenerates. Types gaining `Eq`/`Hash` is additive; nothing
   breaks. Consumers that hand-wrote `Eq` impls to fill the gap must delete
   them — `grep -rn "impl Eq for" signal-* meta-signal-*` finds them.

Wire impact: **none from the derives** — they change the Rust API, not the
archive layout or the text form. The recursion change is **additive**: types
that could not be declared become declarable. The depth ceiling in `signal` is
a *refusal* that did not exist before, so an archive nested past 64 that
previously aborted the process now returns a typed refusal — a behaviour change
nobody should be relying on.

### Researched

The relevant literature here is about *what a framework library may own*, and it
converges on one rule: **a library may own what every instance must do
identically, and nothing that any instance might reasonably do differently.**
OTP is the reference case — `gen_server` owns the loop, the mailbox, the
call/cast distinction, the timeout and the terminate path, and owns **nothing**
about what the state is or what the messages mean. The behaviour module is the
ontology; the callback module is the domain. Ranch owns the acceptor pool and
the connection supervisor and owns nothing about the protocol.

Applied here, the test for "does this belong in `nexus`?" is: *would two
different Nexuses implement it identically, and would getting it wrong be a
defect rather than a design choice?* `ConfigurationState` passes. `Applies`
passes. A lock table does not.

The second finding from the literature is a warning rather than a pattern.
`triad-runtime/src/role.rs` — seven traits with no capabilities — is what
happens when a library is populated by naming nouns rather than by extracting
behaviour. The psyche's own diagnosis of it (*"mindlessly created traits that
don't create a sensible ontology"*) is the standing instruction, and the
practical guard is the `nexus` skill's own rule: *"Traits live on data-bearing
types. A zero-sized type with behavior is a namespace pretending to be a
thing."* A marker trait with no capability and no data is the degenerate case of
exactly that.

### The decision

**`nexus` defines six things, in this order, and each is lifted from a second
witnessed implementation — never invented.** The ordering rule is the important
half: *nothing enters `nexus` until two Nexuses have implemented it and agreed.*
That is the discipline that prevents `role.rs` from happening twice, and it is
the operational reading of *"old code is at most inspiration for that map."*

**1. The configuration lifecycle** — `ConfigurationState`, `Configurable`.
Already there, already correct, two consumers. Done.

**2. Situation** — the observed-binding record and copy guard from item 3.
Universal: every Nexus binds sockets it must not steal, and every Nexus can be
copied. `Situated` with `fn situate(&mut self, …)` at bind and
`fn is_carried(&self, opened: &Path) -> bool` at open. Lifted from orchestrate
once item 3 lands, and lojix needs it identically.

**3. Authority** — `Permissive`, from `orchestrate/src/transport/socket.rs:35-49`
verbatim: a socket's file mode and its `admits(peer_user, owner)` predicate.
Universal by `Vision/nexus.md`'s own two-socket rule. Lifting it also forces the
fix to the per-contract refusal defect named in item 6, because a shared
`Permissive` cannot know which contract to refuse on — which is the good kind of
pressure.

**4. Entering and its effect** — `Applies<Entering> { type Effect; fn apply(…) }`.
This is the one Vision names directly (*"Processing is for the effect … The name
is open, Apply liked"*, `Vision/nexus.md:25-28`) and the one `orchestrate-work.md`
§6.4 already flagged as belonging here. The name `Applies` is the psyche's own
"Apply liked" in qualifier form, so it needs no further ruling.

**5. Announcement** — `Announcing`, plus the subscription contract item 4
designed: a monotonic cursor, snapshot-on-open, bounded per-subscriber queue,
typed lagged refusal. This is where `Vision/nexus.md:117-125` ("observation by
subscription", "polling is forbidden") becomes machinery instead of an
aspiration, and it is the single highest-value thing `nexus` could hold, because
every Nexus will otherwise build it slightly differently — orchestrate already
built one shape, lojix built a stub, sema-engine has a third
(`subscribe`/`SubscriptionSink`/`SubscriptionDelta`, relayed as unused).

**6. The daemon shape** — the two-socket bind, the accept loop, the session
task, and the Kameo actor rules from item 6. This is the largest piece and the
last, and it is the one `recent-vision.md` item 6 calls *"a real port across
three repositories, not a rename."* It should move only after item 6's pilot
runs in orchestrate.

**What `nexus` must NOT define**, stated because the failure mode is
over-population: the frame envelope and codec (that is `signal`'s, already
correct and already shared — witnessed, six crates shed 68 duplicated lines each
into it); the store engine (that is `sema-engine`'s); any domain noun; and
anything resembling `triad-runtime/src/role.rs`'s empty markers. If a trait
has no capability and no data-bearing implementor, it is a note, not a kind.

**On the dependency question A27 asks** — should `nexus` depend on `signal` and
`sema`? **Yes, on `signal`; no, on `sema-engine`.** Items 4 and 5 above cannot
be expressed without the frame and the `Signal<T>` wrapper — an `Announcing`
that cannot name what it announces is another marker trait. `sema-engine` stays
out: the store is generic to `nexus` (`ConfigurationState<C>` is already
parameterised the right way), and depending on a storage engine would make
`nexus` un-implementable by any Nexus that later wants a different one. This is
the OTP split exactly: `gen_server` knows about messages, not about Mnesia.

### Alternatives rejected

- **Leave `nexus` as configuration-only and keep the daemon in
  `triad-runtime`.** Rejected: `triad-runtime` 0.7.0's last substantive commit
  predates every Nexus vision record, it is NOTA-based, and it carries
  `role.rs`. It is inspiration, per the psyche's own word, not a foundation.
- **Design the whole ontology up front before porting anything.** This is the
  literal reading of *"The basic ontology … is designed before implementation."*
  Rejected as the operational plan, and this is the one place this thread

### Implementation plan

Repository `nexus`, six releases over as many landings; nothing big-bang.

1. **0.2.0** — `Permissive` lifted from orchestrate verbatim, with orchestrate
   and lojix both repinned in the same wave. Smallest possible first move; it
   proves the lifting discipline works before anything load-bearing moves.
2. **0.3.0** — `Situated` (item 3), landing together with orchestrate's copy
   guard.
3. **0.4.0** — `Applies<Entering>`, lifted from `orchestrate/src/core.rs:56-63`,

   `triad-runtime/src/reaction.rs`'s `Work`/`Action` enums get their second look

   direct `Response`, and that comparison is real design work deserving its own
   thread.
4. **0.5.0** — `Announcing` plus the cursor-bearing subscription contract from

5. **1.0.0** — the daemon shape and the actor rules from item 6, after the

6. Throughout: **a test in `nexus` per lifted kind, and the two consumers'

## The eight decisions, one paragraph each

**1. Datomizable.** Split it. `Datomizable` keeps only the ascent —
`fn datomize(&self, at: Path) -> Datom`, infallible, with the associated
`Output` deleted so that a `T: Datomizable` bound finally constrains something;
the descent `Protos → Datom` keeps the name `DatomForming` it already has in the
code and loses the one-line `Datomizable` forwarder that exists only to satisfy
the Vision table. The literature is one-sided — serde, `From`/`TryFrom`,
`FromStr`/`Display`, rkyv and bincode all split, and the one unifier, `prost`,
pays for it by forcing `Default` onto every write-only type — and the pair's
proper name is a Prism, whose laws are asymmetric, so a single kind would assert
an isomorphism that non-canonical datom text does not have. `Vision/protos.md:72`
and `:79-81` are superseded, and `Vision/protos.md:65-66`'s naming rule needs one
amending clause distinguishing ascent from descent, because as written it is
direction-blind and generates the same collision for `Protosizable`. Separately
and urgently: the `datom` skill at `Curriculum/skills/datom.md:75-95` documents
`Corporal`, `Embodied`, `incorporate` and `Fault`, none of which exist in any
repository — a tenth false skill statement that every flow reads before touching
datom.

**2. Single-field structs.** Make `X.T` generative first, then refuse
`X.{ T }` second; doing it in the other order breaks protos's own flake check on
day one. The psyche asked for a new type and pointed at the one construct
`Vision/ethos.md:255-256` defines as not being one, so that Vision line is what
gives way, not the psyche's words. The decisive argument is Rust-specific and
absent from every schema-language survey: orphan rules mean an alias can never
carry the dialect's own trait impls, so an alias-only schema language is
structurally unable to attach behaviour to a name — and ASN.1 confirms the
general lesson that naming alone reads as transparent to everybody. The test that
this is right is that it deletes code: `protos.ethos:17`'s `ReaderBudget.{ Integer }`
becomes `ReaderBudget.Integer`, the generated newtype finally matches the
hand-written one at `protos/src/core.rs:67`, and the hand-patched
`Datomizable for protos::ReaderBudget` at `datom-codec/src/composition.rs:595`
— which already unwraps the single position, the way a collapse rule would —
disappears. The cost is honest and large: every rkyv archive in every Signal
contract changes, so this is a whole-estate cutover, not a repository-by-
repository migration.

**3. Socket binding.** The store wins, Vision is right, and A17 misread it. The
sentence it quotes sits inside `Vision/nexus.md`'s **First configuration**
section and the psyche's own raw record explains it as the reason built-in
defaults must exist at all — *"otherwise we wouldnt have a socket path to even
fall back on to even allow the configure signal to come in"* — not as a
precedence rule; and the same record puts socket paths in the metadata tree and
makes meta-Configure the way they change, so a default that won forever would
make that field decoration. The external survey pushes the other way hard (no
mainstream daemon takes its listen address from its own data store, and Postgres
pointedly writes its binding to `postmaster.pid` as *state*, deleted on
shutdown, never read back as config) — but every daemon in that survey has
ambient configuration, and `Vision/nexus.md:78` forbids a Nexus to have any, so
the store is our `postgresql.conf`-in-PGDATA, not our `postmaster.pid`. What is
genuinely missing is the other half Postgres has: an observed record written at
bind (store path, bound sockets, PID, boot id, ideally a store UUID), a refusal
to bind when the opened store is not where its record says it lives, and an
`flock` replacing the connect-probe at `transport/socket.rs:67-81` that currently
deletes a stale socket and takes it.

**4. WatchDeployments.** Delete the vocabulary; keep the tables. Nobody asked
for it, the only exercise is a unit test round-tripping `Query::Unwatch`, the
filter payload is bound to `_` and discarded, five of six declared refusal
reasons are never constructed, and — decisively — the reply block contains no
event variant at all, so there is nothing to implement against and "implement
it" and "delete it" both begin by deleting it. A43 is wrong about the tables,
though: `deployment-outbox` and `pending-transition-intent` are written from
four production deploy paths and drained at store open for crash recovery, so
deleting them would delete recovery. The second half of the decision is for
whenever a real subscription is built anywhere: build it from the store's
`commit_sequence`, not from the in-memory `AtomicU64` token, because a design
that forbids polling needs a monotonic cursor or a reconnecting subscriber
cannot tell "nothing changed" from "I missed everything" and must poll after all
— which is etcd's `compact_revision` and Kubernetes' `410 Gone`, and which
`SubscriptionOpened`'s existing `CommitSequence` field already half-anticipates.
`lojix/ARCHITECTURE.md` makes six false streaming claims and names six types
that exist in no Rust file; those paragraphs go with the verbs.

**5. Hardware classification.** None of A31's three options is right taken
whole; split the eleven fields three ways. `handleLidSwitch{,ExternalPower,Docked}`
were never hardware classification — the deleted derivation reads only
`center`, `lowPower` and `edge`, all three live in today's `BehavesAs` — so they
are recomputable in CriomOS with no Horizon change at all. `typeIs.*` is
`behavesAs.*` under an older name, and CriomOS-home's two `or false` defaults are
the silent-degradation hazard A31 warns about, live today. For the model flags,
match the raw string in CriomOS — which `metal/default.nix` already does in about
a dozen places — but against a closed `modelFacts` attrset with an assertion that
`model` is one of its keys, which is strictly better than `KnownModel` gave us,
since `known()` returned an `Option` and silently emitted all-false for an
unrecognised string. horizon-rs's *"enum-shadow structs"* judgement is
`Intent/context.md` applied correctly: a projection says what a machine is, and
what that means for systemd is the consumer's table. One finding A31 does not
report and which forces the fixture rewrite: the four metal fixtures write a flat
`machine.model` while the module reads `machine.hardware.model`, so they are
false-green on live fields as well as retired ones.

**6. The Kameo actor boundary.** One state actor per Nexus owning the store
outright with no `Mutex`; sockets are not actors, a listener is a task and a
connection is a task holding an `ActorRef`; authority is the message type a
session can construct, minted from the peer at accept, which is what
`Applies<OrdinaryQuery>`/`Applies<MetaQuery>` already achieve structurally; the
mailbox stays bounded and nothing blocking runs inside it, with subscription
fan-out `try_send`-and-mark-lagged so one slow watcher cannot stall every write.
That is ranch's shape and Ryhl's and OTP's, and the privileged path reaching the
*same* actor rather than a different or supervising one is what systemd, etcd and
Postgres all do. Stated honestly: for orchestrate as it stands, Kameo buys
little over the `Arc<Mutex<_>>` Vision permits — what it buys is daemon
lifecycle (`on_start` fallible construction, `on_stop` flush on graceful *and*
panic stop, `stop_gracefully` vs `kill`, restart limits, the console), so the
actor is warranted for the daemon and not for the store. Lifting `Permissive`
into `nexus` will force the fix to a live defect this reading exposed: the peer
refusal at `transport/session.rs:94-106` always writes a *meta*-contract frame,
correct today only because `Ordinary::admits` is unconditionally `true`. On the
fork: its five commits are now established (lifecycle terminal outcomes, split
control mailbox), `#[messages]` is used nowhere in the estate, lojix already
patches it out — recommend crates.io 0.22.2 and offering the lifecycle work
upstream, though A19 remains the living's call.

**7. Derives and recursion.** The terminal answer on `Eq`/`Hash` is to fix
`Decimal` rather than to make the derive conditional: a finite decimal — no NaN,
no infinity, no `-0.0` — is `Eq`, `Hash` and `Ord`, so A7's open item and this
one are the same fix seen from two sides, and with it `Eq`/`Hash` become
unconditional and no machinery is needed. Until then, derive them conditionally
on a cycle-safe "does this type reach a Decimal" fold, and say the cost out
loud: adding one float to one leaf type silently strips `Eq` from every ancestor,
a major semver break emitted by an innocuous schema edit — which is why the
literature prefers an opt-in annotation the generator *errors* on, prost's shape,
and why A7 should be prioritised so the interim is short. Leave `Copy` lost (a
wire type's size is not part of its contract) and never derive `Default`, because
the aggregator already wrote the right rule — *"a runtime ceiling is a policy a
runtime asks for, not a zero value"* — and prost's `Default` is no counterexample,
being a protocol requirement of `Message::decode` rather than a convenience. On
recursion, the report's *"unexpressible in an Ethos Signal"* is true of the
generator and not of rkyv: rkyv ships the exact recipe as
`examples/json_like_schema.rs`, a recursive `JsonValue`, and
`dotos-text-query/src/query.rs:8-24` runs it in production — three type-level
bound attributes plus `#[rkyv(omit_bounds)]` per self-reaching position — so
Ethos Zero should emit that stack where it detects a self-reach, and only there,
since `omit_bounds` silently weakens bounds elsewhere. **The finding that
outranks all of that**: rkyv's `ArchiveValidator` defaults to *unlimited* subtree
depth and the convenience `rkyv::access` goes through that constructor, so any
Nexus validating a recursive archive from a peer is one adversarial kilobyte from
a stack-overflow abort — Cap'n Proto ships depth 64 on by default for exactly
this reason, and `signal`'s frame path should build its validator explicitly with
a ceiling whether or not a recursive type is ever declared. Two smaller gaps
nobody named: nothing is emitted for the archived type, where
`#[rkyv(compare(PartialEq))]` would let a Nexus compare against an archive
without materialising it. And the aggregator's forced flat-arena redesign is the
*better* shape for a peer-facing type — Arrow cannot express recursion at all and
flattens; a flat arena validates in a linear pass with no depth question — so it
should be recommended in the `ethos` skill, not read as a defeat.

**8. The nexus library.** Six things, in order, each lifted only on its second
witnessed implementation: the configuration lifecycle (already there);
situation — the observed binding and copy guard from item 3; authority —
`Permissive` lifted verbatim from orchestrate; entering-and-effect — `Applies`,
which closes Vision's own open name (*"Apply liked"*); announcement — `Announcing`
plus the cursor-bearing subscription from item 4, which is the highest-value
piece because every Nexus will otherwise build it differently and three already
have; and last, the daemon shape and actor rules from item 6, after the
orchestrate pilot runs. Depend on `signal` (an `Announcing` that cannot name
what it announces is another marker trait) and not on `sema-engine` (the store
stays generic, exactly as `ConfigurationState<C>` already is) — the OTP split,
where `gen_server` knows about messages and nothing about Mnesia. The one Vision
line this thread argues is wrong as written is `Vision/nexus.md:16-19`, *"The
basic ontology … is designed before implementation"*: the estate has already
tried that literally and the result is `triad-runtime/src/role.rs`, seven traits
with no capabilities, which is precisely the *"mindlessly created traits that
don't create a sensible ontology"* the psyche diagnosed — and the psyche's own
later *"old code is at most inspiration for that map"* concedes that the map is
drawn while looking at code. Propose: designed piece by piece, admitted on the
second implementation.
