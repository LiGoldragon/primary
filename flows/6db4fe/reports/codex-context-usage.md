# Codex context and usage collection

Observed on 2026-09-21 with Codex CLI and managed app server 0.153.4. The tested native thread was the exact ID supplied by the Field route, not a name or fuzzy lookup. The probe did not resume or change the thread. It called only `initialize` and `thread/read` with `includeTurns:false`, then read a bounded tail of the returned rollout path. The live collector returned in 18 ms in one local run; this is a measured example, not a service latency guarantee.

## Preferred short-term method

`collectCodexContext({nativeThreadId})` in `tools/field-census/codex-context.mjs` connects to the managed app server's WebSocket-over-Unix socket, reads exact thread metadata, validates the returned ID, and uses the server's canonical `thread.path`. On the tested thread, `thread/read` returned that ID, path, model, status, and `updatedAt` in 6.7 ms. The request had zero turns in its response. The local 0.153.4 schema's `Thread` has no usage field. [Official App Server documentation](https://developers.openai.com/codex/app-server) specifies that `thread/read` does not resume or subscribe to the thread.

The collector accepts at most 2 MiB of a metadata response frame (one older live thread returned a 527 KiB frame), projects only ID/path/name/model/status/update time, and discards preview text. It reads at most 1 MiB of the path's tail by default and at most 2 MiB even if a caller asks for more. It parses only JSON records in that tail, extracts the newest `token_usage_record` and `event_msg`/`token_count`, and discards all conversation content. It does not walk a transcript from its start or send a model request. The exact filename-to-native-ID check also applies to a caller-supplied fallback path. If the socket is absent and no exact path is supplied, usage is unknown with an explicit error; an empty result is never zero usage.

The native `token_usage_record` payload observed here contains `usage` (one response), `turn_token_usage`, and `thread_token_usage`. The collector prefers that record's response, turn, and thread counters because its timestamp was later than the last `token_count` event in the live sample. This record is local runtime evidence, not a documented stable App Server response. The latest `token_count.info` supplies `model_context_window` and a second source of cumulative and last-response counters when a `token_usage_record` is unavailable. The observed counter fields were input, cached input, cache-write input, output, reasoning output, and total tokens. Cached input is a subset of input; reasoning output is a subset of output. Do not add either subset to its parent. `thread_token_usage.total_tokens` counts emitted usage across the thread, not the current context length.

The most recent response's `input_tokens` is a **context occupancy proxy**. The native event does not expose exact current resident context tokens, nor exact remaining capacity during an in-progress turn. The collector therefore sets `exactTokens` and `remainingExactTokens` to null. `remainingEstimateTokens = modelContextWindow - lastInputTokens` is labeled an estimate and can lag the current state. If a later user message or compaction marker appears, status becomes `superseded` and the remaining estimate is null; the overview hides that old proxy. It should not drive an automatic compaction threshold without safety margin and a freshness check. If the latest event falls outside the bounded tail, the fields remain null. The exact emitted API token count, invoiceable usage, and ChatGPT subscription usage are different concepts; these local records establish emitted counters only, not a bill.

`token_count.rate_limits` is an account quota snapshot attached to a thread event, with `limit_id`, primary and secondary window usage, reset epoch, and plan type in the observed payload. The collector places it under `quota.scope:'account'`, separate from `occupancy` and `usage`; it can be stale. [App Server documentation](https://developers.openai.com/codex/app-server) describes `account/rateLimits/read` for a fresher account-level pull and `account/rateLimits/updated` for changes. These are account windows, not context-window percentages. A read-only live `account/rateLimits/read` succeeded in 469 ms and returned a 10080-minute `codex` window; overview now makes one such pull per snapshot, separate from all rows. A read-only live `account/usage/read` succeeded in 484 ms and returned summary, daily buckets, and thread usage; it is not per-thread context occupancy or billing evidence. The account ID and any credit details are not retained or rendered.

## Candidate interfaces and tradeoffs

| Interface | Supported information | Boundary / use |
| --- | --- | --- |
| `thread/read` (`includeTurns:false`) | Exact native ID, canonical path, model, status, timestamps, name | Tested read-only; no usage counter. Preferred exact binding. |
| `thread/tokenUsage/updated` | `{threadId,turnId,tokenUsage:{total,last,modelContextWindow}}` | Documented streaming notification. The schema does not contain a standalone read request for this value; subscription is tied to active thread traffic. Useful for a future continuously connected owner, not a cold census poll. |
| Rollout `token_usage_record` | Per-response, turn, thread emitted token totals | Tested in bounded tail; local persisted format may change. Preferred latest usage observation. |
| Rollout `event_msg.token_count` | Thread cumulative and last usage, model context window, account quota snapshot | Tested in bounded tail; fallback usage and preferred window snapshot. |
| `account/rateLimits/read` / `updated` | Current account quota windows | Read tested live; notification documented only. Account scope; one poll enriches all Codex flows. |
| `account/usage/read` | Account token activity and daily buckets | Read tested live; not current context or a bill. |
| `thread/turns/list` | Recent persisted turns without resume | Experimental, optional turn activity metadata; no context usage in the local schema. No need to page history for census. |
| `codex agents` | Interactive session browser | No machine-readable usage contract in 0.153.4 help; unsuitable for a fast collector. |

The [official App Server documentation](https://developers.openai.com/codex/app-server) describes `contextCompaction` item completion as the compaction signal and deprecates `thread/compacted`. A compaction item says compaction occurred; it does not itself state the new resident context count. After compaction, wait for a fresh usage event before updating the input-token proxy. A new native thread should start a new usage series; cumulative totals must be keyed by exact native thread ID. No compaction was performed in this probe, and reset behavior of the local `thread_token_usage` record across compaction remains unverified.

## Nexus contract candidate

Treat the returned object as an observation with `source`, `method`, `observedAt`, `eventAt`, and `nativeThreadId`. `freshness` carries event age, server thread update time, tail bytes examined/truncation, thread status, and whether app-server established the exact binding. `usage` carries response, turn, and thread totals with their source; `occupancy` carries the last-input proxy and model window with exact fields null. `quota` has explicit account scope. `errors` preserves partial failure. A Nexus `Context.Get` request can take an exact native ID and return this observation; a `Context.Watch` process can consume `thread/tokenUsage/updated` and `contextCompaction` items while keeping the bounded collector as a cold-start/recovery path. Store SEMA records for the binding, observed event timestamp, method, units, and uncertainty rather than promoting an estimate to an exact reading.

The name correction route is distinct: 0.153.4's generated schema has `thread/name/set` with `{threadId,name}` and a `thread/name/updated` notification with `{threadId,threadName}`. [Official documentation](https://developers.openai.com/codex/app-server) says it can name a loaded thread or persisted rollout. It was not invoked here.

## Verification

The collector fixtures cover newer per-response usage with separate quota, a truncated first line, and later user/compaction supersession. The overview integration tests cover exact route filtering and identity mismatch. A read-only live call returned exact binding, the newer `token_usage_record`, a 258400-token model window, and no errors in 18 ms. An integrated live overview later returned 13 native context observations across 14 exact routes; the remaining exact HM registration had no native thread ID and was left unknown. These sample latencies are not representative across hosts or load.
