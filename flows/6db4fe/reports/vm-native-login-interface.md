# Existing VM native login boundary

This is **source/interface preparation only** for Prometheus's existing `microvm@vm-testing.service`. Field 6db4fe holds the exact guest runtime reservation 4373. The unit remains inactive; no guest, auth flow, model, or Message transport was started. The coherent Flow/Message/Signal graph and Field parity fixture are prerequisites to any Flow/Message trial. SSH access to the guest and model-account login are distinct gates.

## Luna: supported process-memory path

The installed Codex CLI exposes `app-server --listen unix://PATH` and accepts `-c` configuration. [Official Codex authentication documentation](https://developers.openai.com/codex/auth) defines `cli_auth_credentials_store = "ephemeral"` as keeping credentials in memory for the current process. [Official app-server documentation](https://developers.openai.com/codex/app-server) supports `account/login/start` with `type: "chatgptDeviceCode"`, a one-time user code, and `account/login/completed` on the same server. The supported **proposal** is one guest-local app-server process with a guest-local Unix socket and ephemeral credential store, device-code login completed by the living, then the one disposable Luna turn through that same process. Stopping that process ends its auth lifetime. No host auth cache, token, home directory, SSH agent, or account file is copied or mounted into the guest, and no app-server port is exposed beyond the guest.

This combination has **not** been exercised in the guest. The guest Codex package/version, device-code permission on the account, the login notification, the exact model request, and proof that no guest credential file was written are still required. Do not run `codex login --device-auth` as a separate process with `ephemeral` storage and then expect a later process to be authenticated; the store is process-local. Do not record the one-time code, account identity, token, login trace, or raw request/response in the test artifact. Only redacted success/refusal and process identity belong in the receipt.

## Haiku: native login exists, strict process-only grade is unavailable

The installed Claude CLI exposes `claude auth login` and `claude --model` for a later process. [Official Claude authentication documentation](https://code.claude.com/docs/en/authentication) says the headless/SSH login can present a URL and a code for the living to paste, and that on Linux it stores credentials in `.credentials.json` with mode 0600. [Official environment documentation](https://code.claude.com/docs/en/env-vars) provides `CLAUDE_CONFIG_DIR` to relocate that directory. Thus a guest-local tmpfs config directory could confine a newly performed native login to guest memory and avoid image/snapshot persistence, but it is still a **credential file**, not a documented process-memory-only store. Under a literal process-only/no credential-file requirement, Haiku has no supported accepted interface yet. No setup token, API key, host credential cache, or file copy is proposed.
