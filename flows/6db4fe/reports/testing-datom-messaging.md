# Main-flow machine messaging skill landing

On 2026-09-21, authored Curriculum gained `skills/testing-datom-messaging.md`, and `skills/main-flow.md` added it as a dependency. The skill requires a machine-origin interflow message to be one complete Datom value against a declared recipient type, distinguishes the existing `MACHINE.Relay` transport envelope from the typed payload inside its quote, and keeps direct living conversation under its ordinary response contract. It separates structural codec acceptance, recipient semantic validation, and target-side receipt grades.

The current `tools/msg` bridge wraps its message argument in `MACHINE.Relay.{ ingress from seat heard mode [recipients] quote context }`. A real `tools/messaging-codec` run accepted a quote containing `Status.{ Accepted }` as a structurally valid variant and exited 2 on `ordinary prose`. This proves the parser boundary only; no recipient `Status` semantic contract was asserted by this test, and no live message was sent. `tools/messaging.py` constructs the relay, but its own command path does not validate recipient semantics.

The `curriculum-deploy` source scans every `skills/*.md`; there is no special `testing-` whitelist or pruning rule. Its local built binary generated both `.agents/skills/testing-datom-messaging/SKILL.md` and `.claude/skills/testing-datom-messaging/SKILL.md`, plus refreshed main-flow projections, with `Generated.{ 65 21 }`; `Check.{ 65 21 }` then passed. The documented `nix run` generator was attempted first but timed out contacting the configured Nix cache, so the same local `curriculum-deploy` runtime performed generation. Fresh native launch profiles must explicitly list `testing-datom-messaging`, `datom`, and `messaging` and witness their expanded bodies; a dependency string by itself is not a native start receipt.

The active accepted-workaround record is `NON_IDEAL_AGENTS.md` in primary, with peer files in the signal, orchestrate, CriomOS, and lojix repositories. My earlier search of the `standards` checkout and `vision-raw/nonIdealAgents.md` missed that convention. I checked the existing primary and peer nonideal files before adding any entry: none currently records this messenger bridge's structural-only check. No workaround entry was added in this narrow skill landing; the concrete gap is that a generic Datom variant is accepted without validating the recipient's semantic type. A stable recipient semantic message type/validator for every flow remains open.

For a harmless launch route check, the launcher and target can explicitly agree on a local probe/ack type before sending: `RouteCheck.[ Probe.{ Marker.String } Ack.{ Marker.String } ]`. The wire values are `Probe.{ «unique marker» }` and `Ack.{ «same marker» }`. The launcher must check the actual Datom parse **and** the exact variant, one string field, and marker equality at the target response. This is a bounded probe contract, not a general interflow message schema or evidence of the target's receipt until its answer is observed. The launch worker was given this shape; no live probe was performed by this report writer.
