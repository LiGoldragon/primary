# VSCodium runtime audit

The runtime is a Home Manager-managed package plus a user-state lifecycle reconciler, not a Codium service. The intended managed command protects the mutable Claude links, Nix GC roots, manifest, and extension registry with `flock`; raw or already-running Codium processes do not participate in that lease.

## End-to-end sequence

1. `modules/home/default.nix:76-90` imports the medium Codium desktop module and the managed VSCodium module. The latter is active only for `user.size.medium` (`modules/home/vscodium/vscodium/default.nix:244-268`).
2. `modules/home/vscodium/vscodium/default.nix:15-80` builds the casual Codium wrapper, lifecycle, supervisor, and launcher with absolute runtime dependencies. `:82-97` replaces the package's `bin/codium` with the managed launcher.
3. The extension graph is declarative at `:247-267`: VisualJJ, Claude Code, ChatGPT/Codex, Pi, direnv, Nix IDE, and three Markdown/Mermaid extensions. The raw VSIX inputs and versions are pinned by `flake.nix:50-92`; Claude's native binary is replaced by the pinned Claude CLI at `:154-167`.
4. The authored activation hooks are `bootstrap` before link generation, `activate` after link generation, and three `activation-refresh` attempts after replacement (`:333-350`). The current generated activation confirms the order and adds Home Manager's immutable-file change hook: it deletes `extensions.json` and runs the managed `codium --list-extensions` before the lifecycle replacement (`activate:255-257`, `:310-340`, `:611-637`).
5. Lifecycle startup validates every configured path and runtime executable (`claude-lifecycle.sh:5-95`), then uses the state lock. `register_root` calls Nix's `--add-root --realise` (`:109-125`), so even a nominally diagnostic CLI can create/refresh user GC-root state.
6. Missing or contradictory state is repaired only when the stable Home link, versioned link, manifest, root, package metadata, and immutable declaration authenticate the tuple (`:267-325`, `:327-386`). Normal convergence creates or retargets the current versioned link/root, writes `manifest`, and removes only prior manifest-owned entries (`:634-727`).
7. Registry refresh validates Claude and OpenAI owner records and the immutable snapshot (`:420-483`). An absent registry is seeded from the immutable declaration (`:543-555`); an existing registry is backed up, sent through underlying `codium --list-extensions`, transformed, and atomically replaced or restored on failure (`:557-592`).
8. A managed launcher invocation validates state and lock paths, calls `--prepare-launch`, and then classifies terminal flags (`codium-launch.sh:25-84`). Terminal/state flags—including `--help`, `--version`, `--status`, `--list-extensions`, and extension-management flags—invoke underlying Codium synchronously after reconciliation. GUI/file modes create a session, start the supervisor, wait for authenticated `ready`, acknowledge `consumed`, and return without waiting for the GUI (`:86-117`).
9. The supervisor preserves Codium's foreground process/cgroup/cwd/environment/argv, writes `started`, `ready`, and `status`, forwards only HUP/INT/TERM, then waits for cleanup (`codium-supervisor.sh:49-99`). There is no Codium-specific systemd service in the repository; graphical launches appear as transient user-manager app scopes.
10. The user-local desktop entry is generated by `modules/home/profiles/med/codium.nix:11-117`. Its opener decodes file URLs, handles line/column suffixes, and ultimately invokes bare `codium` (`:17-81`), while the desktop action also invokes bare `codium` (`:113-116`). Thus the desktop environment's PATH is part of the runtime authority boundary.

## Ranked findings

### P1: raw/pre-existing Codium bypasses the lifecycle lease

The lock is held only by the managed launcher/supervisor (`codium-launch.sh:65-78`, `codium-supervisor.sh:78-85`). The legacy-process guard is only in the missing-manifest branch (`claude-lifecycle.sh:654-663`); normal activation with an existing manifest does not inspect running Codium. The desktop opener/action use bare `codium` (`modules/home/profiles/med/codium.nix:75-81`, `:113-116`), and a pre-existing current GUI was observed as the underlying Codium binary in a transient user scope rather than the supervisor. Activation can therefore replace versioned links, roots, or `extensions.json` while an extension host has those paths loaded. This is a concurrency and crash-consistency boundary, not merely a stale-lock problem.

### P1: supervisor loss can release SH while its Codium child survives

The supervisor cleans only on ordinary signals and normal child exit (`codium-supervisor.sh:55-73`, `:83-99`). The launcher closes its own descriptor after startup acknowledgement (`codium-launch.sh:104-117`), and no parent-death signal, process-group ownership, or watchdog binds the child lifetime to the supervisor. A SIGKILL of the supervisor can leave a Codium child and session directory without the SH lease; the next activation can mutate managed extension state while that child runs. The durable check tests TERM forwarding and child reaping (`checks/vscodium-claude-lifecycle/default.nix:1113-1123`), but not supervisor SIGKILL or launcher SIGKILL.

### P1: read-only-looking CLI calls mutate lifecycle state

Every launcher invocation makes directories, opens/truncates the lock, and runs `--prepare-launch` before dispatch (`codium-launch.sh:51-84`). `--version`, `--status`, and `--help` can therefore create manifest/link/root state; `--list-extensions` can rewrite the mutable registry through the underlying Codium path (`claude-lifecycle.sh:557-592`). Home Manager's generated immutable-change hook explicitly removes `extensions.json` and invokes `codium --list-extensions` (`activate:611-619`). The operation is not read-only because lifecycle convergence and Codium's own CLI registry generation are stateful by design.

### P2: manifest and multi-step repairs are not power-loss atomic

Registry paths are synced around temporary-file renames (`claude-lifecycle.sh:473-483`, `:528-535`), but manifest writes use a temporary file and `mv` without a file/directory sync (`:320-324`, `:680-681`, `:694-696`, `:722-726`). Repair plans can execute several root/link mutations sequentially and fail part-way through (`:327-386`). A crash or power loss can leave the manifest, links, and roots in different generations; retries usually fail closed but can strand stale links/roots or make the GUI unavailable.

### P2: activation deferral is silent and can report success without readiness

Activation refresh takes a nonblocking EX lease and returns success when a GUI SH lease is present (`claude-lifecycle.sh:615-632`, `:641-651`). The launcher also exits zero when reconciliation is in progress (`codium-launch.sh:66-77`). A GUI launch can consequently be silently dropped, and Home Manager can finish while the registry/manifest remains unresolved. A child that fails after `ready` is acknowledged is outside the launcher's notification path (`codium-launch.sh:99-117`, `codium-supervisor.sh:83-99`).

### P2: immutable registry authority is not authenticated on the normal refresh path

`registry_matches_immutable` checks file content and the two owner records but not that `.extensions-immutable.json` is still a Home Manager symlink to a store object (`claude-lifecycle.sh:420-470`). The stricter symlink/store authentication exists only in contradictory recovery (`:234-255`, `:300-305`). A mutable regular file can therefore become the accepted snapshot during normal registry refresh, subject to the current Claude version and basic OpenAI metadata checks. This is user-level tampering rather than privilege escalation, but it weakens the declared Home Manager trust boundary and can create a false “ready” registry.

### P2: alternate Codium data paths are not part of the lease contract

The mode classifier recognizes a fixed list of flags (`codium-launch.sh:51-61`). It does not establish a corresponding state/lock relationship for options such as alternate user-data or extension directories. Such a command still reconciles the default managed state and then runs Codium against another state tree, so the lock protects the wrong files. The exact supported option set for the pinned Codium build was not executed because this audit was prohibited from launching Codium.

### P3: environment overrides are executable and stateful trust seams

`CRIOMOS_VSCODIUM_CODIUM` and `CRIOMOS_VSCODIUM_NIX_STORE` replace the executables run during both launch and activation (`claude-lifecycle.sh:71-78`; `codium-launch.sh:34-38`; `codium-supervisor.sh:47-48`). The directory overrides redirect mutable state subject to canonical/direct-child checks (`claude-lifecycle.sh:26-64`). These are useful fixture seams and are not a privilege boundary for an already-compromised user, but inherited environment can cause unexpected code execution or mutation during an apparently ordinary activation/CLI call.

### P3: preserved VSCodium settings can retain dangerous Claude permissions

The settings merge is delegated to Hexis with declared keys but no blanket replacement (`modules/home/vscodium/vscodium/default.nix:316-356`). The current settings witness contains Claude permission-bypass keys not declared by this module. Whether those keys are an intentional user choice or an unsafe drift that should be removed is unresolved and requires the caller's authority; the code currently preserves them.

## Checks and proof boundaries

- `checks/vscodium-casual/default.nix:1-22` is exposed by `flake.nix:541-544` and checks the six disable flags plus selected settings by grepping source and the generated wrapper. It is a change detector, not runtime behavior proof.
- `checks/vscodium-claude-lifecycle/default.nix:1-276` evaluates the Home Manager module, package identity, pinned VSIX metadata, extension versions, and activation ordering. Its runtime derivation (`:277-1210`) uses fake Codium and fake Nix-root executables, then exercises path rejection, unprivileged roots, bootstrap, missing roots, legacy indirection, registry migration, stale-root replacement, contradictory recovery, collisions, shared/exclusive leases, direct same-cgroup launch, CLI exit/status forwarding, registry rollback, malformed manifests, and signal cleanup. It does not run real Codium, a real GUI, or a real Home Manager activation, and it does not cover raw Codium bypass or SIGKILL survivor behavior.
- `checks/agent-intercom/default.nix:84-115`, `:130-159`, and `:182-190` evaluates local capability selection and asserts that the Claude extension embeds the direct pinned Claude binary rather than an Agent Intercom wrapper. The VSCodium assertions are source-text checks; the broader check runs unrelated broker/CLI fixtures.
- `modules/home/desktop-database.nix:19-24` contributes the activation-time MIME cache refresh; it has no Codium-specific behavioral check. There is no repository-defined Codium systemd service or service-specific check.

The lifecycle check is durable and unusually broad, but the source-grep portions do not satisfy the testing doctrine's behavioral-proof standard by themselves. The untested paths above remain unknown rather than verified safe.

## Unresolved authority and unknowns

- Whether every Codium launch must pass through the managed wrapper, including an already-running GUI and desktop action, is an authority decision not settled by the code.
- Whether preserved Claude permission-bypass settings are authorized user state or a security defect is unresolved.
- Whether activation should wait, retry, or fail visibly when a GUI SH lease exists is not settled by the brief.
- The exact Codium flags supported by the pinned build and the precise upstream `--list-extensions` filesystem behavior were not executed under the no-launch constraint.
- No current witness proves extension-host activity, raw process start provenance, or whether the retained recovery directory is safe to remove.
