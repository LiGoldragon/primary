Model-context boundary observed:

- Orca has no provider-model API or transcript-item construction in these paths. Normal `send` persists body/payload in SQLite, then the idle push carries only a PTY pointer. The actual body appears only when the recipient agent invokes `orca orchestration check`; at Orca's boundary this is RPC/CLI output, not a system/developer message or synthetic transcript item.
- `dispatch --inject` is different: the entire preamble/task spec is pasted into the recognized agent's interactive PTY and submitted with CR. At Orca's boundary this is new terminal input intended as a new agent prompt. Because the source does not own provider transcript roles, whether a specific provider records that as a user message, harness item, or another role is not observable here.
- Normal mailbox push is explicitly bottom/new-turn gated by idle status; a busy recipient gets no PTY write. `dispatch --inject` is documented to be used after `tui-idle` (`skill-guides/orchestration.md:379`) but the handler/runtime do not enforce idle, so a caller that violates the precondition can write into an active TUI; provider behavior then remains unknown.
