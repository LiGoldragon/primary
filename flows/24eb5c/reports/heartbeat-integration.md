## One proposed integration into this version

### Existing event and state boundaries
1. `sending.rs:319–348`, after successful ordinary request admission: sender/recipient Address, immutable request identity and admission time are known. `store/logical_delivery.rs:1241–1405` atomically appends the recipient queue and delivery records; `:1397–1398` commits and announces. Use this committed domain change, not mere announcement count, to mark the affected **recipient** changed. Sender attribution is not permission to wake every sender or global subscriber.
2. `reporting.rs:62–83` records harness events; `:86–174` applies correlated events. These can settle heartbeat input receipts but are **not proposed eligibility triggers in this first patch**: current raw Started/Stopped events do not reliably distinguish work caused by heartbeat from unrelated work. General lifecycle-triggered heartbeat would first need causal attribution; that prerequisite stays explicit.
3. `store.rs:3153–3190` LaunchChanges is an existing condition-variable notification, not a typed domain event. Its counter changes for deliveries too. Reuse it only to awaken existing queue/recovery processing after committed pending evidence; never use its number as heartbeat eligibility or a message metric. No new timer, periodic scan, or global event framework.
4. `observe_agent.rs:131–155` already offers per-pane Herdr event subscription; this is request-scoped, not an authoritative always-running census. Do not synthesize missing global working counts from Awake rows.

### Missing abstraction and minimal stored carriers (proposed)
A **recipient evidence record**, keyed by Address, holds latest relevant ordinary-change sequence, last natively received snapshot/baseline, latest coalesced snapshot, and optional outstanding logical-delivery identity. A **traffic-purpose record**, keyed by the existing private logical identity, distinguishes ordinary traffic from generated heartbeat. These are new Memory types, not labels inferred from message wording. A pending sequence must be attributable to an ordinary committed admission; heartbeat queue/counter/receipt changes never increment it.

A small operation on this record marks changed evidence after ordinary admission, another materializes the pending snapshot through existing delivery, and native receipt settlement advances its baseline. These are additions to the existing Operation/Memory specifications, not a new Nexus or event framework. Admission and purpose assignment must be atomic; crash recovery must not lose provenance or duplicate an outstanding notification.

Keep the reminder a `Soft.Notice` from existing `SentBy::Flow`, with snapshot and the instruction to judge echo chambers, increasing jargon/nonsense and acknowledgements of acknowledgements. Existing Notice.String is the textual carrier, rendered from the typed evidence record; it grants no new ACK grammar. The Nexus supplies evidence, recipient judges sanity.

**Recursion boundary:** first-patch eligibility is only committed ordinary admissions from non-Flow origin; generated heartbeat is Flow-origin and purpose-marked. All heartbeat scheduling, native receipts and resulting harness status reports are non-eligible. An ordinary response to heartbeat must not qualify solely because its recipient/sender counters changed. Current generic Notice has no typed answer correlation; suppress eligibility while processing that heartbeat turn only where existing native-turn identity proves that provenance. If this origin cannot be proved at an admission boundary, reliable response exclusion needs an explicit causal-purpose carrier: a prerequisite to implementation, not a string-matching shortcut. Primary must judge this gap before authorizing a patch; otherwise the no-self-sustain acceptance is unproved.

### Coalescing and delivery insertion points
Use one pending record per recipient, not one queue entry per change. At the existing queue-selection/drain boundary in `waking.rs` (typed runs `:2397–2462` and reconciliation `:2465–2478`), materialize latest pending evidence only if no heartbeat is outstanding. Queue it with `store.accept_logical_delivery`, already used for Flow-origin notices in `reminding.rs:60–65`, then reuse existing wake/drain behavior.

Repeated relevant changes update pending latest evidence while one delivery is outstanding; unchanged relevant snapshot produces nothing. An already-submitted immutable payload is never rewritten. Its eventual receipt can release at most one merged follow-up containing newer ordinary evidence, not one per change. No follow-up is justified by the heartbeat's own counters or receipt. This explicitly distinguishes coalescing pending evidence from changing bytes already in a native prompt. If Primary requires a single notification containing even changes arriving after submission, that cannot be guaranteed by this version's immutable input; it is a stronger requirement than this sketch.

Selection belongs under existing dispatch/queue synchronization; materialization must not reacquire a held dispatch/write gate recursively. Exact helper extraction and atomic commit composition require patch design approval; do not call the public accept function from inside its own write lock.

### Count meanings and authoritative ownership
All numbers are observations at one named evidence cut; unavailable data is `Unavailable(reason)`, never zero. Proposed snapshot carries observation sequence/time, recipient and prior baseline sequence, so scope/window is explicit.

* **Awake metaflows:** count State.Awake from `FlowStore::list_metaflows` (`store.rs:5083–5094`), scoped to this NEXT Memory. This says nothing about currently Working panes. Existing method rejects a changed read view rather than mixing snapshots.
* **Working panes:** only actual pane states observed through Herdr (`observe_agent.rs:131–155`), keyed/deduplicated by native pane identity with observation time and coverage. There is no stored authoritative complete census in this inspected path. Report unavailable for cluster-wide total; a known-pane subtotal must say its coverage and age. A complete metric is a prerequisite if Primary requires it, not a poller added here.
* **Messages:** label the available metric **ordinary admitted logical requests**, deduplicated by logical identity, between previous received baseline and current evidence sequence, scoped to this Nexus (or the recipient explicitly). Count committed admission records (`logical_delivery.rs`), excluding heartbeat. It is not messages consumed, and send-attempt outcome counters (`store/send_outcome.rs`) also include refusals/retries. Existing allocation counters are not message totals. If the display must literally mean sent/consumed, those must be separately defined from native receipt records, with unavailable evidence retained.
* **Queue growth:** current outstanding ordinary queue membership for this recipient minus membership count at its prior received heartbeat baseline; signed delta, same queue-state definition and filtered purpose on both cuts. First observation has no prior baseline, hence growth unavailable. A drained queue can yield a negative delta. Heartbeat membership is excluded.

Counts alone never confer eligibility. Unrelated admissions can change global totals but cannot mark this recipient changed. Atomic/sequence-consistent evidence read is required; mixed unrelated read snapshots are not a single claimed instant.

### Receipt versus consumption
Acceptance means committed Queued (`logical_delivery.rs:1399–1404`). Submission means native transport accepted; neither means the model consumed it. Reuse existing `reporting.rs:166–169` correlated PromptSubmitted and `waking.rs:1240–1262` session+digest correlation; `find_receipt` (`:2316–2382`) checks exact Claude input history or Codex queued turn history; `settle_received` (`:1210–1237`) records native receipt and settles delivery.

Those are native-input receipt witnesses, not an invented model ACK. If transcript/session/digest correlation is unavailable, keep outstanding/unknown under existing uncertain-delivery policy; do not infer receipt from a timeout, Idle, stop event alone or delivery acceptance, and do not repeatedly emit replacement heartbeats. Acceptance testing additionally reads the actual recipient's next response/transcript to establish that it reacted to the heartbeat; this is test evidence, not a new production ACK protocol.

### Minimal runtime/meta boundary and version impact
Proposed one Heartbeat configuration family through existing `Configure`/`Configuration`: explicit enabled recipient Addresses (initially only the one sanctioned test recipient), which ordinary admission events qualify, and reminder text/template. Default disabled; no timer interval. Primary layers need not be enabled. New typed family/snapshot fields change meta-signal-flow's wire contract and require matching meta clients and a contract version change. New Memory records require declared schema/version registration and empty/default migration for old stores; existing evidence survives refresh/restart.

No ordinary signal change is needed merely to render existing Flow Soft.Notice. However, reliable exclusion of heartbeat-caused outgoing responses may require causal-purpose propagation absent from existing generic Notice/session admission; if so, ordinary contract/client/harness changes must be separately identified and approved. No claim of zero ordinary-wire impact until that gap is resolved. This is the smallest explicit missing boundary, not authority to create a general causal-event system.
