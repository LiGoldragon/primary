## Summary

- **afc2ca: the mechanism is shown by the code and the rollout together.** Three MiddleAbrupt letters were steered into its running turn T1 [obs rollout]. Each steer set the thread to `Delivered`, which drops T1's id [obs code]. When the HardAbrupt was typed, `delivered()` found the thread `Delivered` rather than `Running`, so it recorded no cut turn [obs code]. On every one of Flow's connections, T1's `turn/completed` precedes T2's `turn/started` [inf source]. The state machine reads an interrupted completion that arrives with no cut turn recorded as rest [obs code]. Which connection Flow applied first is [unk]. Section 4 traces this.
- **0e068b and 28c285: the cause is not established.** The code gives two first-turn paths (F2, F3) that produce a false rest within about a second of the first turn's start [inf]; both depend on Flow's arrival order [unk]. Both come from one gap: the launch's own `turn/start` is never entered into the turn tracker [obs code].
- **The fault spans two layers:**
  - One state, `ThreadTurn`, mixes up "a turn is open" with "a letter is pending" [obs code].
  - A snapshot from one connection, applied late, can overwrite a turn another connection already reported [inf].
  - Closing a Codex seat ends the pane and nothing in the app-server [obs code].
- **The sleep fix is Flow code plus one meta contract addition.** The addition is the Configure value `EndedTurnRetention` (§2.3). It can ride meta 83 together with the signal-flow 64 re-pin. None of the Flow files the fix touches is touched by pko0-90d453, w0f8-90d453 or the release's adapter. It does collide with `context-warnings-7cd167` inside `settle_rested`.
- **Caller-bound Refresh needs a contract change.** It adds a new `RefreshRejection` variant in signal-flow, which makes signal-flow 64. meta-signal-flow re-exports that type, so it must re-pin to 64.

## 2. Event-to-rest semantics

### 2.1 As built

`ThreadTurn` is one of `Unknown`, `Running(Option<turn>)`, `Delivered` or `Resting`, one per thread, held in memory (`codex_turns.rs:52-63`). `TurnObservation.rested` is `!was_resting && now Resting && settles` (`:326-329`). All of this is [obs code].

| Event | State before | State after | Code |
| --- | --- | --- | --- |
| `Started(t)`, t not among ended | any | `Running(Some(t))`; a cut turn with no id is forgotten | `:247-261` |
| `Completed/Interrupted(t)`, not late | `Running(Some(t))`, **`Running(None)`, `Delivered`, `Unknown`, `Resting`** | **`Resting`** | `:287` |
| `Status(Idle)` | **`Unknown`, `Running(None)`**, `Resting` | **`Resting`** | `:291-301` |
| `Resumed(Idle)` | anything except `Delivered`, **including `Running(Some(t))`** | **`Resting`** | `:302-313`, applied at `send_tool.rs:782` |
| `delivered(NotRequested)` | any | **`Delivered`** (the open turn's id is lost) | `:342-353` |
| `delivered(Observed/Unobserved)` | **`Unknown`, `Delivered`, `Resting`** | `Delivered`, **no cut turn** | `:351` |
| the launch's own `turn/start` | any | **unchanged: nothing is recorded** | `performing.rs:551-575` |

Every reader in §1 acts on `Resting`. `settle_rested` at `waking.rs:4025` closes on `refresh_due || ordered_now` **without consulting the turn**.

### 2.2 Correct: rest is "no native turn, item or letter open", from the app-server's own lifecycle

Principles:

- **One lattice per turn and per item: Unseen < Open < Ended.** Every input moves a fact up, never down. The merge is a join, so the result does not depend on Flow's arrival order (§2.4).
- **A turn ends only by native evidence:**
  - its `turn/completed`;
  - a consistent cut that shows it not running;
  - `thread/closed`.
- **A status notification never moves the ledger.** On one connection, `thread/status/changed` is sent immediately before the turn event that causes it [obs `bespoke_event_handling.rs:158/180` and `:190/193`, inf ordering]. It therefore carries nothing the next frame does not, and it is never a rest trigger.
- **A letter is pending until a receipt names it.** No turn start takes a letter.
- **Process-backed items outlive their turn.** A `commandExecution` whose unified-exec process is still alive is completed by an exit watcher that may fire after its turn ended or was interrupted (§5, N9–N11) [inf].
- **Nothing is inferred from the pane or from a timer.**

The rules apply one event at a time, under the dispatch gate. "Below the watermark" means an id not held in `OpenTurns` or `EndedTurns` with `t ≤ EvictedThrough`.

**Turns**
- `TurnOpened t`:
  - t in `EndedTurns`: nothing changes.
  - t below the watermark: `Unreconciled`, `Reconcile`, `RetentionExceeded t`.
  - Otherwise t joins `OpenTurns`.
  - **No letter is taken.**
- `TurnClosed { t s }`:
  - t below the watermark: `Unreconciled`, `Reconcile`, `RetentionExceeded t`.
  - Otherwise t leaves `OpenTurns` and joins `EndedTurns`, whatever `s` is.
  - Every `TurnBound` item of t ends with it. The app-server emits `TurnComplete` after the task loop has finished, and `TurnAborted` after `task.handle.abort()`; neither emits item ends for in-flight tool calls (`tasks/mod.rs:921-1010`) [obs code, inf]. `ProcessBacked` items of t stay open.
  - If `EndedTurns` exceeds the bound, its least TurnId is evicted and `EvictedThrough` becomes the greater of itself and that id. `EndedItems` of the evicted turn are dropped.

**Items**
- `ItemOpened i`:
  - Its turn is ended and i is `TurnBound`: nothing changes, because a late start from another connection names an item that already ended.
  - i in `EndedItems`: nothing changes.
  - Its turn is below the watermark: `Unreconciled`, `Reconcile`.
  - Otherwise i opens.
  - A `commandExecution` is `ProcessBacked` when its `processId` is set and no `item/completed` came in the same frame batch; it is `TurnBound` otherwise. The app-server stores the process when it is still alive after the initial yield (`unified_exec/process_manager.rs:596-628`) [obs code].
- `ItemClosed i`: i ends. A `ProcessBacked` i joins `EndedItems`.

**Letters**
- `LetterTyped`: the letter is appended. Nothing else changes.
- `LetterReceipt { a t i }`: letter a is taken.
  - The receipt is a `userMessage` item, in `item/started`, `item/completed` or a cut's page items, whose `content` is exactly one `text` input equal to a's `PayloadText`. This is the same predicate Flow already uses, `carries_user_text` (`codex.rs:314-333`). The item's `turnId` and `id` become the `NativeReceipt` (`NativePromptId` = item id), and the queue attempt moves to `ReceiptRecorded`.
  - Two pending letters with the same text are `Ambiguous` (existing `Undecided`) and both stay pending.
- `LetterSettled a`: letter a leaves. This happens only when the existing queue record leaves `Prepared`/`Uncertain`:
  - by an `AbsenceProof` (`HandOverRefused`, `HistoryAbsent`);
  - by an explicit `ResolveQueueDelivery`, which the meta contract already has, with a reason and a resolver.
  
  An unseen letter is `AbsenceUnprovable`, as the code already rules (`waking.rs:2941-2945`), and stays `LetterAwaited`.

**Cut**
- `Cut { status turns }`. The page is the newest turn (`initialTurnsPage { limit 1 sortDirection desc itemsView full }`).
  - Each listed turn that is `InProgress` opens.
  - Each listed turn with any other status ends.
  - Every open turn `t` less than a listed turn ends, because one turn is active at a time (`session.rs:92`, `active_turn: Mutex<Option<ActiveTurn>>`) [obs field, inf].
  - Every `TurnBound` item of an ended turn ends.
  - Open turns greater than every listed turn are kept. These are the turn/start answer that the listener has not yet processed (F2), and turns started after the cut whose events arrived first on another connection.
  - `status` is recorded and moves nothing else.
  - Items of the listed turn: `userMessage` items are receipts; work items open or end by their status.
  - The ledger becomes `Established`.
- `BackgroundTerminals ps`, read after a `Cut` on the same subscription: each listed process with no ended item opens a `ProcessBacked` item, attributed to the newest turn. This input opens items and never ends one.
- `SubscriptionEnded`: `Unestablished`, `Reconcile`. Flow opens a new subscription, and its `Cut` re-establishes the ledger. The app-server disconnects a slow connection when its outbound queue fills (`transport.rs:160-166`) [obs], so a gap in a stream always surfaces as a connection end, never silently.
- `ThreadClosed`: every open turn ends, and every `TurnBound` item ends. `ProcessBacked` items move to `ItemsOrphaned` and stay open (see "thread/closed, natively" below).

**Rest**
- **Rest is `AtRest` alone.** `settle_rested`, `rests_for_closing`, `rests_now`, Confirm and the restart path all read `ThreadStanding`. `RestReached` is the only settlement trigger, and settlement re-reads the standing under the gate.

#### thread/closed, natively

- **When it is emitted.** `thread/closed` is emitted from `unload_thread_without_subscribers` (`app-server/src/request_processors/thread_lifecycle.rs:416-470`), and only on `ThreadShutdownResult::Complete` (`:451-456`). On `TimedOut` the thread stays loaded and nothing is sent (`:463-466`) [obs].
- **Its preconditions.** No connection is subscribed and the status has not been `Active` for the unload delay (`:56-63`). The agent is not `Running` (`:369-372`) [obs]. A running turn or a pending approval or user-input request makes the status `Active` (`thread_status.rs:447-468`) [obs]. **A background terminal does not** [obs: `RuntimeFacts` has no process count]. While Flow's responder is subscribed, the thread is never unloaded this way [inf].
- **What shutdown does first.** `Shutdown` runs `shutdown_session_runtime` (`core/src/session/handlers.rs:287-322`):
  - `abort_all_tasks(Interrupted)` at `:298`: every turn task is aborted.
  - `unified_exec_manager.terminate_all_processes()` at `:309`: every stored process is drained from the store and sent `terminate()`. For a local process that is a synchronous kill request; for an exec-server process it is a spawned task. The exit is not awaited (`process_manager.rs:1796-1811`, `process.rs:246-257`) [obs].
  
  `ShutdownComplete` follows (`:338-380`).
- **What happens to item events.** The listener loop `break`s right after it starts the unload (`thread_lifecycle.rs:384-394`), so events raised during shutdown (`TurnAborted`, exit-watcher item ends) are not relayed to any client [obs, inf]. Before `thread/closed`, `remove_thread` publishes `notLoaded` (`thread_status.rs:333`) [obs].
- **What becomes of each kind of fact:**

| Fact before `thread/closed` | Native fate | Ledger | Mark |
| --- | --- | --- | --- |
| an open turn | none should be running (precondition); any racing one is aborted by `abort_all_tasks` before `ShutdownComplete` | ends | inf |
| a `TurnBound` item | its task future is aborted with its turn | ends | inf |

### 2.3 Ended-turn retention

**What `EndedTurns` is for.** It recognises a repeat: a turn's start or end that reaches Flow after the turn already ended in the ledger. Repeats come from one of two sources:
- a second connection;
- the `turn/start` answer, which can arrive after the turn's `turn/completed` on the subscription.

**The watermark.** Codex turn ids are UUIDv7 ("Codex-generated turn IDs are UUIDv7", `Turn.id` in the schema [obs]). Core makes them with `Uuid::now_v7()` (`core/src/session/mod.rs:1073-1079`) [obs], and `turn/start` takes no client turn id [obs schema]. So a turn started later has a greater id [inf]: within one millisecond, ordering depends on the uuid crate's v7 counter [unk]. `EvictedThrough` holds the greatest evicted id. An unknown id at or below it is ambiguous: an old turn's late repeat, or a start Flow never saw. The ledger then goes `Unreconciled` and asks for a `Cut`. A same-millisecond tie, or a system clock stepping backwards, can only cause an extra `Cut`, never a wrong rest.

**Bounds:**
- **Correctness minimum: 0.** With the watermark, every value is correct: the ledger never treats an evicted repeat as a fresh turn, and never drops a fresh turn as a repeat. The bound trades memory for reconciliations.
- **No reconciliation for the orderings in §4: 1.**
  - afc2ca has one connection, and T1's end and T2's start are adjacent.
  - F2 and F3 report T1 on two sources (the `turn/start` answer, and the responder or the launch connection), and no turn ends in between.
  
  A repeat of turn t arrives after at most the turns that end between t's first and last report across Flow's sources. That is 0 or 1 in every §4 ordering. How far a stalled responder can lag is Flow's arrival order [unk], so a larger value buys margin.
- **Seed: 64.** It costs about 64 × 36 bytes per live thread.
- **When the bound is exceeded:** the event that reaches below the watermark sets `Unreconciled`, `Reconcile` and `RetentionExceeded t`. Flow logs `RetentionExceeded { flow thread turn bound }` to its journal and takes a new `Cut`. The seat is never `AtRest` while `Unreconciled`. History that fell below the watermark is therefore never presented as rest; it costs one `Cut`.
- **Refusal:** a negative value is refused.

The value is a Configure value in the meta contract, following `RequestIdDraws.DrawBound`. Memory seeds it the way `SEEDED_REQUEST_ID_DRAWS` seeds `DrawBound` (`store.rs:1714`), and a declaration replaces it.

```ethos
; meta-signal-flow 83.0.0 (on 82.0.0, recovery-text-82-bdb323 570b173): ended-turn retention is configuration
TurnRetentionBound.Integer                 ; ended Codex turn ids one thread ledger keeps, 0 or more; seeded 64 in a new Memory
ConfigurationChange.[ ; … every variant of 82, unchanged …
                      EndedTurnRetention.TurnRetentionBound ]       ; one value, replaces the committed one
ConfigurationSnapshot.{ ; … every field of 82, unchanged …
                        ConfiguredEndedTurnRetention.TurnRetentionBound }
ConfigureRefusal.[ ; … every variant of 82, unchanged …
                   EndedTurnRetentionRefused ]                      ; a negative bound
```

A change applies to every ledger at once. A ledger holding more than the new bound evicts down to it, and its watermark rises.

### 2.4 Proof: no newer event is lost or overwritten

**Assumptions**, each with its evidence:
- **A1. One connection is FIFO.** On one connection, the app-server delivers every notification and response in the order its thread listener emitted them. Each thread has one listener loop that relays core events in order (`thread_lifecycle.rs:278-360`) [obs]. All of them go through one `mpsc` (`outgoing_message.rs:741-790`) into one routing loop (`transport.rs:203-240`), and each connection has one FIFO writer queue (`transport.rs:140-175`) [obs]. A1 is [inf].
- **A2. The resume answer is a cut.** For a loaded thread, the `thread/resume` answer is built and the connection subscribed inside that listener (`SendThreadResumeResponse`; comment `thread_state.rs:61`: "atomically subscribing for new updates"; `thread_lifecycle.rs:484`, `:566`, subscription at `:706`) [obs]. So every event emitted before the answer is reflected in it, and every event after it reaches that connection after it [inf]. The page's non-`InProgress` statuses, synthesized ones included, are evaluated from the listener's own state at that point: they mean "not running at the cut" [inf, `thread_lifecycle.rs:599-660`].
- **A3. A cold resume.** For a thread that is not loaded, the subscribing resume loads it, and no turn can run before the load [inf].
- **A4. One active turn per thread** (`session.rs:92`), and later turns have greater ids (§2.3) [inf].

**Proof:**
1. Each fact is a value in a finite chain: Unseen < Open < Ended. Every rule moves a fact to the join of its value and the evidence. The join is commutative, associative and idempotent, so for a fixed set of evidence the final ledger is the same in every arrival order. This includes events from other connections arriving before or after the cut, and the `turn/start` answer arriving at any point.
2. **No newer event is lost.** By A1 and A2, any event emitted after the cut arrives on the subscribing connection after the cut answer. A connection that ends sets `SubscriptionEnded`, and the next subscription's cut covers the gap. So every event emitted after the latest cut is applied.
3. **No newer event is overwritten.** A cut can end a turn only in two cases:
   - It lists the turn not `InProgress`. By A2 the turn was not running at the cut, and it cannot run again: a turn id names one turn.
   - It lists a greater turn. By A4, the lesser turn was not active at the cut.
   
   An open turn that is greater than everything listed is never ended by the cut. Such a turn started after the cut, or was handed to Flow by `turn/start` before the listener saw it.
4. **Retention.** Eviction cannot cause an overwrite: an id at or below the watermark goes to `Unreconciled` (§2.3), never to Ended or Open.
5. **Statuses.** `thread/status/changed` moves nothing, so a stale status from any connection overwrites nothing.

**Why `thread/turns/list` is not used to close turns.** It is served by the request processor, not the listener. It reads the rollout, `agent_status`, the watch status and the active turn at separate moments (`thread_processor.rs:3073-3150`) [obs]. When the status it reads is not `Active`, it rewrites `InProgress` to `Interrupted` (`:5811-5825`) [obs]. So a turn that has just started can be listed `interrupted` [inf; whether core sets `agent_status` before the rollout write is [unk]]. Flow's delivery reconciliation may keep using it to find receipts (`codex.rs:1360-1455`), because a receipt only moves a letter up.

## 3. Sleeping a Codex flow whose turn is still open (for Psyche, through Astra)

Today a sleep closes the pane only (`waking.rs:3608-3626`) [obs code]. The app-server thread runs on with no pane (sol-succession.md finding 5) [obs].

### Option A: sleep only at rest

- **What it does.** An OnDemand Codex seat is closed only when the ledger stands `AtRest`. Any other standing keeps it, and the sleep is taken at the next `RestReached`. The `refresh_due || ordered_now` arm at `waking.rs:4025` stops applying to Codex.
- **Consequences:**
  - A turn is never cut. This matches vision flow-nexus:275.
  - A turn that never ends, a background terminal that never exits, or a letter whose receipt never comes keeps the seat Awake. Ending such a seat stays an explicit act: Stop, Restart, `ResolveQueueDelivery` for a letter, or option B as an operation.

### Option B: interrupt, await the end, then close

- **What it does.** For each open turn, Flow sends `turn/interrupt { threadId turnId }`. It awaits `TurnClosed { t Interrupted }`, or the refusal `no active turn to interrupt` (seen by n9y8 for an ended turn [obs]). Then it closes.
- **Consequences:**
  - Work in flight is cut mid-step, with no handover. This contradicts vision line 275 for a refresh.
  - **An interrupt does not end background terminals.** The process is stored before the initial yield "so interrupting the turn cannot drop the last Arc and terminate the background process" (`process_manager.rs:596-597`) [obs comment, inf]. Ending them needs the experimental `thread/backgroundTerminals/terminate` or `clean` (`app-server-protocol/src/protocol/common.rs:737-753`) [obs]. Whether either awaits the exit is [unk] (P3).
  - It needs new Emissions in `crates/flow-nexus/ethos/emission.ethos`.

Either option could be one configured value per permaflow. That is part of the same ruling, not decided here.
