01 The whole, one pass

Three things reach this Nexus: a living person through the flow CLI, the Message Nexus daemon connecting to the same socket directly, and a marker file on disk that flow-id writes and the Nexus later reads. Each box names the repository it comes from.

Default configuration is hard-coded in the executable: store /home/li/.local/state/flow/flow.sema, Codex control socket /home/li/.codex/app-server-control/app-server-control.sock, model gpt-5.6-terra, timeout 10s. observed What the vision says it is for, and what the code does

Vision/flowNexus.md:5-7: "The Flow Nexus sets up and starts a model flow: its working directory, system prompt, training files and instruction prompt." And :11-13: "A Nexus component decides the system prompt and everything about a launch, replacing the harness's subagents with specialized harnesses launched with specialized system prompts."

In code, the whole of launch is one hard-coded flow_type string "codex-medium" mapped to one hard-coded goal sentence, and anything else refused. No system prompt, no training files, no skill provisioning, no Claude launch path. The working directory is created by the Codex child's environment. The largest live use of the component is instead ResolveRecipient, which the vision file does not mention at all.

Grounding §7a · flow-nexus/src/lib.rs:40-44 · flow/README.md:74-76

observed Polling instead of subscription — and parking instead of reaping

Vision/nexus.md:117-125: "State is observed by subscription … Polling is forbidden; a correct system goes quiet when nothing changes." There is no subscription surface in either ethos — every response is a one-shot reply to a one-shot query. Resolution polls on every request: it forks herdr … api snapshot as a subprocess and re-reads state.json, roster.json, /proc/<pid> and two socket paths. flow/README.md:43-46 states this as the intended behaviour: "Claude resolution rechecks the job state, daemon roster, rendezvous socket, control socket, and worker process on every request."

Beside it, Vision/flowNexus.md:29-32: "A replaced session is reaped by the refresh itself … so a dead end is never left registered and addressable." In code there is no reaping. Stale bindings are parked: refresh_route sets HerdrRouteSelection::Unavailable and downgrades the endpoint to RouteReadiness::Parked while leaving the row; claude.rs does the same. The row stays registered and stays resolvable.

Where Flow Nexus sits among the messaging layers

The messaging skill draws four layers: Herdr 0.8.2 as transport, Hacky Messenger as "the live compatibility bridge … a bridge, not Flow Nexus or Message Nexus", Flow Nexus 0.3 as "the identity and resolution design" that "does not itself prove transport or durable delivery", and Message Nexus 0.12 as installed for durable attempts and receipts. The code matches that drawing, with one asymmetry.

observed Message Nexus does consume Flow Nexus

message/Cargo.toml:49 pins signal-flow at exactly the revision this report read — the peer depends on the wire type repo, never on the flow crate. FlowResolver::resolve connects to /run/user/1001/flow/flow.sock, sends ResolveRecipient, and maps RecipientResolved → Some(node), RecipientResolutionRejected → None. Its delivery trait holds the receipt grade honestly: "Accepted records transport submission only. It does not claim that the target harness consumed, interpreted, or completed the submitted message." This is flow/DESIGN.md:39-42: "Message Nexus consumes that typed reply instead of maintaining a second identity registry." §6 · nexus_delivery.rs:1-3,26-85

observed, by absence Hacky Messenger does not

/home/li/primary/tools/hacky-messenger/ contains no match for flow.sock, ResolveRecipient, FLOW_SOCKET, flow resolve, or flow-meta. It calls herdr directly and keeps its own registry with its own conflict rule — "Flow already registered to a different terminal; retire its registry file explicitly". So the bridge in live use maintains precisely the second identity registry that DESIGN.md says Message Nexus avoids: the bridge bypasses the resolution component, while the durable component that does use it is behind it in the stack. §6 · hm.py:27-163
