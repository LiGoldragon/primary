knowledge:compaction · mind-belief › knowledge/compaction.md

Mostly measurement and citation, but its core bears on psyche: neither harness keeps the living's words whole through compaction.

Compaction replaces the active conversation history with a smaller continuation context. Earlier records remain in the transcript; their presence on disk does not mean they remain in the next model request.

Verified on 2026-10-13 against installed Claude Code 2.1.294 and active Codex 0.161.0-alpha.2. Source behavior below belongs to those versions. Measurements belong to the named sample, not every session or model.

Claude Code

Mechanism. The normal cached-prefix summarization path makes a forked model call with tools denied and maxTurns: 1. It normally uses the configured main-loop model. Retry, fallback-model and media-stripping paths also exist: one successful summary does not establish that only one request was made, that the same model always wrote it, or that every original input was passed unchanged. Manual and automatic compaction are both recorded.

What is summarized. Selected earlier conversation messages become a readable text summary. The installed program contains several summary formats, not just one fixed template. One format requests nine sections, including user messages, decisions, files, errors, pending tasks and current work. All four inspected summaries used that nine-section format. Asking for all user messages does not itself preserve their complete text.

What is retained or restored. A preserved tail can remain alongside the summary. In the four inspected boundaries it was the last assistant text reply and its duration record. Earlier tool calls, results and thinking were not listed in that preserved tail. The program also restores selected context separately: recently read files, invoked skills, a plan where present, task status and other attachments. File restoration selects up to five recent eligible files, reads them again from disk, and applies a 5,000-token per-file limit and a 50,000-token aggregate limit. Invoked-skill restoration applies 5,000 tokens per skill and 25,000 total, with recently invoked skills considered first. It can truncate or omit bodies; it does not guarantee every loaded skill is restored verbatim.

In the inspected session, each of the four boundaries restored the same 21 skill bodies, totaling 43,761 characters, and two to four file-content attachments plus file-reference notes. The system-prompt snapshot was identical before and after each boundary. Instructions and tool configuration remained separate request inputs. Restored file content comes from a new read, rather than a promise that the earlier tool result is preserved unchanged.

Core study, reported 2026-10-16. Codex

Mechanism. In the installed version, the provider's compaction capability selects remote compaction or a local model-summary path. A separate token-budget mode starts a new context window without model/server summarization. These are different implementations. The observed current-version corpus used remote compaction with an encrypted result. In remote V2, the client sends conversation input, base instructions, tool specifications and a compaction-trigger item through its Responses stream, receives a compaction item, installs replacement history and recomputes context usage. Retries and model fallback are implemented.

What is retained. Remote V2 selects real user/hook messages and eligible inter-agent messages, then retains the newest selected content within a 64,000-token budget. The boundary message can be truncated and older messages omitted. Agent messages above the 10,000-token eligibility limit, descendant progress messages and final-answer notifications are excluded by the source filter. Client-authored developer messages are retained only when the corresponding feature is enabled. Initial context is inserted during mid-turn compaction or fully re-injected on a subsequent regular turn after standalone/pre-turn compaction. There is no source guarantee that every user or other-flow message survives verbatim.

What is replaced or summarized. Ordinary assistant messages, reasoning, tool calls and tool results are not selected as raw retained dialogue by remote V2. The server-produced compaction item carries encrypted_content; the inspected local records provide no readable text summary of its contents. Those records do not establish which individual omitted facts the server preserved. History outputs may also be truncated before a remote request if they exceed the available context.

The local-summary implementation instead produces a readable text summary and retains recent user text within a separate 20,000-token budget. Its existence in the installed source is not evidence that it ran in the inspected remote-compaction sessions.

Observable effect and cost. A read-only scan of the current Codex home's session files found 338 compaction records, all tagged CLI version 0.161.0-alpha.2. Every replacement history contained an encrypted compaction item; the records' plaintext summary field was empty. Aggregate replacement item types were messages, agent messages and compaction items, with no raw reasoning or tool-call/result items. Earlier transcript records remained present before those checkpoints.

Remote compaction is an additional server request, with input/output and cache usage recorded when supplied by the server. Compaction time and rebuilt context affect the continuation request. Token-budget compaction makes no summarization request. Automatic limits depend on model/configuration; this version's model limit is capped at 90% of its resolved context window. A particular observed trigger, retention percentage or next-request size is not a universal limit or price.

Core study, reported 2026-10-16. Measured on 355 compactions, the retained user text held near 260,000 characters across repeated compactions, matching the 64,000-token budget. A message larger than the budget lost its middle with no marker of the cut. This sample is separate from the earlier 338-record scan above and is attributed to Core’s study, not independently reproduced here.

Other harnesses and providers

OpenCode keeps the last two user turns within 2,000 to 8,000 tokens and summarises the rest. pi keeps about the last 20,000 tokens and rolls earlier ones into a summary of at most about 13,000. Anthropic's API compaction replaces everything before its compaction block with a summary and keeps no user message unless the caller keeps a tail. OpenAI's API compaction returns the user messages followed by one encrypted compaction item, with no stated cap.

These source summaries and limits are attributed to Core’s study supplied on 2026-10-16; this edit does not independently verify provider behavior or extend those measurements to other versions.

Codex: release tag rust-v0.161.0-alpha.2, codex-rs/core/src/{tasks/compact.rs,compact.rs,compact_remote_v2.rs,compact_remote_v2_attempt.rs,compact_token_budget.rs} and codex-rs/protocol/src/openai_models.rs; current-version session checkpoints. Exact source excerpts, transcript locations, measurements and the claim-by-claim verification are retained with this module's publication evidence.

Provider cache and quality boundaries

Claude API prompt caching defaults to a 5-minute lifetime and offers a 1-hour TTL. The lifetime starts at request start and includes generation time; reuse refreshes it without a new write charge. Claude's documented idle compaction shortly before one-hour expiry is optional and can be disabled; it does not describe ordinary automatic compaction as TTL-scheduled. OpenAI documents a 30-minute minimum TTL for GPT-5.6+ and earlier in_memory and 24h retention modes as typical inactivity and maximum periods. For GPT-5.6+, writes are 1.25x and reads are 0.1x on most models, with GPT-6.1 Sol reads at 0.05x; earlier generations have no additional write charge and model-dependent read rates. Neither provider documents an advance expiry warning. Matching an unchanged eligible prefix, model/cache scope, or warm session improves eligibility but does not guarantee a hit. An external-tool wait with no generation or API request adds no model tokens in that narrow accounting case; separate meters may apply, and API formulas do not automatically describe subscription charges.

Claude Code's documented compaction boundaries include 200K for Sonnet 4.6 and Opus 4.6 without extended context and about 967K for native 1M models. These are client defaults/configuration boundaries, not universal measured trigger counts. OpenAI Responses compaction is opt-in through context_management.compact_threshold, separate from cache retention. The source map, exact TTLs, accounting fields, and limitations are in [cache-compaction-research.md](../evidence/cache-compaction-research.md).

Long-context quality is task-specific. The 2025 NoLiMa study reports GPT-4o falling from a 99.3% short-context baseline to 56.0% at 128K on its retrieval task, with an 8K effective-length criterion. The 2025 LongCodeBench study reports Claude 3.5 Sonnet LongSWE success of 29%, 19%, 15%, and 3% at 32K, 64K, 128K, and 256K buckets, and GPT-4o 11%, 6%, and 5% at 32K, 64K, and 128K. These do not define a universal handover threshold.

Compaction replaces a thread's active history with a smaller continuation; the transcript on disk keeps everything, the next request does not. Claude Code keeps a paraphrased summary and the last few messages whole; Codex keeps user messages newest first within a budget and cuts the middle of a long one unmarked; the living's exact words outlive compaction only where a record holds them.

knowledge:orchestrate · mind-belief › knowledge/orchestrate.md

Locks are how flows coordinate edits; the exact request forms are needed.

Use orchestrate for ordinary requests. The installed wrapper supplies ORCHESTRATE_SOCKET; a direct client binary requires it.

Acquire a Lock. Its four positional fields are LockName, FlowId, LockPaths, and LockReason:

orchestrate 'Lock.{ <LockName> <FlowId> [ <absolute-path> ... ] <LockReason> }'

LockName names the work; FlowId is the owning flow's FLOW_ID; LockPaths lists the reserved absolute paths; LockReason states why. Put the actual owning FLOW_ID only in FlowId, never concatenated into LockName merely for uniqueness or title display.

Datom strings are in guillemets, «like this»; curly quotes and ASCII double quotes are not delimiters. A copyable multi-word reason example is:

orchestrate 'Lock.{ OrchestrateDocs 444e5e [ /absolute/path/to/file ] «Clarify Lock fields» }'

A single-word reason is bare.

Locked returns the complete Lock: its integer ID, name, Flow, paths, and reason. LockRejected is a typed refusal. Paths are absolute.

Release by the returned integer ID using the Orchestrate release request skill variable, substituting the integer for <lock-id>. Read the typed reply.

Released returns the complete Lock. ReleaseRejected is a typed refusal.

A lock whose holder has no live flow is stale: check the holder's six-character id against herdr pane list labels and flow 'Metaflows'; orchestrate 'Release.<id>' releases any lock by its number, whoever holds it, and a stale lock is released by whoever meets it.

Observe current Locks:

orchestrate 'Observe.Locks'

Observed carries one complete point-in-time Lock snapshot. It is not a subscription.

Treat a client failure as a failed operation.

Orchestrate holds path locks between flows. orchestrate 'Lock.{ <LockName> <FLOW_ID> [ <absolute-path> ... ] «reason» }' answers Locked with the lock's integer id, or LockRejected; orchestrate 'Release.<id>' releases a lock; orchestrate 'Observe.Locks' shows the current locks. A lock whose holder has no live flow, checked against herdr pane list and flow 'Metaflows', is stale and is released by whoever meets it.

knowledge:lojix · mind-belief › knowledge/lojix.md

Deployment safety rules matter; the fourteen-position field lists belong in the signal-lojix schema, not a module.

lojix-nexus owns durable state and two authority-tiered sockets. The ordinary contract is signal-lojix; the owner contract is meta-signal-lojix.

Use lojix on the ordinary socket for Query, WatchDeployments, WatchCacheRetention, and Unwatch.

Use lojix-meta on the owner socket for Deploy, Pin, Unpin, Retire, and Test. The owner contract is not optional.

Use LOJIX_ORDINARY_SOCKET and LOJIX_OWNER_SOCKET; neither socket has a default path.

Request syntax

Each public client rejects files, zero arguments, and extra arguments. A request root is one value.

A struct is brace-enclosed and positional, a vector is bracket-enclosed, a variant is a head with the period glued to both sides, and a variant carrying nothing is bare. None is bare and Some carries one glued payload. A string with a space or a delimiter is written in guillemets.

Deployment contract

Every deployment transport is explicit. Lojix uses the supplied Nix store URI and SSH destination verbatim; it never derives a route from cluster, node, or user names.

The logical node selects what is built; the activation destination selects which machine is changed. Before a state-changing deployment, verify that they identify the same node. If they do not, stop.

A CompleteHost deployment uses an explicit root-privileged Nix store URI and SSH destination.

A UserEnvironment deployment uses an explicit user-scoped Nix store URI and SSH destination.

When a deployment directly names a target pair, use it without asking for a second transport confirmation. Otherwise derive the canonical internal hostname as <node>.<cluster>.<internal suffix> from Horizon cluster data and use it as the host in the required CompleteHost or UserEnvironment Nix store URI and SSH destination. If the supplied or derived pair is invalid, report it rather than substituting another route.

A deployment proposal must be an existing absolute regular non-symlink horizon-definition.datom file.

Use RequireImmutable when production deployment must identify one exact source revision. Push producer revisions before pushing the consumer revision that pins them.

A Current generation is Lojix's committed state. It does not establish the target's live Nix profile or runtime links.

A terminal activation failure can follow a partial target change. Inspect the target profile, runtime links, and activation journal, then report Lojix state and live state separately.

What the break-even expression measures

With the final answer held common, the study's visible-text comparison defines:

  • C: direct main call text; O: its results; A: other avoidable main text.
  • B: child brief; R: returned text; H: additional parent-side envelopes, notifications, followups and polling.

Under those definitions, the delegated parent package is smaller exactly when C + O + A > B + R + H. This is an accounting identity in the chosen units, not a rule about when to delegate. The verified case tables use characters; applying it to tokens requires token measurements for those same terms and a return that answers the task adequately.

Total reported-token comparison instead includes every parent and child request.
