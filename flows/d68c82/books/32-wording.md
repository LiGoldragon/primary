# How a presentation is worded

```
 one response from a flow
     |
     v
 +------------------------+
 | its type               |
 | vision, intent,        |
 | knowledge,             |
 | compensation, inquiry  |
 +------------------------+
     |
     v
 +------------------------+
 | the presentation       |
 | plain words, one view  |
 | at a time: what you    |
 | read                   |
 +------------------------+
     |
     v
 +------------------------+
 | the technical part     |
 | files, paths, commits, |
 | branches: what         |
 | machines read          |
 +------------------------+
```

A book reads like a picture book about a hard idea. One view, then the next. Nothing on the page asks you to look past it.

## Proposal 1: no noise

File: the vision of books

+ A presentation to the living is plain and non-technical: one simple view at a time, nothing that distracts from it. Every technical reference sits apart, in the technical part.

Ruling: land, amend, or reject.

## Proposal 2: every answer is a presentation

File: the vision of books

+ Every response a flow gives the living is a presentation, typed by what it carries: vision, intent, knowledge, compensation or inquiry.

Ruling: land, amend, or reject.

## Proposal 3: the shape of a presentation

File: the presentation type in Ethos

```
- Presentation.{ Title }
+ Kind.[ Vision Intent Knowledge
+        Compensation Inquiry ]
+ Presentation.{ Kind Title Body
+                Technical }
```

The type comes first. The body is what you read; the technical part is what machines read.

Ruling: land, amend, or reject.

## Proposal 4: the book rule that made the noise

File: the rules for writing books

```
- Its only operational fact is whether
- the work is on the production or a
- development branch.
+ Files, paths, commits, branches and
+ identifiers appear only in the
+ book's technical part.
```

Ruling: land, amend, or reject.
