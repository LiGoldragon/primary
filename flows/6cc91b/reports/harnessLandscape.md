# Harness and model landscape, September 2026 — Hermes, the best programmable harness, and the best models

Extends yesterday's `reports/openSourceHarness.md`; does not repeat its content. Every claim tagged with a URL and graded: (a) primary page, (b) search snippet/aggregator, (c) inference. Cross-checked where possible against this org's own prior research (`flows/7b4d4c/reports/research-other-harnesses.md`, 2026-09-04) and the living's own words (`flows/6cc91b/vision/openSourceHarness.md`).

## 1. What "Hermes" is

Two separate Nous Research products share the name; the living's question spans both.

- **Hermes Agent** (`github.com/NousResearch/hermes-agent`) — an open-source, model-agnostic coding/general agent harness, MIT-licensed. (a) https://api.github.com/repos/NousResearch/hermes-agent ; (a) https://hermes-agent.nousresearch.com/docs/
- **Hermes 4 / 4.3** — the separate open-weight model line (70B/405B, plus a 4.3 variant on a ByteDance Seed 36B base), hybrid-reasoning, trained partly on Nous's decentralized "Psyche" network. (b) designforonline.com, crabtalk.ai summaries; (a) technical report https://arxiv.org/pdf/2508.18255 (built on Llama-3.1-405B/70B, plus a 14B-on-Qwen3 variant)
- Harness architecture: a custom Python harness, not a documented fork of OpenHands/OpenCode. (c) inferred from doc language, no fork attribution found
- Notable design: a persistent cross-session "learning loop" that writes and improves its own skills, plus subagent spawning for parallel work. (a) https://hermes-agent.nousresearch.com/docs/
- Models it runs: explicitly **not** locked to Hermes-branded models — "Nous Portal, OpenRouter, OpenAI, or any [compatible] endpoint," 300+ models via Nous Portal. (a) same URL
- Programmability: 7 execution backends (local, Docker, SSH, Daytona, Singularity, Modal, Vercel Sandbox); messaging-gateway integrations (Telegram/Discord/Slack/WhatsApp/Signal, 20+ platforms); Python can call tools via RPC; a built-in cron scheduler. (a) same URL. No JSON-RPC session-attach/steer protocol like Codex's app-server was found documented — the programmability story is RPC tool-calls plus messaging/cron hooks, not mid-turn steering. (c)
- License: MIT, confirmed via GitHub API. (a) https://api.github.com/repos/NousResearch/hermes-agent
- Adoption: GitHub API reported **245,426 stars** as of 2026-09-14, created 2025-07-22, with tagged releases roughly weekly through September (`v2026.9.14`, `v2026.9.11`, `v2026.9.7`...). (a) GitHub API, direct call. **Caution**: this number was not cross-checked against a second source (e.g. a star-history site) and is unusually high for a 14-month project; DeepSeek Harness's independently-corroborated ~200k-in-weeks growth (section 2) makes explosive open-source-agent star counts plausible in this period, but treat the exact Hermes figure as unverified pending a second source. `flows/7b4d4c/reports/research-other-harnesses.md` (2026-09-04) separately lists "Hermes" among harnesses documented as working with ChatGPT-subscription OAuth tokens, corroborating that it is a live, maintained project, not confirming the star count. (a) that internal report

**Answer to "is it pi?"**: no — Hermes and Pi are different projects (Nous Research vs. Mario Zechner/Earendil Works). Pi is covered in yesterday's report and again below.

## 2. The best "just programmable" open-source harness, ranked

Criteria: a program can drive sessions, inject prompts mid-session, receive structured events, swap models, and run in a container/separate-user environment.

1. **DeepSeek Harness (dsh)** (`deepseek-ai/deepseek-harness`) — the standout new entrant, not covered in yesterday's report. "Everything is a plugin": model adapter, tool registry, session log, sandbox, and the agent loop itself are all swappable plugins, on a DI framework called Cordis; a "profile" (package.json + `cordis.patch.yml`) fully composes one session. (a) https://github.com/deepseek-ai/deepseek-harness ; corroborated in detail by this org's own prior research at `flows/7b4d4c/reports/research-other-harnesses.md` (system-prompt assembly pipeline, AGENTS.md/CLAUDE.md loading order, provider catalog). Not locked to DeepSeek's own models — Claude, OpenAI, Bedrock all pluggable. (a) same. TypeScript/pnpm monorepo, MIT. (a) prior internal report. Released 2026-08-13; star growth independently reported at ~203k in two weeks by the internal report and ~223.8k as fetched fresh by this pass — consistent trajectory, reportedly the fastest star growth in GitHub's history. (a)/(b) https://pasqualepillitteri.it/en/news/11573/deepseek-harness-fastest-github-stars-record. Caveat, stated by the project itself: "developer preview," compatibility-breaking changes expected. (a) GitHub repo page. This project already carries a `deepseek-harness` skill (`Curriculum skills` / this session's skill listing), i.e. this org has already begun treating dsh as a first-class integration target, not a speculative pick.
2. **mini-swe-agent** (`SWE-agent/mini-swe-agent`, successor to SWE-agent, Princeton/Stanford SWE-bench team) — smallest possible surface (~100 lines), bash-only tool interface so it runs behind *any* model via litellm/openrouter, and >74% SWE-bench Verified despite the minimalism. ~6.2k stars. (a)/(b) repo README via search. The only harness in this whole survey (this pass and yesterday's) with primary-documented Bubblewrap, Podman, and Singularity/Apptainer sandbox backends in addition to Docker — the cleanest "separate namespace" story found. (a) repo README
3. **Claude Code / Claude Agent SDK** (closed-source, scriptable) — `-p`/`--print` headless mode, `--output-format stream-json`, `--resume`/`--fork-session`; `query()` (stateless) vs. `ClaudeSDKClient` (stateful, required for full hook support incl. SessionStart/SessionEnd/Notification). (a) https://code.claude.com/docs/en/agent-sdk/hosting. Best-documented multi-tenant container story of anything checked: ephemeral-per-task containers, long-running multi-session containers, hybrid hydrate-from-store sessions, per-tenant `CLAUDE_CONFIG_DIR` and egress rules. (a) same URL. Constraint: single-vendor model-tied, closed-source harness binary.
4. **OpenCode / Pi / Goose / OpenHands** — see yesterday's report for full detail; no material version change found this pass beyond what's noted in section 4 below.
5. **Crush** (`charmbracelet/crush`) — FSL-1.1-MIT (converts to MIT after 2 years), pre-1.0, ~28.1k stars. Built on the Claude Agent SDK; `crush serve` gives a REST-ish backend for multiple clients against one workspace, mid-session model swap across 50+ providers, "preliminary" hooks. (a)/(b) github.com/charmbracelet/crush. No independent container/sandbox documentation — likely inherits whatever the Agent SDK provides. (c)
6. **Amp** (Sourcegraph) — proprietary, not open-source; included for completeness only. Runs Claude/GPT backends, reports 40,000+ dev teams adopted it as primary workflow within its first two months of 2026. (b) llmreference.com, producthunt. Fails the open-source criterion outright.
7. **Hermes Agent** — see section 1; strong on programmability (RPC, cron, messaging hooks) but no session-attach/steer protocol found; ranked here rather than higher pending confirmation of that gap and of its star count.

### Plain verdict
For a containerized secondary/tertiary flow needing strong programmatic control: **DeepSeek Harness (dsh)**, if the "developer preview, will break" risk is acceptable — its plugin-everything architecture is a near-literal match to "just programmable," it is MIT, it already has real Nix/Docker community packaging, and it has the largest and fastest-growing community of anything surveyed, open or closed. If that instability is disqualifying, **mini-swe-agent** is the safer fallback: tiny, auditable, model-agnostic, with the cleanest primary-documented sandbox-backend story of the group. **Claude Code's Agent SDK** is the best-written container/multi-tenancy doc set of all of them and already familiar via this org's `claude-harness` skill, but it only wins if staying inside the Anthropic model ecosystem is acceptable — which contradicts the living's evident interest in DeepSeek/Hermes/Qwen/GLM as first-class options.

## 3. The best models right now, open-weight and frontier

All scores below are point-in-time, dated where the source states a date; grade per claim.

- **DeepSeek**: the living's "V4.1" is real — **DeepSeek V4.1 Flash**, technical report/model card dated 2026-09-10, 552B total params, 8B/16B active in/out MoE. (a)/(b) benchlm.ai/models/deepseek-v4-1-flash, mindstudio.ai/blog/deepseek-v4-1-flash-benchmarks. Scores 74.2 on "Deep SWE," roughly matching GPT-6 Astra/Gemini 3.8 Flash/Opus 5 in that range. (b) On the Artificial Analysis Intelligence Index (Sept 2026), "DeepSeek V4 Pro 0813 (max)" scores 36 — trailing GLM-5.3/Kimi K3 at 44. (b) artificialanalysis.ai via benchlm.ai. Hands-on testers report it stumbling on tasks its own benchmark scores imply it should ace — a real benchmark-vs-practice gap. (b)
- **Kimi K3** (Moonshot AI): confirmed current, released 2026-07-16 (weights 2026-07-27), 2.8T-param MoE, open-weight. (a)/(b) tomshardware.com, cometapi.com. #1 in Frontend Code Arena (1,679 pts, ahead of Claude Fable 5); 88.3% Terminal-Bench; 91.2% BrowseComp; 93.5% GPQA-Diamond. (b) cometapi.com. Ties GLM-5.3 for the top open-weight Intelligence Index score (44), ranking #3 overall behind only Claude Fable 5 and GPT-5.6 Sol among *all* models, proprietary included — the strongest open-weight showing found. (b) 247wallst.com/benchlm.ai
- **Qwen**: the living's "Qwen 3.8" is real but the family moved fast in 2026 — Qwen3.5 (397B-A17B MoE, 2026-02-16) scored 76.4% SWE-bench Verified, 88.4 GPQA-Diamond, 91.3 AIME-2026, 83.6 LiveCodeBench v6. (b) aireleasetracker.com. Qwen3.6-27B (dense) then beat it on agentic coding at 77.2% SWE-bench Verified despite ~1/15th the params. (b) Qwen3.8-27B (newest, Aug 2026) is reported "level" with 3.6 on independent measures; on the Intelligence Index a differently-sized "Qwen3.8 2.4T-A95B" scores 40. (b) codersera.com, benchlm.ai — the size discrepancy across sources suggests multiple Qwen3.8 variants exist; flag as unresolved, not confirmed against one primary model card.
- **GLM** (Zhipu/Z.ai): the living's "GLM 5.3" is real and current — 743B-param MoE, released 2026-08-14, MIT-licensed, code-first. (a) huggingface.co/zai-org/GLM-5.3. Leads open-weight scores on Terminal Bench 3.0 and "Agents' Last Exam (CLI)," with standout cybersecurity/CyberGym results, but Z.ai's own framing states GPT-5.6 Sol and Claude Fable 5 still lead on some coding/terminal/offensive-security tests. (b) blog.mean.ceo, edenai.co. Ties Kimi K3 for top open-weight Intelligence Index score (44).
- **Hermes models** (coding/reasoning quality only): current line is Hermes 4 on Llama-3.1-405B/70B (also a 14B-on-Qwen3 variant), hybrid reasoning with a toggleable think mode, ~5M-sample/~60B-token post-training corpus. (a) https://arxiv.org/pdf/2508.18255. No independent SWE-bench/LiveCodeBench/Terminal-Bench placement was found — coverage is "competitive"-language and community-measured, not a hard leaderboard entry. Treat as open and reasoning-focused, not benchmark-verified at the Kimi/GLM/DeepSeek tier. (c)
- **Llama & Mistral**: Llama 4 (Scout/Maverick/Behemoth) has clearly fallen behind for coding — 2026 retrospectives call it uncompetitive against Qwen-Coder/DeepSeek and note Meta's headline arena score used an unreleased tuned variant, not the shipped model; no Llama model appears in the Sept-2026 Intelligence Index or SWE-bench top tiers found. (b) rootly.com, codersera.com. Mistral Large 3 (675B MoE, "large-2512") is reported to beat Kimi-K2/DeepSeek-3.1 on some comparisons, but one source states it has no source-displayable benchmark rows yet on major boards — treat Mistral's standing as unresolved. (b) dev.to/jangwook_kim, benchlm.ai
- **Frontier reference** (Sept 2026): SWE-bench Verified — Claude Opus 5 ~96%, GPT-5.6 Sol ~96.2%, both near-saturating the benchmark; Gemini 3.1 Pro was 80.6% as of May 2026, not in the current top tier. (b) benchlm.ai, morphllm.com. Intelligence Index: GPT-5.6 Sol 58.9, GPT-5.6 Terra 55.0, Claude Fable 5.1 53.4. (a)/(b) benchlm.ai/artificialanalysis

### Where open-weight matches frontier, where it trails
On the Intelligence Index, the best open-weight models (Kimi K3, GLM-5.3, both 44) sit ~9 points behind the frontier leader (GPT-5.6 Sol, 58.9), with Kimi K3 ranking third overall ahead of every proprietary model except the top two. On narrower agentic/coding boards the gap looks smaller or closed: Kimi K3 leads the Frontend Code Arena outright, GLM-5.3 leads Terminal Bench 3.0 and the CLI agent exam among open-weight models — though Zhipu's own materials admit GPT-5.6 Sol/Claude Fable 5 still lead some coding/terminal/offensive-security evaluations. The clearest remaining frontier lead is specifically **SWE-bench Verified**: DeepSeek's and Qwen's newest land in the high-70s to low-80s versus mid-90s for Opus 5/GPT-5.6 Sol. Llama has genuinely fallen off the competitive tier; Mistral and Hermes both lack solid independent benchmark placement and should be treated as unverified, not confirmed competitive.

## 4. Container, separate-user sandboxing, and Nix packaging

Per the living's ask for "a light sandbox... container for the codex, the code, or whatever harness we decide on":

- **OpenHands** — has the clearest documented read-only host-mount mechanism: `SANDBOX_VOLUMES` takes `host_path:container_path[:mode]` with `ro` supported explicitly, inside a controller-container/per-task-sandbox-container architecture via a mounted Docker socket. (a) https://docs.openhands.dev/openhands/usage/v0/runtimes/V0_docker. Not found in nixpkgs or `numtide/llm-agents.nix` this pass. (c)
- **Hermes Agent** — container-by-default architecture: every tool call executes inside one persistent Docker sandbox container spanning the process lifetime (including `/new` and subagents); all state (config, keys, sessions, skills, memories) lives in one host directory mounted into the stateless container at `/opt/data` — a shared-persistent-volume pattern, not literally read-only, but the most architecturally central container design of the group. (a) https://hermes-agent.nousresearch.com/docs/user-guide/docker. Nix: packaged in `numtide/llm-agents.nix`; not confirmed in nixpkgs proper.
- **Pi** — has a dedicated containerization doc naming three patterns, notably **Gondolin**: keeps Pi/auth on the host and routes commands into a local Linux microVM — the only harness explicitly designed to keep the owner's login/auth on the host while sandboxing execution, closest to the living's "reuse owner's login" framing, though the doc doesn't confirm the auth directory is mounted strictly read-only. (a) github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/containerization.md. Nix: in `numtide/llm-agents.nix`; not confirmed in nixpkgs proper.
- **Codex CLI** — OS-native sandbox (Landlock+seccomp/Seatbelt) by default, plus a Docker/microVM mode (Docker Sandboxes GA 2026-01-30) and a `codex-universal` image. (a) codex.danielvaughan.com, docs.docker.com. No credential-read-only-mount doc surfaced. In nixpkgs proper (`pkgs/by-name/co/codex`) and `llm-agents.nix`. (a) github.com/NixOS/nixpkgs
- **Claude Code** — official "Choose a sandbox environment" doc covers the built-in sandboxed Bash tool, devcontainers, Docker, VMs. (a) code.claude.com/docs/en/sandbox-environments. Notably the documented credential mechanism runs the *opposite* direction from the living's ask: a `sandbox.credentials` setting (v2.1.187) lets you **block** reads of `~/.aws/credentials`, `~/.ssh`, etc., rather than deliberately mount them read-only for reuse. (a) code.claude.com/docs/en/sandboxing. In nixpkgs proper, plus faster-moving community flakes (`sadjow/claude-code-nix`, `ryoppippi/nix-claude-code`).
- **Goose** — official Docker-Compose doc exists, but a third-party security report ("Agent Safehouse") states Goose ships with **no built-in sandboxing** and runs with full user permissions by default; credentials are passed as plain env vars in `docker-compose.yml`, weaker than a shared read-only credentials-directory pattern (keyring doesn't work under Ubuntu-in-Docker). (a) goose docs; (b) agent-safehouse.dev. In nixpkgs (`goose-cli`) and `llm-agents.nix`.
- **DeepSeek Harness** — sandbox is a first-class plugin per its "everything is a plugin" architecture, but whether that plugin natively supports a separate-Unix-user/container mode, versus community Docker/Helm images layered on top, was not confirmed from primary docs this pass — treat native-container support as (c) inference only. Community Docker/Compose/Helm projects and at least one Nix flake exist, plus a pending (not yet merged) nixpkgs PR (#554081). (b) github.com/runzhliu/deepseek-harness-docker, github.com/NixOS/nixpkgs/pull/554081. Confirmed **not yet in nixpkgs proper** by this org's own 2026-09-04 research (`nix search nixpkgs deepseek` found only unrelated projects). (a) `flows/7b4d4c/reports/research-other-harnesses.md`
- **Crush** — sandboxing is an open, unimplemented GitHub issue (`charmbracelet/crush#1541`); a third-party community sandbox repo exists but nothing first-party. Ships NixOS/Home-Manager modules via NUR, not nixpkgs proper. (a) github.com/charmbracelet/crush/issues/1541
- **OpenCode, Aider, mini-swe-agent** — OpenCode: no sandbox doc surfaced, in nixpkgs proper. Aider: no sandbox doc, thin stdin/stdout design (consistent with yesterday's finding), `aider-chat` in nixpkgs proper. mini-swe-agent: primary-documented Bubblewrap/Podman/Singularity backends (section 2) — the strongest sandbox-backend documentation found in this entire survey, but no host-credential-mount pattern specifically described.

**Summary judgment (c)**: no single harness combines "in nixpkgs proper" + "documented read-only credential mount" + "container-by-default" all at once. If the requirement is specifically *reusing the owner's login via a read-only-mounted credentials directory*, OpenHands's `SANDBOX_VOLUMES ...:ro` is the only harness with that exact mechanism written down; Pi's Gondolin is the only one designed around keeping auth on the host by intent; Hermes Agent is the most container-native architecture overall, just not read-only. None of this org's current two production harnesses (Claude Code, Codex CLI) documents the read-only-credentials-mount pattern the living described — Claude Code's documented mechanism is the inverse (blocking credential reads), and Codex's container mode doesn't address credentials at all in the docs found.
