## 5. Reviewer's view: Ethos as a schema language

*This section is the reviewer's own assessment on code evidence. It is not an error finding, and nothing here is ruled.*

### What it does well

**One declaration yields one consistent, fully derived type.** The live signal-orchestrate contract:

```
LockRequest.{ LockName FlowId Vector<LockPath> LockReason }
```
```rust
#[rustfmt::skip]
#[derive(rkyv::Archive, rkyv::Serialize, rkyv::Deserialize, Clone, Debug, PartialEq, Eq, Hash)]
#[cfg_attr(feature = "datom", derive(datom_codec::Datomizable, datom_codec::Composing))]
pub struct LockRequest { pub lock_name: LockName, pub flow_id: FlowId, pub lock_path_vector: std::vec::Vec<LockPath>, pub lock_reason: LockReason }
```

The ratio of ethos to Rust is about 1:6. Text support is compiled out of the Nexus by construction. Every type is hashable and comparable.

**The ethos is authoritative wherever the binding pattern is used**, and the pattern is four lines of build.rs (signal-orchestrate, witnessed):

```rust
let file = Potential::<File>::from(source).actualize().unwrap_or_else(|_| panic!("read Signal"));
let generated = file.generate().unwrap_or_else(|_| panic!("generate Signal"));
assert_eq!(generated, std::fs::read_to_string(root.join("src/generated/signal.rs")).expect("generated"));
```

Where it is used (23 signal and 16 meta-signal repos), ethos and code cannot drift. The flow example shows this: the audit's "drift" was found only where the pattern had been removed.

**Kinds map cleanly to traits** (fixtures/capability-kinds.ethos → capability-kinds.rs):

```
Fillable.[ push!{ [ String ] [ Result<Integer SinkError> ] }  drain![ Vector<String> ]  create:[ Self ] ]
```
```rust
pub trait Fillable {
    fn push(&mut self, input: String) -> std::result::Result<i64, super::SinkError>;
    fn drain(&mut self) -> std::vec::Vec<String>;
    fn create() -> Self where Self: Sized;
}
```

The receiver glyphs `.`, `!` and `:` are terse and exact. The `Sized` bound is added where Rust needs it.

The checker is typed and refuses cycles, duplicates and undeclared names. It escapes keywords, and the recursive `Option<Box<T>>` placement is deliberate and explained in the source (generation.rs:331).

### What is missing or wrong

**1. A name buys a field name, not a type, and the role of a position is lost.** In signal-flow@5ca97ce there are 33 `X.String` aliases. `LaunchProfile`'s optional `FlowId` is the *predecessor* (the file's header comment says "names the replaced flow as its predecessor"), yet the generated field is `pub flow_id_option: Option<FlowId>`. To name the role, an author must add yet another `String` alias, which buys no safety.

ethos-zero's own contract shows the end state of the rule: `Generation.{ String String }` becomes `first_string` / `second_string`, for a source path and an output directory. The naming rule gives up exactly where two positions share a type, which is where a name matters most. In my view, **role and type need to be separable** (a role-named position whose type is given), and **a named scalar should be a newtype**. The first is not in the audit's list. The second is fix 9, which waits on a ruling.

**2. Meaning changes at a distance.** A bare variant silently carries any type of the same name. The tool's own fixture and the live contract diverge on this with near-identical text:

```
; ethos-zero fixtures/orchestrate.ethos             ; signal-orchestrate ethos/signal.ethos
ObserveSelection.[ Locks ]  Locks.Vector<Lock>      ObserveSelection.[ Locks ]      (no type Locks)
```
```rust
pub enum ObserveSelection { Locks(Locks) }          pub enum ObserveSelection { Locks }
```

The most-written ethos in the estate carries the same trap. The final-response `Type` block declares `Kind.[ MainFlow Subflow ]` beside `Subflow.{ Topic Markdown }`. Under ethos-zero's rule the `Subflow` variant would carry a `{ Topic Markdown }` struct, which the skill surely does not mean (*inference*; the Type root is refused today, so no generator has ever shown it). I would refuse a bare variant whose name is also a type, and make capture explicit (`Locks.Locks`). That costs one repetition and buys the removal of a silent failure.

**3. The Signal root cannot say what a Nexus contract is about: which reply answers which query, and which query streams.** Query and Response are two flat enums. The pairing `Lock → Locked | LockRejected` is naming convention only. The streaming and exchange-lifetime rules live in comments:
- signal-orchestrate: "Nothing on the wire says which queries stream — this text does, and both sides read it."
- signal-flow@5ca97ce: "Observe.Launch opens an exchange that goes on answering … Every other query is answered with exactly one frame."

Those comments are then dropped from the generated Rust (31 `;` lines → 0 in signal-orchestrate). In my judgement this is the largest gap for a language whose main job is Nexus contracts. With pairing and a stream mark in the grammar (e.g. `Lock.LockRequest → [ Locked LockRejected ]`, `Observe.ObserveSelection →* [ Observed ]`), the generator could emit typed client calls, and the framing and streaming splits the anatomy report found (§6 items 2 and 11) would become checkable. It would also serve "Ethos may generate default implementations for Query and Response" (Vision/ethos.md:291).

**4. Imports are unchecked strings.** meta-signal-flow@4748cfa imports a `RecipientDisposition` that does not exist. It survives because an unused import emits nothing, and a used one would emit a path nobody resolves until rustc. Ethos-to-ethos imports that resolve against the imported file are the precondition for the manifest the living asked for (fix 1).

**5. Scalars are too few, and the derive set is fixed.**
- `Integer` is only `i64`; there are no bytes and no fixed arrays (fix 4).
- Every type derives `Eq + Hash`. That forced ethos-zero commit 34f4a8c, "Lower Decimal to the finite type and derive Eq and Hash unconditionally": the schema language bent a numeric type to fit its fixed derives.

**6. The Sema root is hollow while the vision ranks Sema above Nexus.**

```
Sema
[]
[ Record.{ String Vector<Entry> }  Entry.{ String Integer } ]
```
```rust
#[derive(datom_codec::Datomizable, datom_codec::Composing, Clone, Debug, PartialEq, Eq, Hash)]
pub struct Record { pub string: String, pub entry_vector: std::vec::Vec<Entry> }
```

The output has no rkyv (so no archived storage form), no key or identity, and no migration. "Operational editing should yield the migration with the edit" (Vision/sema.md) has no foothold in the grammar yet. A positional, unnumbered schema can only evolve by versioned migration. That makes a migration notion in the Sema root more urgent than it would be for Protobuf-style formats.

**7. Naming is not one rule.** Fields are named by type. Capability inputs are named `input`, `input_0`, `input_1` (generation.rs:784-791). Derived types are `_Data`, except when they collide. ethos-zero hand-writes `Generation_Error`, which is `_`-named but not derived. In my view one naming law should cover fields, inputs and derived types.

**8. There is no formatter, so the canonical print is aspirational.** signal-flow@5ca97ce's entire types section is one physical line (line 26, about 5 KB). Ethos's terseness only pays off when the print is canonical and enforced. A `Format` query beside fix 7's `Check`, run by the freshness test, would close that.

### Summary of the reviewer's view

The data core is excellent: one line of ethos becomes a fully derived, feature-gated, freshness-bound Rust type, and where the build.rs binding is used the ethos is truly authoritative. The weaknesses are semantic, not mechanical:
- positions cannot carry roles, and aliases carry no type;
- a bare name can silently change meaning;
- the Signal root cannot state query-to-reply pairing or streaming, so contracts keep their most important facts in dropped comments;
- imports resolve nothing;
- Sema has no identity or migration notion.

Before whole-program syntax (fix 1), the next best investment is making Signal say what its comments say today, and making role, newtype and import resolution first-class.
