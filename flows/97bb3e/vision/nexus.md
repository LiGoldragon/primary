## A Nexus exposes what can be configured through a configuration interface

Context: the living, to Psyche core Secondary 97bb3e, 2026-10-24 evening, answering 97bb3e's restatement of his five points (seats; comments fetched by the Tertiary; Fable decides what a new Primary is given for the anatomy; Mind's report on flow starting; Nexus configuration). Words of the turn before, confirmed in this one.

> I want my Nexuses, as much as possible, to expose anything that we might want to configure through a configuration interface (so that we don't hardwire any part of the behavior that could be configured in the Nexus, which would then both make it difficult to change and would also hide the behavior).

## Multiple capsules; a simple query on the default, a variant with one more field

> There's another thing: it should be able to configure having different capsules, multiple capsules. That's the thing: we can have many different features that are not exposed in all of the queries. We would have a simple query to interact with Flow that just uses the default capsule and then we would have a slightly different query that maybe has just one additional field that lets us specify the capsule that we want.
>
> I want this pattern to become widespread especially in responses so that, for example, when we get responses we don't get all of the technical stuff like the message ID and the flow ID and all that crap.
