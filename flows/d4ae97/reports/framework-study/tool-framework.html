Tool Framework Study

Which language and libraries should every tool that flows write to query and act on the system share? Sixteen candidates scored against the living's criteria, with startup cost measured on goldragon.

Recommendation

Clojure, with Malli schemas over datom-shaped EDN. Run from source in Babashka; ship as a GraalVM native image.

Clojure is the only candidate that is homoiconic, data-centred, mature, Nix-packaged, EDN-native and written well by machines all at once. Its weak point is static types. The second weak point, JVM startup, goes away with a native image: the same Clojure + Malli tool starts in 11.5 ms as a native image, against 137 ms in Babashka and 465 ms on the JVM. A slow build is acceptable (53 s here). Rust stays the language a tool graduates into once it becomes a component, following the psyche's path of Malli prototypes, then ethos, then Rust.

field-clj '#commit ["msg" ["README.md"]]' ;; one inline EDN value, no flags status-clj '[flows 10]' ;; small default page status-clj '[flows 10 10]' ;; the #more [10] it printed, passed back

What was measured

11.5 msClojure + Malli tool built as a GraalVM native image (graalvm-ce 25.0.2, 53 s build)
19–25 msBabashka 1.13.219 bare, and with babashka.cli and clojure.edn loaded
128–137 msBabashka once Malli loads: Malli is interpreted from source on every call
4.3–5.4 sfield-clj as deployed (a JVM uberjar). With its shadowing source files stripped: 462 ms

Defect found in clj-build. mkCljUberjar writes every jar entry with one date (--date 1980-01-01T00:00:02Z). Clojure loads a namespace from its .clj unless the compiled class is strictly newer, so equal dates make every deployed JVM tool recompile clojure.core, Malli and its own code at each start. Stripping the 62 shadowed sources cut field-clj from 4321 ms to 462 ms (median, 6 runs). The fix is to omit sources that have an __init.class, or to give classes a later date than sources.

Does Clojure have types?

What is true

Clojure is dynamically typed. Every value has a runtime type (a JVM class or protocol), and records, protocols and type hints exist, but nothing is checked before the program runs. "Clojure has types" holds in three weaker senses, listed here by how much they are used.

The three options

Malli (metosin): schemas are plain data vectors such as [:tuple :keyword :int]. It validates, explains, coerces and generates, instruments functions in development, and exports clj-kondo type hints for a light static lint. It runs in Babashka and in native images. It fits a datom-shaped design best.

clojure.spec: built in, but specs are macros rather than data, and spec 2 has stalled. Not recommended.

Typed Clojure 1.3: a real optional static checker with occurrence typing that can read Malli schemas. It runs on the JVM only, not in Babashka, and few people use it. Keep it as an option for one critical tool; do not make it the standard.

If the living wants checking before the program runs, the honest choices are Rust (already the system's compiled language, with ethos-generated types), Lean 4, OCaml, or Coalton inside Common Lisp. None of them is homoiconic and data-centred the way Clojure is. Shen has the strongest type system of the Lisps here, but it ships as a REPL with no scripting entry point, no EDN, and a very small community.

Proposed standard dependency set

  • Runtime
    Babashka while a tool is young or rarely called. A GraalVM native image (via com.github.clj-easy/graal-build-time) once flows call it routinely. Never a plain JVM jar for a tool that should be cheap to call.
  • Input
    clojure.edn reads the one inline EDN value that emulates datom. knowledge-datom already rules no flags, so babashka.cli is not part of the standard; keep it only for a tool whose callers are people.
  • Schemas
    metosin/malli: an Input and an Output schema per tool, output validated before printing, m/explain turned into a #refused value. Malli's function schemas export clj-kondo types.
  • Static check
    clj-kondo in the flake check, fed the Malli-exported types. Typed Clojure optional.
  • Process and files
    babashka.process and babashka.fs: built into Babashka, ordinary libraries on the JVM and in a native image.
  • Output bounds
    No library does this. Write one shared namespace (proposed home: clj-build or a small tool-clj library) that takes the result sequence, prints a default page (count and byte budget), and ends with #more [offset]. The offset is a small integer, never a hash.
  • Stores
    The Datalevin pod messenger-clj already uses. A Rust component joins as a Babashka pod or a subprocess speaking datom text.
  • Testing with traces
    clojure.test running golden EDN traces (each a recorded [input output] pair played against the built binary), malli.generator with test.check for generated inputs, and Malli instrumentation in development. FlowStorm for time-travel debugging on the JVM, optional.
  • Nix
    clj-build: mkCljCli with runtime = "bb" today; add a mkCljNative builder for native images and fix the uberjar date defect.

Proposed skill lines

Both lines go in one new operation skill, because no existing mind-skills file covers writing system tools. knowledge-datom line 95 already rules the call shape (one inline datom value, no flags), so these lines do not repeat it. The framework line encodes a choice an agent cannot derive. The contract line encodes the living's 2026-10-08 ruling and the measured field-clj startup.
