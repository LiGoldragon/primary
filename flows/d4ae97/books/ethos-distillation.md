## Proposals

Proposed, appended:

### 2. Non-repetition: a type is never wrapped twice
Now:
> Any repetition in ethos syntax is an implementation failure. Ethos aims to be the most terse, non-repetitive syntax ever made.

Proposed, appended:
> A type is never wrapped in a second new type: where a thing is a LockId, it is written LockId. No type is invented to say what a variant carries.

```
Library                                  ; the shared types of a lock service
[]                                       ; imports: none
[ LockId.Integer                         ; types: LockId is an Integer
  Release.[ LockId                       ;   Release: the variant LockId carries the LockId type itself;
            All ] ]                      ;   no Target.LockId is invented to wrap it again
[]                                       ; kinds: none
[]                                       ; associations: none
```

Your words:
> If a job is a flow ID, then why are we even using the word "job"? Just use "flow ID". Why are you going to wrap a new type with another new type? Don't double-wrap types. That's silly.
-- d4ae97 ethos, 2026-10-06
> I don't want this repetition of types, like where we invent another type to say what's inside a variant.
-- 91ea9f ethos, 2026-10-02
> And what are the double new type wrapping about? I don't like it.
-- d63804f2 newtypeWrappingAndSingleFieldStructs, 2026-08-07

### 3. Non-repetition: an enum whose every variant carries the same type is a struct
Proposed, appended to Non-repetition:
> An enum whose every variant carries the same type repeats that type in each variant; it is written as a struct of the two.

```
Library                                  ; the shared types of Flow
[]                                       ; imports: none
[ Voice.{ Aspect.[ Psyche                ; types: a voice is a struct of its aspect and its layer,
                   Mind                  ;   not Voice.[ Psyche.Layer Mind.Layer Field.Layer ],
                   Field ]               ;   which repeats Layer in every variant
          Layer.[ Primary
                  Secondary
                  Tertiary
                  Quaternary ] } ]
[]                                       ; kinds: none
[]                                       ; associations: none
```

Your words:
> I think we're going to abandon this idea that we wouldn't have an enum where each data-carrying variant carries the same type, because it creates this repetition that you can see now: `[psyche].layer`, `[mind].layer`, `.layer` is being repeated. I think rather the voice is a struct that contains the aspect and the layer
-- aa887c ethos and bad807 ethos, 2026-10-04
> Voice.{ Aspect.[ Psyche Mind Field ] Layer.[ Primary Secondary Tertiary Quaternary ...
-- edf227 flowRole, 2026-10-03, written as ethos by you

On 2026-10-03 you wrote `psyche.primary` as "a data-carrying variant that holds a variant" (5578cc flow); the 2026-10-04 words above say to lean on structs instead. This proposal carries only the repetition rule, nothing about chained variants elsewhere.

### 5. New heading after Non-repetition: Everything is a type
Proposed:
> ## Everything is a type
> There is no key-value in Ethos; everything is a type. A struct's positions are types, and no name is written beside a value.

```
Library                                  ; the shared types of a lock service
[]                                       ; imports: none
[ LockId.Integer                         ; types
  LockName.String
  Lock.{ LockId LockName } ]             ;   Lock: each position is a type, no key names a value
[]                                       ; kinds: none
[]                                       ; associations: none
```

Your words:
> We don't have key-value in Ethos anymore. Everything is a type.
-- 91ea9f ethos, 2026-10-02
> The key-value map is out of our syntax because it's really just a poorly specified struct, which has a sort of open-ended number of fields: name the field and then give it a value.
-- 93ba9f ethosNames, 2026-09-26

### 6. Inline types: inline unless used again; about three deep
Now:
> A type may be declared where it is used.

Proposed, in its place:
> A type used in one place only is declared inline, where it is used; only a type used in more than one place is declared apart and named. Inline nesting goes about three deep, not as a hard limit; past that depth a type is imported from a library.

```
Library                                  ; the shared types of Flow
[]                                       ; imports: none
[ FlowId.Integer                         ; types: FlowId is used in many places, so it is named
  Flow.{ FlowId                          ;   Flow: a struct
         State.[ Running                 ;   State is used only here, so it is declared inline
                 Ended ] } ]
[]                                       ; kinds: none
[]                                       ; associations: none
```

Your words:
> I would also like to make it so that unless a type is used in more than one place, it should be declared inline. We would have a maximum depth after which we would require the types that are at, I don't know, maybe the third depth to be imported from an external library.
-- 91ea9f ethos, 2026-10-02
> We don't have to make it a hard limit. Maybe it's not a hard hard limit
-- 91ea9f ethos, 2026-10-02

### 7. New heading after What a declaration turns into: One position
Proposed:
> ## One position
> There is no struct of one position. A type that holds one other type is written as its name, a dot, and that type.

```
Library                                  ; the shared types of a lock service
[]                                       ; imports: none
[ LockName.String ]                      ; types: one position, written LockName.String,
                                         ;   never LockName.{ String }
[]                                       ; kinds: none
[]                                       ; associations: none
```

Your words:
> I think we should possibly even refuse single-field struct types and ethos
-- 8e9e77 single-field-structs, 2026-09-08
> a new type should be just the name of the type and then the separator, which is a period, and then the name of the contained type.

### 8. New heading after Spacing: Vertical
Proposed:
> ## Vertical
> Ethos expands vertically wherever there is a next layer: the structure opens on its line and its elements hang beneath the first, aligned, and going right is free. The closing delimiter ends the last element's line; it never takes a line of its own.

```
Signal                                   ; what Flow says
[]                                       ; imports: none
[ Launch.{ Voice.{ Aspect Layer }        ; queries: Launch has a next layer, so it opens here,
           Brief.String } ]              ;   its elements aligned; the closing delimiters end this line
[ Launched                               ; responses
  Refused ]
[ Aspect.[ Psyche Mind Field ]           ; types: no next layer inside, one line
  Layer.[ Primary Secondary Tertiary Quaternary ] ]
```

Your words:
> I want it to be a language that expands vertically. ... it has to be perfectly lined up, beautifully formatted, a bit like Nix or Python. It looks more like a data structure that expands vertically whenever there's a next layer.
-- 91ea9f ethos, 2026-10-02
> When you're defining inline, like `flow.voices`, then you should go vertically and be liberal in going to the right.
-- 91ea9f ethos, 2026-10-02
> I don't want the closing delimiter to create a whole new line
-- 91ea9f ethos, 2026-10-02

### 9. New heading after Declaration: File: Ethos is written whole, and commented
Proposed:
> ## Written whole, and commented
> Ethos is always written whole: inside its root, every section in place, so what each type is for is known. Types lifted out of their root are not ethos. Ethos carries many comments, so whoever reads it sees what the machine reads.

```
Library                                  ; the root: what follows is a library
[]                                       ; imports: none
[ FlowId.Integer ]                       ; types: a flow's id, an Integer
[]                                       ; kinds: none
[]                                       ; associations: none
```

Your words:
> Whenever ethos is written, this block is not ethos because it's lacking a type so it's invalid. Ethos always has to be correctly written; otherwise it's out of context
-- c64ee3 ethos, 2026-09-29
> You can't just throw uncontextualized ethos code around. It doesn't mean anything.
-- d4ae97 books, 2026-10-05
> You need to always specify your object type in Ethos. ... let's just make this a requirement to talk about Ethos with clarity.
-- 692df8 ethos, 2026-09-15
> I actually would like all of the Ethos code to get way more comments so that I can see what the machine is seeing.
-- edf227 ethosComments, 2026-10-03

### 11. New heading after Associations: The memory kind
Proposed:
> ## The memory kind
> Every record type of Memory bears a kind whose change is standard: it succeeds or it fails.

```
Memory                                   ; what Flow remembers
[ flow:FlowId ]                          ; imports from the Library
[ Flow.{ FlowId                          ; record types: Flow bears the memory kind,
         State.[ Running                 ;   so a change to it either succeeds or fails
                 Ended ] } ]
```

Your words:
> It's going to be a kind that's going to have a standard successful or unsuccessful change implemented on these particular data types.
-- 91ea9f ethos, 2026-10-02

Whether Memory is a root of its own is ruling 1; the upgrade between versions is ruling 4.

## Rulings

### 1. Roots: Sema or Memory
Vision/ethos.md, Roots, now:
> Library, Signal, Sema. No version in a file. Signal's sections are queries and responses, since there is communication; Sema's are record types, the rest to be decided. Signal gives a Nexus its main types and Sema its database types.

One side, 2026-09-09:
> When we create the SEMA Ethos type for the root type, like we have library and signal, then we're going to be defining database record types.
-- 564f55 sema

Other side, 2026-10-02, and landed in Vision/nexus.md on 2026-10-04:
> Yeah the memory is good. That's what it is I guess: signal, operation, and memory.
-- 91ea9f ethos
> This is good. Can land
-- aa887c nexus, on «Three parts and one path»: Signal, Operation, Memory, each its own ethos specification

(a) Memory is the root once named Sema. Roots becomes:
> Library, Signal, Operation, Memory. No version in a file. Signal declares what a Nexus says, its sections queries and responses; Operation what it does, one operation type for every effect; Memory what it remembers, its record types; Library what they share.

(b) Sema stays the root of record types; Memory names the Nexus's part only. Roots becomes:
> Library, Signal, Operation, Sema. No version in a file. Signal declares what a Nexus says, its sections queries and responses; Operation what it does, one operation type for every effect; Sema what it remembers, its record types; Library what they share.

Under (a), Vision/sema.md's "its root, Sema" needs a proposal of its own later.

### 2. What one position turns into in Rust
Vision/ethos.md, Every declared type bears both kinds, landed 2026-09-09:
> An alias bears them through the type it names: an alias is not a new type and cannot carry a derive.

Your words, 2026-09-08:
> This should be a new type and not a struct with just a single element in it. ... A new type generally is like `name.string`, `age.integer`
-- 8e9e77 single-field-structs

(a) `LockName.String` stays an alias:
```rust
pub type LockName = String;
```
(b) `LockName.String` is a Rust newtype, bearing both kinds:
```rust
#[derive(Datomizable, Compositional)]
pub struct LockName(String);
```

### 3. A capability's inputs: types, or only kinds and Self
Vision/ethos.md, Kind syntax, landed 2026-09-04, takes a String as input:
```
Library                                  ; a sink
[]                                       ; imports: none
[ SinkError.[ Closed Full ] ]            ; types
[ Fillable.[ push!{ [ String ]           ; kinds: push takes a String, a concrete type
                    [ Result<Integer SinkError> ] } ] ]
[]                                       ; associations: none
```
Your words, 2026-10-02:
> I don't understand how there's a specific type as an input for a kind. That shouldn't be, right? It should only be another kind because a type is too specific. ... The voice is launchable, right, so it uses self.
-- 91ea9f ethos

You asked for real Rust checks with this; none is reported yet.
(a) A capability speaks only in Self, the kind's own parameters and other kinds. The Kind syntax example changes to match.
(b) A concrete type may stand as an input, as now.
(c) Wait for the Rust checks.

### 4. A memory format's upgrade: from, or both ways
Your words, 2026-10-02:
> each version is possibly going to have an implementation of an upgrade from or an upgrade to. I'm not sure. I guess an upgrade from makes more sense because you're trying to upgrade the past but it could be a symmetrical operation.
-- 91ea9f ethos

(a) Each version carries the upgrade from the previous format.
(b) Each version carries an upgrade both ways.
(c) Not yet.
