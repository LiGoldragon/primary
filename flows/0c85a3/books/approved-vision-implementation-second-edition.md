# Approved vision into working systems

## Inquiry 1: How does knowledge stay current? · mind-context › inquiry/knowledge-auditing.md, a new file

+ ### Open questions
+ What should cause a knowledge statement to be checked again: an elapsed interval, a change to its component, a reported contradiction, or some combination? If elapsed time matters, who chooses the interval?
+ When a statement is disputed, should a flow still receive it with a qualification, receive only the inquiry, or stop receiving it until the question is settled?
+
+ ### What Mind knows
+ The approved context vision asks for knowledge to be checked from time to time against practice, with variations going to inquiry. The Nexus vision forbids polling. Core's back audit did not find an implemented periodic knowledge audit. That absence does not decide what the trigger should be.
+ Inquiry is the means by which the machine develops question books for the living. Recording a discrepancy is therefore the beginning of an inquiry, not its completed outcome.
+
+ ### What is being tried
+ This edition is trying that question-book form on six real gaps. For knowledge auditing, Mind is comparing a scheduled review request with a request caused by a relevant change. Neither trigger has been implemented or selected. A useful next case would take one dated knowledge statement, its original evidence and a later contrary observation, and show exactly what the next flow would receive under each choice.
+
+ ### What would settle it
+ A ruling on the triggers and the treatment of disputed knowledge would settle the policy question. A worked case would then have to show that the discrepancy reaches an intelligible question book, without silently replacing knowledge or repeatedly checking an unchanged system.

## Inquiry 2: What is a layer or topic section? · mind-context › inquiry/role-sections.md, a new file

+ ### Open questions
+ Does a role section mean a directory for each layer and topic, a named section in a module, or a grouping resolved by Curriculum? What should a topic specialization do when it contradicts its layer role: override it, be refused, or return the conflict for review?
+
+ ### What Mind knows
+ The context vision calls for role sections for Primary, Secondary, Tertiary and Quaternary, with optional specialized topics. The three context repositories own authored context. Curriculum already resolves module identities and composes explicit role selections. Core's audit found flat role folders, not the requested layer sections. A folder arrangement alone would not establish how the resulting roles combine.
+
+ ### What is being tried
+ Mind is separating the question of where a role is authored from the question of what a flow receives. The comparison is between a layer module plus a topic module and a complete module for each specialized layer. Neither layout is selected. The next worked example should use one existing role and one deliberate conflict, without changing its model configuration or copying its instructions into another authority.
+
+ ### What would settle it
+ A ruling on the meaning of section and on conflict handling would settle the design. The example must then resolve every selected module exactly once, expose the conflict rather than conceal it, and account for all existing consumers before any move.

## Inquiry 3: When does a small model decide to wake a topic? · mind-context › inquiry/topic-wake-judgment.md, a new file

+ ### Open questions
+ Does the judgment apply only when input has no explicit destination, or can it defer an order already addressed to a metaflow? What should happen when several topics fit, or none does? Which declared model and budget should be used, and where should an uncertain decision go?
+
+ ### What Mind knows
+ The Flow vision says a small model judges whether to wake an idle topic and at which layer. It also gives addressed orders, questions and the living's words a waking effect. Core's audit found waking by request type but no small-model topic judgment. These two statements do not, on their own, tell us whether judgment may veto an explicitly addressed request.
+
+ ### What is being tried
+ Mind is framing four cases for the review: an addressed order, an unaddressed remark about one topic, input relevant to two topics, and input with too little context. No model evaluation or routing experiment is claimed. The comparison will show what information each decision needs and whether a decision changes the authority of the original request.
+
+ ### What would settle it
+ A ruling on these four cases would establish the judgment's scope. A later bounded trial would need to preserve the original input, report uncertain decisions, and demonstrate that a wrong or failed judgment neither loses the request nor starts an unauthorized flow.

## Inquiry 4: How should Nexus vision follow code modules? · mind-context › inquiry/nexus-module-vision.md, a new file

+ ### Open questions
+ Is one vision module required for every source module, or for each coherent responsibility that may span several files? Where do shared principles live so that specialized modules do not copy them? Should the first example be the shared Nexus library or Chronos?
+
+ ### What Mind knows
+ The Nexus vision asks for vision split by code modules and distinguishes Signal, Operation and Memory. Core's audit found the common Nexus vision still in one file. A source-file split and a responsibility split can differ; neither is established as the intended granularity by that observation.
+
+ ### What is being tried
+ Mind is comparing those two mappings before proposing any move. A single effect, followed from its incoming signal through operation and memory to its response, is the candidate example. No complete mapping or repository reorganization has been produced. The comparison should expose both duplicated rules and responsibilities that the current code has not separated.
+
+ ### What would settle it
+ A reviewed mapping of that effect would settle the initial granularity and location of shared rules. Its value must be shown by finding the governing vision from each participating code module and locating the implementation of each vision statement, without inventing a match where none exists.

## Inquiry 5: What proves the Chronos example is implemented? · mind-context › inquiry/chronos-implementation.md, a new file

+ ### Open questions
+ Must the first accepted implementation cover the entire approved fourth edition, or may a named subset land while the rest stays open? Which independent reference and tolerance should establish numerical correctness? What evidence should show that Chronos is also a sound example for other Nexuses?
+
+ ### What Mind knows
+ Core records approval of the fourth edition of Chronos. Its proposed vision includes solar and lunar arcs, a declared ephemeris range and location selection. Core's audit distinguishes that approval from a landed vision module and completed implementation. The existing Chronos and Prototyping authors retain the work. Passing a parser or compiling generated types cannot alone establish correct numerical answers.
+
+ ### What is being tried
+ This inquiry separates three questions previously compressed into completion: whether the approved text is landed, whether the numerical behavior agrees with an independent reference, and whether the implementation demonstrates the Nexus architecture. No numerical test is claimed here. The existing owners should supply a coverage example with normal inputs and boundary cases before a reduced first scope is treated as acceptable.
+
+ ### What would settle it
+ A ruling on scope, followed by agreed reference cases and tolerances, would settle numerical acceptance. A review of the same examples through Signal, Operation and Memory would establish which architectural claims are demonstrated and which remain open.

## Inquiry 6: What is the executable Ethos contract now? · mind-context › inquiry/ethos-implementation.md, a new file

+ ### Open questions
+ Does doing without traits in the short term mean omitting trait declarations from Ethos while retaining handwritten implementation traits, or also removing the implementation requirement? May the approved separator-whitespace and single-declaration Type changes land independently of that decision?
+
+ ### What Mind knows
+ Core's audit found separator-whitespace and Type work on proposal branches rather than main. It also found a branch that refuses a declared type without a trait, while reporting the instruction to do without traits in the short term. The long-term goal places types and traits in Ethos. These observations expose a conflict; they do not authorize Mind to choose one reading silently.
+
+ ### What is being tried
+ Mind is separating the language accepted now from its long-term anatomy. The next comparison should show the same small declaration under both short-term readings, the generated code each requires, and the current consumer that can or cannot use it. This book does not claim that comparison or downstream tests have run. Existing branch authors retain their work pending the ruling.
+
+ ### What would settle it
+ An explicit short-term trait ruling would settle the conflict. If whitespace and Type may proceed separately, acceptance must show their exact parser and generator revisions working together, including spaces, tabs and line breaks after separators, malformed-input refusals, and a real consuming declaration. Branch existence alone does not settle publication or deployment.
