## 2026-09-26 addendum: live-link relay and TCP scope

**Relay grade:** Field Sol `9ac67c` relayed a read-only **delegated Field peer-coordination witness**, not user-provided evidence and not independently re-witnessed by this flow: the Ouranos USB to Prometheus integrated-Ethernet link has carrier at 1 Gb/s and bridge forwarding, and Kea received then ACKed a fresh `DHCPREQUEST` from Prometheus's NIC for `10.44.0.148`. This corrects the original provenance wording in this addendum. It agrees with this flow's earlier direct Ouranos-side bridge, neighbor, and DHCP evidence, but it does not upgrade the relay into a direct Prometheus host observation.

This rules against a physical or L2 failure on **that first hop at that relay time**. It does not address Prometheus's separate USB-downlink-to-Zeus cable, any other adapter, or the older simultaneous `NO-CARRIER` report for that downstream leg. A DHCP ACK establishes that the server answered the client MAC; it does not establish that Prometheus applied the address, selected its return route, admitted TCP/22, or had a listening SSH service.

The one timeout in this flow must also be read narrowly. On Ouranos, `/etc/hosts` maps `prometheus.goldragon.criome` only to Yggdrasil IPv6 `200:ca41:6b12:fba:d7bc:cfc6:4aaa:165f`; OpenSSH was therefore aimed at that overlay destination, not `10.44.0.148`. The timeout is compatible with an overlay route/peer/firewall failure and says nothing directly about TCP/22 on the cable address. The local neighbor table currently has one stale mapping of `10.44.0.148` to the expected Prometheus MAC; it supplies no duplicate-address evidence.

### Ranked remaining hypotheses and discriminating passive read

1. **Yggdrasil overlay reachability or policy failure to the hostname's IPv6 address — strongest for the observed timeout.** Read the Prometheus and Ouranos Ygg peer/route state and both relevant IPv6 firewall counters, together with `ip -6 route get` for the exact address. This must remain distinct from the cable path.
2. **Prometheus DHCP client did not retain/apply `10.44.0.148`, or lacks the expected cable return/default route.** Read Prometheus `networkctl status` for its integrated NIC, `ip address`, `ip route`, DHCP lease/event log, and resolved link state. The ACK alone cannot resolve this.
3. **TCP/22 listener or input-policy fault on Prometheus's cable interface.** Read `systemctl` state for sshd, `ss -lntp` bind addresses, and the exact nft input-chain rules/counters for TCP/22 on the integrated interface. No direct cable TCP probe was made, so neither refusal nor drop is observed.
4. **Prometheus's separate USB-downlink selection/bridge ownership remains wrong.** Read the actual generated `05-usb-eth`/`30-usb-eth` rule, udev `ID_BUS` and driver for the downstream adapter, networkd ownership, bridge membership, and Zeus's carrier. This is the historical driver-match defect's proper scope; it does not explain the cable-to-Prometheus Ygg timeout by itself.
5. **AP client-specific fault.** It remains unranked: no fresh Zeus/phone association, lease, route, or AP station record exists. Earlier AP success excludes only a general historical service outage.

**Separate historical cache fact:** the prior Field record attributes a Prometheus firewall policy that dropped TCP/80 arriving from the Ouranos USB path, matching one bounded cache HTTP timeout. That is a historical explanation for that cache path only. It does not explain the TCP/22 timeout to the Yggdrasil hostname, and it must not be used to infer current TCP/80 policy or any TCP/22 rule without a Prometheus-local nftables witness.

## Causal assessment

1. **Most likely blocker for direct Prometheus-to-Zeus cable now: physical carrier loss or the original USB-match deployment gap.** The former has prior simultaneous carrier-loss evidence; the latter has a specific deployed-generation causal chain. They are alternatives until current Prometheus and Zeus link state, bridge membership, and networkd match are read. The current Ouranos-to-Prometheus DHCP lease proves neither.
2. **AP failure is not established.** Earlier AP association and DHCP evidence show that AP service could work. A failure to reach Zeus through AP could instead be a missing Zeus Wi-Fi association/IP/default route, AP client isolation/firewall, or the AP's Internet/NAT path. A fresh client attempt with its MAC, time, and failure stage is required to distinguish those.
3. **The cable and AP are separate L2 entrances into the same Prometheus router LAN (`br-lan`) in the reported design.** If the stated bridge is current, a Zeus Wi-Fi client and Zeus USB-Ethernet client should receive the same 10.18.0.0/24 gateway/DNS and differ only at association/carrier. This is an inference from reported configuration, not a current read.
4. **A second wireless association is a poor substitute for the cable transfer path.** It may recover reachability, but the living's existing transport record favors direct Ethernet for heavy Nix paths and Yggdrasil/DNS only for activation. Use it as an acceptance variant, not proof that the durable cable downlink works.

## Smallest permanent declarative proposal

Port the already-described `usb-downlink` composition into current CriomOS `main` only if a source diff proves it is absent from `d04257a8`; otherwise, the smallest delta is materialization/deployment plus the acceptance below. The exact known implementation is `946bcbd501f14050c04d6025bc879a4e72fc0122` on `usb-downlink-da88cf`; this report cannot claim it is current main code.

* Select USB Ethernet by stable udev bus role (`Type=ether`, `ID_BUS=usb`) while excluding the declared WAN, not by a driver list and not by a guessed interface name.
* On a Router such as Prometheus, attach that selected link to `br-lan`; keep Kea, DNS, forwarding, firewall, and masquerade in the router module as the sole DHCP/NAT owner. Do not add a second NetworkManager shared profile or NAT owner.
* On non-router nodes such as Ouranos, use `br-downlink` with its own declared subnet and the existing cable default route; NetworkManager must leave only those USB links unmanaged. The local state already shows this shape operating, but it is not a durable-deployment claim.
* Express uplink/downlink roles in typed topology data. The direct hardware fact can choose a USB downlink only after the intended use is confirmed; a USB tether may be an uplink. The durable schema must allow an explicit exception or per-link role.

This proposal changes ownership selection rather than AP security or transmit power. It directly addresses the historical **Prometheus-to-Zeus USB-downlink** match failure and prevents competing DHCP/NAT managers. It is not a repair for the delegated live Ouranos-to-Prometheus L2/DHCP first hop, and it is not a repair for the observed Yggdrasil-hostname timeout. A source-only comparison of `946bc…` and `d04257a8` is the required next fact before calling it either an already-implemented fix or a new source delta.

If a current Prometheus-local passive read confirms the historical TCP/80 drop and the cache is intended to be reachable over the cable, the smallest separate declarative delta is an interface- and source-subnet-scoped TCP/80 allow to the cache listener, before the router's default drop. It must not broaden TCP/22 or become an AP/client rule. If it does not confirm that rule/listener/path, make no cache firewall change. TCP/22 requires its own listener, destination-address, and input-counter evidence first.

## Field acceptance procedure (proposal only; do not run without a change/deployment authority)

1. Capture immutable source, generated configuration, deployed generation, and rollback generation. Verify the intended WAN and each selected USB interface from udev properties before activation; reject ambiguous USB links and a WAN selected as downlink.
2. With cable uplink present, activate one bounded generation with console/out-of-band recovery available. Verify Prometheus retains its upstream default route and Internet before any downstream assertion.
3. Attach Zeus by its intended Ethernet path. Read link carrier on both ends, networkd ownership and bridge membership on Prometheus, Zeus DHCP lease, default route via `10.18.0.1`, DNS query through the gateway, and a bounded HTTPS request. Verify Prometheus→Zeus SSH/Nix-store handshake with strict known hosts; run no deployment as part of this network acceptance.
4. Test optional AP client mode separately: associate Zeus to the recorded AP without removing cable, then verify Wi-Fi lease/default/DNS/HTTPS and strict SSH. Record which route is selected. Disconnect Wi-Fi and confirm cable is still selected; reconnect cable and confirm it recovers after hotplug. The AP test must not be accepted as cable proof.
5. Negative cases: unplug/replug the downstream USB Ethernet only; remove upstream cable; attempt an unintended USB interface; and verify no duplicate DHCP, no second masquerade/NAT owner, no default route moves to the downlink, and no management loss. Check that existing AP clients retain association/leases through a cable hotplug.
6. Roll back only to the captured previous generation if cable Internet, AP clients, DHCP/DNS, the intended default route, or management access regresses. Do not delete a pre-existing operational bridge until its declarative replacement has passed steps 2–5. A physical `NO-CARRIER` outcome stops configuration testing and moves to cable/adapter/port inspection; it is outside a declarative rollback.

## Missing facts that block a definitive fix

* Current Prometheus deployed revision and rendered `30-usb-eth`/`05-usb-eth` rule, plus current networkd status for its USB link.
* Current Zeus carrier, wired and Wi-Fi addresses/routes, and whether it is actually associated to the Prometheus SSID.
* The intended permanent role of each physical USB Ethernet adapter, particularly whether a USB tether is an uplink exception.
* A timestamped phone or Zeus AP attempt identifying failure stage: visibility, authentication, DHCP, DNS, or Internet.
* Current bridge/NAT/firewall counters on Prometheus, needed to distinguish path forwarding from client association.
