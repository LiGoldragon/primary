Startup Syntax

A proposed Ethos and Datom slice for Flow startup — turning the design into visible syntax so the types and their values can be reviewed together.

Provisional — not deployed, not a final approved schema. Every identifier below is a declared fixture, not a live launch.

The asynchronous shape

A Start is accepted before a Flow is ready. Observe is one subscription — an initial snapshot, then changes — never a polling loop.

Selection is not expansion

The first subscription snapshot only acknowledges the attempt:

Started.launch-a
Observe.launch-a
Observed.{ launch-a None Accepted }

A later update observes expansion actually in progress — and it can lag selection:

Observed.{
  launch-a
  Some.native-session-a
  ExpandingSkills.{
    [ main-flow refresh spirit behavior nexus ethos datom ]
    [ main-flow refresh spirit behavior ]
  }
}

  • The first vector is RequiredSkills; the second is ExpandedSkills. Here nexus, ethos, and datom were selected but had not yet entered the expanded vector — selection alone proves nothing.

  • The schema does not itself prove main-flow was expanded first — the native adapter still has to demonstrate that ordering in the actual input.

Failure never silently retries

Early rejection, before an attempt is even accepted:

StartRejected.UnknownModel.gpt-unknown
StartRejected.NativeBindingRefused.MissingNativeSession
ObserveRejected.UnknownLaunch.launch-missing

Binding failure can also surface after acceptance, on that same attempt:

Observed.{ launch-a Some.native-session-a Failed.SkillNotExpanded.nexus }

These are separate fixture outcomes. No automatic deletion or unchanged retry counts as a repair.

Ready is its own, later attempt

Started.launch-b
Observe.launch-b
Observed.{ launch-b Some.native-session-b Ready.{ 7a9c22 evidence-start-b } }

FlowId appears only inside Ready — matching the first-prompt readiness boundary. A name like evidence-start-b is a fixture reference; a name alone does not prove expansion or publication actually happened.
