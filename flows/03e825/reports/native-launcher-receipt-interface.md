# Native launcher plan and receipt interface (2026-09-21)

For Mind Medium `2c61af`, the Flow adapter owner `e798f3`, and Field `03e825`. This records the current Primary Codex launcher; it is not a proposed Flow schema or a launch authorization. No native seat was started for this report.

## Supported entry and paths

`tools/native-seat-launch.mjs --seat <profile> [--profile-file FILE] [--fresh | --predecessor SIX_HEX] --cwd /home/li/primary` prints a JSON **plan** by default. `buildPlan()` returns `version: 2`, `seat`, `cwd`, `model`, `effort`, `role`, `predecessor`, `ancestor`, `canonicalRole: {aspect,power}`, `provisionalTitle`, `profileSha256` (external profiles), `sourceAudit`, `requiredSkillNames`, `requiredMainFlow`, `sources: [{path,sha256}]`, `sourceManifestSha256`, `firstPromptSha256`, and `safety`. The plan deliberately omits the first prompt body from default JSON output; `--prompt` prints it. Source records are requested local-file hashes, not native observations. `requiredSkillNames` includes `testing-flow-titles`; `main-flow` is required. See `tools/native-seat-launch.mjs:88-110,302-304`.
`buildPlan()` has no parameters and is not exported; the CLI options above supply its inputs. Its default path reads audited local source files and prints the plan without starting or touching a native seat.

The caller may supply `--receipt /absolute/path.json`; otherwise the launcher chooses `<cwd>/.native-seat-receipts/<seat>-<--name or unnamed>.json`. The batch controller always supplies `<directory of its --state file>/receipts/<agent>.json`, records that path as `seat.receipt` in its state, and for Claude also writes `<agent>.manifest.json` beside it. `--verify-thread`, `--activate`, and `--finalize-title` require the explicit receipt path. See `tools/native-seat-launch.mjs:113-115,260-304` and `tools/native-batch-refresh.mjs:91-106`. Existing historical examples include `flows/6db4fe/mind-sol-native/receipts/mind-sol.json` and `flows/6db4fe/field-sol-native/receipts/field-sol.json`; their `version: 3` receipts predate the new title fields and must not be promoted to `ready` by inference.
No live `version: 3` receipt with the new provisional/canonical title fields was found in the inspected examples. The new title fields and `ready` transition are source and fixture contracts, not a claimed live launch receipt.

## Codex receipt and evidence grades

Fresh `--launch` and guarded `--adopt-herdr-thread` write a JSON `version: 3` receipt before the first turn, initially `created` or `adopting`, then `pending`. It contains `seat`, exact native `threadId`, `turnId` once returned, optional `generationId`, requested `model`/`effort`, `firstPromptSha256`, `sourceManifest` (`path`,`sha256`), `sourceManifestSha256`, and `skillManifest` (`name`,`path`,`source`,`sha256`) loaded from the native `skills/list` paths. New receipts also contain `provisionalTitle` and `canonicalRole`. Adoption adds `herdr` binding (`session`, pane, agent, terminal, workspace and revisions). The manifest and receipt fields describe the submitted input; `skillManifest` alone is **not** expansion proof. See `tools/native-seat-launch.mjs:185-257`.

`verifyReceipt()` requires the same native thread and target first turn, observed `turn_context` model and effort, exact prompt digest, exact expanded skill count/path/source digests, source-manifest digest, receipt-only response, and native title readback when a provisional or canonical title is recorded. If app-server turn expansion is unavailable, `verifyRolloutReceipt()` checks the target native rollout's session, turn context, typed skill input, expanded skill source content and receipt-only response; it records a `rolloutEvidence: {path,sha256,verifiedAt}` snapshot. A matching first-turn witness changes the on-disk status to `verified` and outputs `readiness: "native-context-verified-title-pending"`; an incomplete turn outputs `pending`. The rollout digest is a snapshot of a live file, not a permanent full-file hash. See `tools/native-seat-launch.mjs:115-139,205-220,249-257,302`.

`--activate --receipt FILE` accepts a `verified` first-turn receipt and starts a separate activation turn; its output is `activation-started`, not title readiness. After that seat claims its own Flow ID, `--finalize-title --seat <same profile> --receipt FILE --flow-id SIX_HEX` checks the exact `flows/.<id>.flow-id` marker against the receipt's native thread UUID and `harness=codex`, role/model/effort/title skill, reads the before-title, sets `<Aspect> <Power> <own Flow ID>` through native `thread/name/set`, and reads it back. Only then does it write `status: "ready"`, `canonicalFlowId`, `canonicalTitle`, `titleVerifiedAt` and output `readiness: "native-ready"`. Failure to read back attempts rollback to the provisional title. See `tools/native-seat-launch.mjs:260-300`.

`tools/native-batch-refresh.mjs` validates a version-1 batch manifest and may select/launch, but its Codex path uses guarded adoption and records `native-pending` after first-turn verification; it does not claim an ID or finalize a title. Its `publicState().launchAttemptsSettled` includes pending and failed attempts, and `allNativeVerified` requires each seat's `phase: "native-verified"`; neither is a substitute for inspecting the exact receipt and native readback. See `tools/native-batch-refresh.mjs:48-70,91-106,117-132`.

## Integration boundaries

The launcher's accepted role metadata is an explicit canonical `Psyche|Mind|Field` plus `High|Medium|Low|Ultra Low`, or the mapped legacy `Field/Mind Astra` to High and `Field/Mind Sol` to Medium. Power is not derived from model or effort. External profiles must meet their existing authorization, audited source, and native-skill checks; app-server `--launch` currently permits only the specifically authorized Mind Sol, Field Sol, and Field Astra external profiles. Other seats are not made launchable by a valid selector result. See `tools/native-seat-launch.mjs:45-80,100-110,223-230`.

A Flow consumer can use the plan to check its requested selector/profile inputs, then the exact receipt path and `version: 3` fields to correlate a native thread/turn and source bundle. It must distinguish `pending`, `verified` first-turn context, and post-claim `ready`; it must independently preserve the exact native model/effort and Herdr pane/terminal binding. There is no exported `buildPlan`, `launch`, or `finalizeNativeTitle` library API: the supported surface is this CLI plus exported pure verifiers/helpers at `tools/native-seat-launch.mjs:304`. The current tests are `tools/native-seat-launch.test.mjs` and `tools/native-batch-refresh.test.mjs`; they exercise fixture launch/adoption, typed expansion, title claim mismatch, readback and rollback. Fixtures do not grant live readiness.
HM route binding, Message delivery/reply, task acceptance, and predecessor retirement are separate evidence outside this launcher. A `native-ready` title receipt alone proves none of them.
