psyche-context/skills/vision-flow.md

Under «Short term», after Proposal 1's paragraph.

Words used here: a route is the messenger's record of where a flow is reached: its pane (the terminal area in herdr, the third-party terminal program the flows run in) and its aspect, topic and layer. A flow in transition is one being replaced. A held message is one the messenger did not type; it keeps it as a pending record (a message stored to be typed later) in its Datalevin database (the database the messenger keeps all its records in).

Sources: flow d68c82, 2026-10-13. The long-term counterpart already stands in «What it does»: "a metaflow under refresh queues what arrives until its successor has started."

Removed: none.

Added, the vision:

Short term: the messenger also marks a flow in transition when its context reaches its threshold. From then on it holds every message addressed to that flow's metaflow instead of typing it in, so the flow can write its handover and be replaced rather than be kept turning by new arrivals. When the successor registers, the messenger delivers what it held to it, oldest first.

Witnessed in messenger-clj today: a route carries a :transition mark (typed_store.clj, the route schema); in-transition? reads it; a send to a marked route is held with the reason InTransition and stored as pending. No command sets or clears the mark, and only repair releases a held message, and only one held for a broken route. A marked flow cannot send at all: sender-origin! refuses it. A message held in transition does not keep its sender's envelope, so it could not be delivered later as it was sent. The messenger has no daemon and no listener of its own: each command runs once and ends.

The machine's design, each a numbered choice below:

A. Who sets the mark. A1: the context-refresh hook, right after its warning is delivered, so the warning itself is not held. A2: the flow itself, when it begins its handover.

B. The marked flow's own sending. B1: it still sends (its handover messages to topic flows need this). B2: it sends nothing; its handover is a file only.

C. Who releases. hm-register is the messenger command that records a new flow's route; hm-retire is the one that takes a flow's route out of use for good. C1: the successor's registration (hm-register with the same aspect, topic and layer) delivers the held messages and retires the predecessor. C2: retiring the predecessor (hm-retire) moves them.

D. The tools. D1: the launcher and the messenger stay two tools; the launcher already registers each flow through the messenger. D2: they become one tool.

Lands in messenger-clj/src/messenger_clj/core.clj. Setting the mark (under A1 the hook runs it; under A2 the flow does):

+ (defn mark-transition! [flow on?]
+   (with-reservation flow
+     (fn []
+       (let [route (read-route flow)]
+         (save-route! (registry) flow
+           (assoc route :transition on?))
+         (str (if on? "InTransition" "Live")
+              ".{ " flow " }")))))

main.clj gains the command transition FLOW on|off, and the hm-transition shorthand beside the others.

Keeping the sender, in held!:

- repair-envelope (when (= reason
-                          :RepairRequired)
+ repair-envelope (when (#{:RepairRequired
+                          :InTransition}
+                        reason)

Under B1, in sender-origin!:

- (when (or (needs-binding? route)
-           (in-transition? route)
-           (:route_hold route))

+           (:route_hold route))

Releasing, under C1 at the end of register!, under C2 in retire!. deliver-held! types one stored envelope into the successor's pane by the same steps repair! uses today. Oldest first is by time: the existing pending-for sorts by a random id.

+ (defn transition-held [flow]
+   (->> (store/pending-for (root) flow)
+        (filter #(= :InTransition
+                    (get-in % [:attempt
+                               :reason])))
+        (sort-by #(get-in % [:attempt :at]))))
+
+ (defn release-held! [successor]
+   (let [address (metaflow!
+                   (read-route successor))]
+     (doseq [[flow route] (route-records)
+             :when (and (not= flow successor)
+                        (in-transition? route)
+                        (= address
+                           (metaflow! route)))
+             held (transition-held flow)]
+       (deliver-held! successor held))))

Lands in the Nexus, long term: crates/flow-nexus/src/delivery.rs refuses a flow that is stopped, retired or exited and passes one that is pending or active; there is no state for a flow being replaced, and crates/flow-nexus/src/lib.rs refuses every queue request because Flow holds no queue yet. The lifecycle is declared in signal-flow, the repository of the message types the Nexus sends and receives (Signal is the name of that typed message format):

- FlowLifecycle.[ Pending Active Stopped
-   Retired Exited ]
+ FlowLifecycle.[ Pending Active Refreshing
+   Stopped Retired Exited ]

and delivery.rs stores a message for a Refreshing flow instead of typing it.
