## Checks made by the source checker

The publication CLI calls `check-book` before rendering. The standalone checker requires exactly one absolute readable source path; the builder itself accepts its source/output paths and reports read/write failures. Both load their configuration/data files through the corresponding readers; unreadable or malformed files fail rather than producing a successful page.

1. **Page structure:** known Presentation kind; permitted title/signature placement; located proposal headings; a real change or deletion in each proposal; at least one proposal except in an Account; prose/headings outside proposals only where the page kind or authenticated module view permits them. The check does not require a Presentation line/title in every possible source: legacy forms remain accepted.
2. **Locations and provenance:** repository/path syntax and safe relative paths; belief repositories restricted to authored module locations; origin main resolved through `git ls-remote`, with a regular blob at that revision. Missing remote/revision/blob/source refuses. Whole module views must reconstruct the current module exactly, including removals and move-source text. Plain proposal paragraphs must exist in their named source module; `shown` excerpts must be exact contiguous source lines. Comments cannot supply provenance.
3. **Descriptions:** front matter is not printed as book content; descriptions use the labelled container, at the head and once. Empty/malformed descriptions, unchanged signed descriptions, changes outside a proposal and mismatches against current module metadata refuse. Current Markdown module views with descriptions and new Markdown modules require the container. In-place description changes stand at the module head and authenticate their removed text.
4. **In-place proposals:** legal placement inside the named module view; same-module or correctly declared move endpoints; actual changes; proper move/description/comment structure; proposed marker permitted only as the first nonblank content of a Review proposal. The remaining view must be the source as it stands.
5. **Containers:** exact open/close forms for comments, shown excerpts, descriptions, moves and proposed markers; no unexpected close/nested container; comments nonempty, once, before changes; shown containers carry a valid location and nonempty authenticated excerpt; move bodies/endpoints/form must be coherent; second comments/descriptions/moves refuse where restricted.
6. **Move edits:** inline removed/added word marks close on the same line, contain words and do not nest; moved-source reconstruction retains removed words and excludes added words. Added move lines must say something. Code-fence contents are treated as code rather than parsed as prose word marks.
7. **Fences and signs:** closed fences; proposal fences name their language; Markdown is not stranded as plain code; signed Mermaid fences use one consistent sign on every line, with signed intentional blanks. Ethos fragments distinguish whole documents, changes, context-only and malformed mixtures; context alone is not a change. Retired `File:` body lines and quote blocks refuse.
8. **Closing Questions:** a legal Questions section follows a proposal/module (or an Account's prose); later proposals/headings, comment/shown/description/move/proposed containers, change marks, code fences and quote blocks refuse inside it. Its ordinary prose is accepted through the end of source. This checks the supplied source: it cannot recover questions already removed from that source before the build.

## Checks made during rendering

- The renderer independently parses its blocks and refuses malformed/unclosed/nested shown, comment, description and move forms, invalid shown location/excerpt shape, and misplaced proposed markers.
- It reads the source, page-code and configuration files; CLI errors, validator failures and output I/O failures end the command unsuccessfully.
- A parsed authored figure graph requires nodes and edges that name existing nodes. An illustration must begin as SVG; the renderer strips scripts, foreign objects, event handlers, external references and unsafe URLs, namespaces local IDs/references, and maps its paint to the page theme. These transformations are not a semantic comparison of the drawing against its diagram source.
- Every Mermaid fence that must be drawn requires its ordered SVG asset, and that asset must render as an illustration. Missing/unreadable/unrenderable required figures refuse with the figure name. Mixed Mermaid change signs refuse. **Other legacy optional diagrams may still be omitted with a warning** rather than failing the page.
- Under the CLI's Ethos gate, added/standing whole Ethos and applicable root-headed changing fragments go through the configured validator. Bare declarations are checked as an implied Library. Rejected Ethos or unavailable validation refuses. Authenticated module excerpts/views are not independently whole-document Ethos. Since fd83f44, a wholly removed fence is historical text: it keeps highlighting and is not checked. A changed fragment's reconstruction is still checked where the root-headed rule applies.
- Syntax highlighting uses the configured grammar and tree-sitter when available. Missing/failed highlighting can fall back to plain code with a warning. That is **not** a refusal and not proof that highlighting occurred. Width itself is not a publication gate.

## Checks of the emitted page

`check-built-page`, called by `build` before output is written, currently checks:

1. Page chrome (`meta`, `title`, `h1.book-title`) is not emitted inside an authenticated module article. It names the offending element.
2. Adjacent rendered `.del` and `.add` blocks that repeat a majority of the shorter passage's words are refused as **`replaced-line-printed-twice`**, naming both complete passages and their line. Balanced nested divs are included. This catches the former two-description-block output. It is a targeted generated-HTML check, not a general DOM validator or a detection of arbitrary semantic repetition. Rendered code-line/table-row shapes remain a follow-up scope.

The ordinary word-diff renderer now prints prose/headings and replaced descriptions once, including unrelated old/new descriptions with no shared words. Removed tokens are struck through and additions marked inline, under the normal change margin. There is no low-overlap fallback.
