# Flow 0.24.0: session id per Nexus, refused launches released, sema-engine 0.18.0

Subflow of f1c841, worktree `~/wt/github.com/LiGoldragon/flow/next-f1c841`
(Orchestrate lock 11715, that path only). flow-test is untouched and still

## What landed on flow main (0.24.0)

1. **Session id carries the Nexus.** `ChoosesNativeSession` now lives on
   `HerdrCli` and derives the Claude session id from SHA-256 of
   `flow-claude-session-v2 \0 <ordinary socket path> \0 <launch request id>`,
   UUIDv5-shaped. The ordinary socket is the one the store configures (the
   same path exported as FLOW_SOCKET), so two Nexuses sharing `~/.claude`
   choose different sessions and different `flow-id` claims for one
   request id. Reserve, Spawn (`--session-id`) and Bind's verification all
   call the one method. Test: `herdr::reservation::tests::two_nexuses_never_choose_one_session_for_one_request`.
2. **Refused after Reserve, released.** New Operation `Release.FlowId`,
   Outcome `Released` (ethos `crates/flow-nexus/ethos/operation.ethos`,
   generated module regenerated by the pinned ethos-zero through build.rs).
   `start` now runs everything after Reserve in `launch_reserved`; when that
   answers `StartRejected` and Reserve gave a FlowId, it performs
   `Release`: the store retracts the held events row (unless the flow was
   registered), then `ReleasesFlowIdentity` on `HerdrCli`, under the
   claim's own `.<id>.flow-id.lock`, removes the empty lane and the marker
   (Claude markers only; a lane with content keeps its claim). Reserve
   also releases when it claims but cannot hold. The old test that pinned
   the leak was rewritten as
   `tests::reservation::a_claude_launch_refused_after_reserve_gives_back_its_flow_and_claim`;
   it was seen failing with the Release call disabled, then passing.
   Store unit test `store::events::tests::a_released_reserved_flow_is_no_longer_held`;
   claim test `herdr::reservation::tests::a_refused_launch_gives_back_its_empty_claim`.
3. **Codex FLOW_ID / FLOW_SOCKET: gap, not built.** The codex-harness
   skill shows no way to name or learn a Codex session before it starts.
   A Herdr-launched Codex is `codex --remote unix://<app-server socket>`:
   the thread id is assigned by the app server at `thread/start`, after the
   pane command runs, and the TUI has no session-id flag. Its shell tools
   run inside the remote app server process, not in the pane, so a pane
   `export` (the Claude mechanism) would not reach them at all. The only
   route seen in the code is Flow's own direct app-server path
   (`codex.rs` `thread/start` with `config.shell_environment_policy.set`
   FLOW_ID/FLOW_DIRECTORY), which works because there Flow starts the
   thread itself. Closing the gap needs Flow to start the thread over the
   app server first (learning its id, claiming the FlowId, setting
   FLOW_ID and FLOW_SOCKET through `shell_environment_policy.set`), then
   attach the TUI to that thread; whether `codex --remote` can attach to an
   existing thread was not verified.
4. **sema-engine 0.18.0.** Repinned from 516f01fe (0.16.0) to 9884905
   (0.18.0); the underlying `sema` kernel is unchanged in Cargo.lock. Its
   0.17/0.18 changes are additive for Flow (Flow declares no `with_prior`).
   Witness: a copy of `~/.local/state/flow/flow.sema` opened under the
   repinned `FlowStore::open` with its configuration
   (`/run/user/1001/flow/flow.sock`) and 26 flow rows read back. The copy
   was opened, so its bytes changed (an open commits); the live store was
   only copied.
